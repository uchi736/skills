# AIエージェントによる論文再現ワークフロー

研究論文の再現は「翻訳タスク」であり「拡張タスク」ではない。
論文という人間可読な仕様書を、機械可読なコードに変換する作業として
位置付けることで、エージェントを創造的問題解決者ではなく、
忠実な翻訳者として運用する。

## このスキルを使うタイミング

- AI/ML系論文の手法を、自分の環境で動くコードベースとして再現したい
- 再現の過程で、論文の前提・落とし穴・実装上の判断を理解したい
- 再現済みコードを起点に、派生研究や応用検証を進めたい
- 複数論文を同じスキームで再現し、コード品質と一貫性を保ちたい

逆に、以下の場合はこのスキルではなく別のアプローチを推奨する。

- 論文の中身を読み解きたいだけ（要約・解説）→ 別の読解スキル
- 既存OSSをそのまま使いたい → リポジトリのREADMEに従う
- 完全自動化された再現を目指す → 本スキルは人間介入を前提とする

## 前提知識：なぜこのアプローチが有効か

**論文 = 仕様書という再定義**：
査読を通過した論文は、原理的には自己完結した手法仕様である。
だからこそ「論文を読んで→コードを書く」という工程は、
創造性ではなく忠実性が問われる翻訳作業として捉え直せる。
この再定義により、エージェントの暴走（論文に書かれていない最適化を
勝手に入れる、新しい工夫を加える等）を抑制しやすくなる。

**人間の役割の転換**：
コードを書く役割をエージェントに渡す代わりに、人間は
「読む・テストする・理解する・方向付ける」役割に専念する。
これにより、再現作業の副産物である「研究者の理解の深化」が
むしろ強化される。コードは資産、理解はそれ以上に重要な資産。

**構造的中庸**：
完全に固定化された再現パイプライン（論文ごとにテンプレートを書き分ける）と
完全に自由なエージェント運用（プロンプト一発で丸投げ）の中間に位置する。
タスク分解と検証ポイントを構造化しつつ、各タスクの中身は
論文ごとの実情に応じて柔軟に決める。

## 全体フレームワーク

ワークフローは初期化フェーズと実装フェーズの2段で構成する。

```
[初期化フェーズ]
  ↓ 論文 + 初期プロンプト
  /plan   : エージェントが論文を読み、明確化質問→タスク分解（約10個）を提案
  ↓ 人間が計画を検証・修正
  /setup  : 機械可読な仕様（project.json）にコンパイル
  ↓
[実装フェーズ]  ← 各イテレーションで1タスクのみ実行
  ┌──────────────────────────────────────┐
  │ 次タスクを取得                          │
  │   ↓                                   │
  │ サブエージェントが並列で実装・検証      │
  │   ↓                                   │
  │ テスト合格？  ── No → 修正してリトライ  │
  │   ↓ Yes                               │
  │ チェックポイント？ ── No → 次タスクへ   │
  │   ↓ Yes                               │
  │ エージェントが要約 → 人間が /chat で検証│
  │   ↓                                   │
  │ 承認？ ── No → 修正指示                │
  │   ↓ Yes                               │
  │ 次タスクへ                             │
  └──────────────────────────────────────┘
  ↓ 全タスク完了
[成果物：再現コードベース + 人間の理解]
```

各イテレーションの境界はgitコミットで区切る。
これにより、いつでも作業を中断・再開できる。

## 初期化フェーズの詳細

### 初期プロンプトの設計

初期プロンプトは、再現の「スコープ」と「合格条件」を確定させるために
最も重要な人間入力。後の作業全体を方向付けるため、ここで時間を使う。

含めるべき要素：

- **対象論文**：arXiv IDまたはURL。補助資料があれば併記
- **再現範囲の限定**：論文全体ではなく、再現する手法・実験の範囲を明示
  （例：「ParticleNet-Lite モデルのみ、top tagging タスクのみ」）
- **合格条件となる指標**：論文記載の数値を明示
  （例：accuracy、AUC、特定の閾値での背景棄却率など）
- **計算環境の制約**：GPU有無、フォールバック条件
- **使用フレームワーク**：PyTorch + Lightning、JAX等を指定
- **smoke-test モード**：少量データで全パイプラインを通せる仕組みを要求
  （`--n-events N`のような形）
- **バージョン管理付き出力**：実験を比較可能にするため `--version i` 形式
- **不確実性の扱い**：論文と同じ統計手法を使うことを明示

「論文と同じやり方で不確実性を扱え」のような明示指示は、
エージェントが勝手に簡略化するのを防ぐ。

### 計画の作成と検証

`/plan` フェーズではエージェントに以下をさせる。

1. 論文（と参考資料）を読み、不明点を質問させる
2. 約10個のタスクへの分解案を `plan.md` として提案させる
3. その中の数タスクに「チェックポイント」フラグを付与させる

人間側でチェックすべきポイント：

- タスクの粒度：1タスクが1日で終わるくらいの大きさか
- 依存関係：データ準備 → モデル定義 → 学習 → 評価 の順序が妥当か
- チェックポイントの配置：誤りの伝播コストが大きい箇所に置かれているか
  （データ前処理の直後、モデル定義の直後など）
- 抜け漏れ：論文に書かれている前処理・正規化・後処理が漏れていないか

人間からの修正指示で plan.md を更新したら、`/setup` で
project.json（機械可読な仕様）に変換する。これ以降の実装フェーズは、
project.json を「契約書」として進む。

## 実装フェーズの詳細

### 1イテレーション = 1タスクの原則

各イテレーションでは、計画上のタスクを1つだけ取り出して実装する。
理由は2つ。

- **コンテキストウィンドウの圧縮**：1タスク分の情報だけを集中的に扱う
- **状態の永続化と再開可能性**：タスク境界でgitコミットすれば、
  後日でも作業を再開できる

イテレーション間の状態引き継ぎは、以下の最小セットで完結させる。

- git のコミット履歴（コードの状態）
- project.json（計画と仕様）
- progress.txt（現在の進捗）

「会話履歴を保ち続ける」必要はない。エージェントが新しい
イテレーションを始めるたびに、これらのファイルから状態を復元できる
構造にしておく。

### サブエージェントによる並列分業

各イテレーション内では、専門サブエージェントに並列で仕事を割り振る。

- **論文分析担当**：該当タスクに関連する論文の記述を抽出する
- **コード担当**：実装する
- **テスト担当**：テストファースト方式で検証コードを書く
- **統計担当**：統計手法・不確実性評価が絡む部分を担当する
- **批評担当**：モジュール性・テスト容易性・堅牢性の観点でレビューする

並列分業の狙いは、専門性によるコンテキスト分離。
1つのエージェントに全部やらせるより、各エージェントの
コンテキストを軽く保つほうが品質が安定する。

「批評担当」を独立して置くのが要点。コードを書いた本人ではない
視点から、冗長性・テストの薄さ・依存関係の濫用などを指摘させる。

### チェックポイントの運用

チェックポイント付きタスクが完了したら、エージェントに以下を
させてから人間に制御を渡す。

1. その回のタスクで実装した内容の要約
2. 動作確認のためのコマンド例
3. 関連するテストの実行方法
4. 起こりうる問題の事前アラート

人間は要約だけで判断せず、必ず以下を実施する。

- 実際にコードを動かす
- 中間出力を可視化する（特徴量分布など）
- 論文と数値を突き合わせる
- 「論文に書いていないこと」をエージェントが追加していないか確認する

修正が必要なら `/chat` インターフェース（または通常の会話）で
具体的に指示し、エージェントに作り直させる。

## 人間介入の3類型

人間からエージェントへの介入は、目的別に3種類に分類できる。
自分の介入がどのカテゴリに偏っているかを意識すると、
ワークフロー自体の改善ポイントが見えてくる。

| 類型 | 内容 | 例 |
|------|------|-----|
| 必須介入 | 論文への忠実性に必要な情報・修正 | 「論文の式(3)では学習率を10エポックごとに半減と書かれている」 |
| 任意介入 | 論文の範囲外の追加スコープ | 「ついでに混合精度学習も入れて」 |
| メタ介入 | ワークフロー操作 | 「コミットして」「次に進んで」 |

そして複雑度別にも分類できる。

| 複雑度 | 内容 |
|--------|------|
| 高 | 方法論的洞察、スコープ確定、密度の高い指針 |
| 中 | 具体的なパラメータ・データセット・修正の指示 |
| 低 | 承認、エラー報告、軽い言い回し |

**第1メッセージは必ず「高・必須」になる**。
ここで再現対象と合格条件を提示するため。これ以降の介入が
「中・必須」（具体的な修正）と「低・メタ」（コミット指示）に
集中していれば、エージェントの自律性が高い証拠。

「高・必須」の介入が中盤以降に頻発する場合は、
初期プロンプトの記述が不十分だったサインなので、
次回はそこを補強する。

## 制限事項と落とし穴

### 微妙な実装差異

エージェントは、論文との微妙な実装差異を入れ込むことがある。

- 学習率スケジュールの形（cosine vs step decayの混同等）
- 活性化関数の選択（GeLU vs ReLU等）
- プーリング・集約方法の選択（mean vs max等）

最終指標への影響は小さいことが多い。対策として、
「論文の実装と一致しているか確認せよ」という明示的な
クロスチェックプロンプトを、チェックポイント時に必ず投げる。

### ドメイン知識が必要な失敗モード

自動テストでは検出不可能な、ドメイン特有の罠が存在する。
論文の元データセットの仕様を熟読しないと気付けない種類の
バグで、これが最も危険な失敗モード。

具体例：分類タスクのデータセットに、正解ラベルそのものが
入力特徴として含まれていることがある。これを読み込んでしまうと、
タスクが自明化して見かけの精度が異常に高くなる。

対策：

- データセットの公式ドキュメントを必ず人間が読む
- 入力特徴の分布を可視化し、明らかに異常な分離が出ていないか確認する
- 訓練が論文より明らかに簡単に収束したら疑う
- ベースライン（ランダム特徴）でも同様の精度が出ないか確認する

### 自動テストの過信

ユニットテストが通ることと、論文を正しく再現していることは別。
テストが網羅できるのは「実装内部の整合性」であり、
「論文との一致」は人間の目視・計算による比較が要る。

## チェックリスト

### 初期プロンプト

- [ ] 対象論文と再現範囲（モデル・タスク・指標）を明示したか
- [ ] 合格条件となる数値を論文から書き写したか
- [ ] 計算環境とフレームワークを指定したか
- [ ] smoke-testモードと出力バージョン管理を要求したか
- [ ] 不確実性評価の方法を明示したか

### 計画レビュー

- [ ] タスク粒度は適切か（1タスク1日以内）
- [ ] 依存関係の順序は妥当か
- [ ] チェックポイントが伝播コスト大きい箇所に置かれているか
- [ ] 論文の前処理・後処理が漏れていないか

### チェックポイントごと

- [ ] 実際にコードを動かして動作確認したか
- [ ] 中間出力（特徴量分布など）を可視化したか
- [ ] 論文との数値比較を実施したか
- [ ] エージェントが論文外の最適化を勝手に入れていないか

### 最終検証

- [ ] 論文の指標値と再現値の差は許容範囲内か
- [ ] 第三者が独立に動かせる状態になっているか（環境構築、データ取得を含めて）
- [ ] 学習済みモデルを論文外のスクリプトで再評価できるか
- [ ] データセット由来の落とし穴（ラベル漏洩等）を確認したか

## 発展的応用

### 複数論文への横展開

同種の論文（例：物体検出系の異なる手法）を同じスキームで
再現していくと、計画フェーズのテンプレートが洗練されていく。
タスク分解に共通パターンが見えたら、それを再利用可能な
雛形として固める。

### サンドボックス環境

エージェントが暴走的にファイルシステムやネットワークを
操作するリスクを抑えるために、コンテナで隔離して動かす運用が
推奨される。少なくとも以下を制限する。

- ファイルシステムアクセス：作業ディレクトリと特定の入出力先のみ
- ネットワーク：論文配布元（arXiv等）、パッケージリポジトリ、
  限定された外部API のみ許可

### 会話ログの分析による改善

ワークフローを何度も回したら、各回の人間メッセージを
類型×複雑度で分類して傾向を見ると改善ポイントが分かる。
「メタ介入が多い」→ 自動進行の仕組みが弱い。
「中・必須が中盤以降に多い」→ 初期プロンプトが不足。

## アンチパターン

### 1イテレーションに複数タスクを詰める

コンテキストが膨れ上がり、エージェントが文脈を見失う。
原則を守る。

### 計画フェーズを省く

「とりあえずプロンプト一発で全部やって」と頼むと、
論文の前処理が抜けたり、合格条件が曖昧になったりする。
計画フェーズの15分は、後の数日を救う投資。

### チェックポイントを承認だけで通す

「動いてるみたいだから承認」では人間がいる意味がない。
必ず実コードを動かし、論文と数値を突き合わせる時間を取る。

### 自動テストの結果を最終判断にする

テストは「実装内部の整合」を見るもので、
「論文との一致」は別途の検証が要る。両方やる。

## 参考情報

このスキルは、Birk他「A Scientific Human-Agent Reproduction Pipeline」
（2026, arXiv:2604.18752）で提案された SHARP フレームワークの
方法論的知見をもとに構成している。SHARP は粒子物理学における
ジェット分類タスクの再現を題材として、コード生成エージェントと
人間の協働ワークフローを実証した。

関連する設計原則として、同著者らによる FlexCAST
（モジュール性・テスト可能性・堅牢性を柱とする科学データ解析の
設計原則, arXiv:2507.11528）と、Geoffrey Huntley の Ralph Pattern
（反復的なエージェント運用パターン）がある。

このスキルは SHARP の特定実装（Claude Code 上の `/plan`、`/setup`、
`/chat` スキル群、claude-hpc サンドボックス、claude-parser 解析ツール）
には依存しない一般化されたワークフローとして書かれている。
特定の実装ツールが必要な場合は SHARP のリポジトリ
（github.com/stanford-ai4physics/sharp）を参照されたい。
