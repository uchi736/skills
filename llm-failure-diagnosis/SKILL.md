# LLM失敗診断スキル（4次元フレームワーク）

LLMやエージェントの出力が期待通りでないとき、「なぜ失敗したのか」を
構造的に切り分けるためのスキル。混合した失敗をひとつずつ解きほぐし、
対応策の選択を誤らないようにする。

---

## このスキルを使うタイミング

- エージェントやRAGシステムの出力がおかしいが、原因が分からない
- 対応策（RAG追加、Fine-tuning、プロンプト調整など）の前に診断したい
- 複数のモデル・エージェントを比較評価する枠組みが欲しい
- 評価ベンチマークを自社業務向けに設計したい
- ユーザーからのバグ報告を分類したい

「出力が悪い→とりあえずRAG」のような反射的対応を避けるために使う。

---

## 前提知識: 4次元フレームワーク

LLMの生成は概念的に3段階で動く。

1. **記憶検索**: 内部パラメータから関連情報を取り出す
2. **指示理解**: ユーザーの制約・形式要求を把握する
3. **推論**: 取り出した情報を組み合わせて答えを作る

この3段階のどこで壊れるかによって、失敗は4つに分類できる。

| 次元 | 略称 | 何が起きているか |
|------|------|-----------------|
| 知識エラー | KE | 内部知識が間違っている・古い |
| 知識欠落 | KM | そもそも必要な知識を持っていない |
| 推論エラー | RE | 事実はあるが論理で繋げられない |
| 指示追従エラー | IFE | 知識も推論もOKだが形式や制約を破る |

重要な原則: **4次元は独立に扱う**。
ひとつを改善する施策が、別の次元を悪化させることがある。
混ぜて考えると対応を誤る。

---

## 診断ワークフロー

### Step 1: 症状を具体的に書き出す

「なんとなく変」で止まらず、何がどう違うかを文章化する。
以下の観点で見る。

- 含まれる事実は正しいか
- 必要な情報は揃っているか
- 論理の飛躍や矛盾はあるか
- 指定した形式や制約は守られているか
- 言語や長さは指示通りか

### Step 2: 一次切り分け（決定木）

以下の順で質問していくと、主要次元に当たる。

```
Q1: 出力は指示された形式・制約を守っているか？
  NO  → IFE（指示追従エラー）の可能性
  YES → Q2へ

Q2: 出力に含まれる事実関係は正しいか？
  事実が明確に間違っている
    → KE（知識エラー）
  「わからない」と言うべき場面で無理に答えた
    → KM（知識欠落）
  事実は正しいが組み合わせ方や結論がおかしい
    → RE（推論エラー）
```

順序が大事。IFEを先に切り分けるのは、形式違反が他の評価を
無意味にするから（JSON壊れてたら中身の正誤以前）。

### Step 3: 下位分類に落とし込む

主要次元が決まったら、典型パターンに当てはめる。
下位分類まで絞ると対応策が具体化する。

#### KE（知識エラー）の下位分類

- **FD 事実歪曲**: 一般に知られた事実を誤認（例: 発明者の誤り）
- **IMC 内部記憶矛盾**: 同じ事実を問い直すと答えが揺れる
- **EIC エンティティ混同**: 同名・類似エンティティの情報を取り違える
  （例: 別のX氏の経歴を混ぜる、多義語の語義を取り違える）

#### KM（知識欠落）の下位分類

- **DSK ドメイン固有知識**: 専門分野の新しい/ニッチな内容が欠落
- **FK 架空知識**: 実在しない事柄について無理に答える
- **TK 時事的知識**: 学習カットオフ後の情報を推測で埋める
- **NPK 非公開知識**: 私的・内部情報を推測で生成する

#### RE（推論エラー）の下位分類

- **LF 論理誤謬**: 前提から無効な結論を導く
- **PF 手続き失敗**: 多段推論で途中ステップを飛ばす
- **IIF 情報統合失敗**: 長文やノイズから必要情報を抽出できない
- **MRF 数学的推論失敗**: 計算・アルゴリズム推論のミス

#### IFE（指示追従エラー）の下位分類

- **EF 明示フォーマット**: JSON・XML・テンプレートの構造違反
- **LC 長さ制約**: 文字数・段落数・項目数の上下限違反
- **LgC 言語制約**: 指定言語外で応答、言語混在
- **CCL 複雑・認知負荷**: 否定（〜するな）・条件付き指示を無視、
  キーワード包含/禁止の見落とし

### Step 4: 対応策を選ぶ（トレードオフに注意）

次元が特定できたら対応策を選ぶ。
ただし各対応策には副作用がある。以下は代表的なマッピング。

| 主症状 | 候補手法 | 改善が期待できる次元 | 悪化する可能性のある次元 |
|--------|---------|---------------------|-------------------------|
| KE | RAG、知識更新、外部検索 | KE | IFE（形式乱れ）、RE（文脈内矛盾の処理負荷） |
| KM | RAG、拒否プロンプト、知識拡張 | KM、KE | IFE、RE |
| RE | CoT、Self-Consistency、Reasoning系モデル/SFT | RE | KE、KM、IFE |
| IFE | 制約強化プロンプト、Instruct tuning、スキーマ検証 | IFE、一部KE | RE（推論の単純化） |

**経験則として意識しておくこと**:

- Few-shot デモを増やしても、主にフォーマット補助にとどまる。
  根本原因（知識不足など）は解決しないことが多い
- Instruct tuning を強めると、指示追従と一部の知識整合は改善するが、
  推論の丁寧さは落ちる傾向がある
- Reasoning系のSFTや蒸留は推論を伸ばすが、
  知識関連や制約遵守が弱くなることがある
- Chain-of-Thought の出力は、実際の内部推論を
  忠実に反映しない場合がある。ステップの存在を正解の証拠にしない

## 内部メカニズムを踏まえた診断のコツ

### KEとKMは注意の向き方が違う

- **KEのとき**: 入力に正しい証拠が書いてあっても、モデルは自分の
  パラメトリック知識に引っ張られる。注意が広く拡散し、決め手になる
  証拠トークンを素通りする。
  → 「証拠を信じさせる」工夫が必要（引用強調、対比提示、根拠要求）

- **KMのとき**: 内部知識が弱いので、入力中の誤誘導に過剰に
  吸着する。間違った文脈に注意が集中して、誤答を強化する。
  → 「誤情報を疑わせる」工夫が必要（不確実性の明示、反証検討、
  拒否オプションの提示）

同じ「文脈を与える」でも、KE向けは信頼性の裏付け、
KM向けは警戒心の喚起、という発想の違いがある。

### 拒否はコストが高い

「わからない」と答えることは、モデルにとって計算的に重い動作。
活性ニューロンが増え、注意もより分散的に働く。
つまりデフォルトでモデルは拒否を避けるバイアスを持つ。

これを知っておくと、KMへの対策がなぜ効きにくいかが分かる。
「知らないなら知らないと言え」と一文足すだけでは不十分で、
拒否が選択肢として浮上するような文脈設計が要る
（例: 選択肢に「情報不足」を明示する、信頼スコアを出させる）。

## 複数次元が絡むケースの切り分け

実運用の失敗は複数次元が同時に起きていることが多い。

典型的な組み合わせ:

- **KE + IFE**: 誤情報を整った形式で出す（一番厄介。形式が綺麗で
  信じてしまう）
- **KM + RE**: 知識が足りない上に、埋め合わせる推論も誤る
- **IFE + RE**: 形式制約に気を取られて推論が雑になる
- **KE + RE**: 間違った事実を使って一貫した推論をしてしまう

### 単純化による切り分け手順

入力を段階的に単純化して、どの要素を取り除くと失敗が消えるかを見る。

1. **知識系を切り分ける**: 必要な事実を文脈に明示的に与えて再実行
   - 失敗が消える → KMだった（知識がなかっただけ）
   - 失敗が残る → KE（知識を与えても自分の誤知識で上書きしている）

2. **推論を切り分ける**: 事実を極端に単純化して、論理だけ残す
   - それでも失敗 → RE単独
   - 単純化で成功 → IIF（情報統合の容量問題）の可能性

3. **指示を切り分ける**: 形式制約を外して意味内容だけ問う
   - 中身は合っていた → IFE単独
   - 中身も違う → IFE + 他

この切り分けは、1つの事例について3〜4回モデルを回す必要がある。
重要な失敗事例ほど、このコストを払う価値がある。

## チェックリスト

### 診断を始める前
- [ ] 失敗の症状を具体的に文章化したか（「変だった」で済ませていないか）
- [ ] 再現できる最小入力を持っているか
- [ ] 期待される出力が明確か

### 診断中
- [ ] 4次元のどれに該当するか仮説を持ったか
- [ ] 下位分類まで絞り込んだか
- [ ] 複数次元が絡む場合、単純化で切り分けを試したか
- [ ] KEかKMかを混同していないか（証拠を与える実験で確認したか）

### 対応策選定前
- [ ] 候補手法のトレードオフを認識しているか
- [ ] 悪化しうる次元への影響を評価する計画があるか
- [ ] 施策前後で全4次元を比較できる評価セットを用意したか
- [ ] 「1つの次元を直す」ではなく「トレードオフを許容できる範囲に収める」
  という目線で見ているか

## 業務への応用アイディア

### エージェント品質管理
自社で運用するエージェントごとに、4次元の失敗率を定期測定する。
どの次元が強く、どの次元が弱いかをプロファイル化して、
エージェント選定・配置の判断材料にする。

### RAG評価の設計
RAGシステムの評価で「正答率」だけ見ると、KEとKMとREが
ごちゃ混ぜになる。評価セットを4次元で切り分けて設計すると、
改善施策（取得器を直すか、生成器を直すか）が明確になる。

### モデル乗り換えの判断
新モデルがリリースされたとき、既存モデルと比較する際に、
H-Score（4次元の平均失敗率）で見ると総合判断できる。
ただし、業務特性によってはRE偏重で見るべき場合もある（医療診断、法務）。
一律の平均ではなく、業務別の重み付けを決めておく。

### ユーザーのバグ報告分類
エンドユーザーから「変な答えが出た」と報告があったとき、
サポート担当者がこの4次元で分類するテンプレを持つと、
開発チームへのエスカレーション精度が上がる。

## 限界と注意点

- **診断は万能ではない**: 失敗の原因が次元のどれにも綺麗に
  収まらないケースはある。4次元は便利な第一近似であって、
  終着点ではない

- **LLM-as-a-Judgeのバイアス**: 診断作業を別のLLMに
  自動化させる場合、判定LLM自身の4次元バイアスが混入する。
  特にIFE・REは判定モデルとの一致が取りにくい

- **CoTの見かけに騙されない**: ステップバイステップ出力が
  あるからといって、それが実際の内部推論を反映しているとは
  限らない。REの診断では最終出力と過程の両方を別々に見る

- **マルチモーダルには未整備**: 視覚・音声の失敗は本スキルの
  射程外。モダリティごとの追加診断軸が必要

- **動的知識には弱い**: 時系列で変わる知識の追従問題は、
  静的診断では捉えきれない。TK（時事的知識）の失敗率は
  測定時点に強く依存する

## 発展的応用

### スキル自体の拡張

- 業界特化の失敗パターンを下位分類として追加する
  （例: 医療ならKE_Drug、法務ならKE_Precedent）

- ツール使用エージェントへの拡張: ツール呼び出しの失敗を
  別の次元として追加する余地がある（Tool Use Error）

- マルチエージェント系への拡張: エージェント間の伝言ゲーム
  失敗は、複数のKE/KMが連鎖する問題として再定義できる

### 診断の自動化

- 4次元判定をLLM-as-a-Judgeでパイプライン化する際は、
  各次元ごとに独立したプロンプトで判定させる
  （1つのプロンプトで4次元を同時に判定させると混線する）

- 人手レビューとの一致率を継続的に測定し、
  判定モデルのバイアスをキャリブレーションする

## 参考情報

この4次元診断フレームワークは、LLM幻覚ベンチマーク研究における
「生成パイプラインの段階別失敗分類」のアイディアを診断実務向けに
再構成したもの。具体的には、記憶・指示・推論の3段階を基盤に、
知識誤り/知識欠落/推論ミス/指示違反の4次元で失敗を独立に
評価する直交性原則と、主要な緩和策間のトレードオフに関する
実証的知見に基づく。

元論文はベンチマーク構築の観点で書かれているが、本スキルは
それを現場のエラー切り分けと対応策選定の道具に再構成している。
