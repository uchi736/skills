# Test Scenario Generalization: 初期テストからのシナリオ汎化

開発者が書いた1つのテストケースを「シナリオの種」として扱い、
そこから本来あるべき複数のテストシナリオを系統的に展開する。
ブランチカバレッジでは捉えられない要件由来のテストシナリオを
網羅することを目的とする。

## このスキルを使うタイミング

- フォーカルメソッドに対して初期テストが1つだけあり、追加テストを派生させたい
- 既存テストスイートの「抜け」を発見したい（重要なシナリオの取りこぼし検出）
- レビュー時に「このテストパターンは他にどう変奏すべきか」を網羅的に提案したい
- ブランチがほぼないメソッド（setterやファサード）に対するテスト設計が必要

このスキルは「ゼロからのテスト生成」ではなく「既存テストを起点とした汎化」に特化する。
完全自動化ツールではないため、初期テストはユーザーまたは別ツールが用意する前提。

## 前提となる考え方

**核心仮説**: 開発者が書いた1つのテストには、そのテストが体現している
「潜在的なシナリオテンプレート」が暗黙に含まれている。テンプレートを
明示化して変動点（VP）を特定すれば、同じテンプレートから別のシナリオを
派生させられる。

**3つの主要な失敗モード**を意識しておく：

- **暗黙的パターン認識の失敗**: 変更可能なコード要素は無数にあるが、
  そのうち真の変動点（テストシナリオを区別する要因）はごく一部
- **シナリオ具体化の失敗**: 変動点を見つけても、それに代入すべき
  プロジェクト固有の値（代替API、許容パラメータ）を知らないと汎化できない
- **オラクルの誤り**: フォーカルメソッド自体にバグがある場合、
  実装から導いたオラクルも誤っている可能性がある

**コードカバレッジ駆動との違い**: テストシナリオは制御フローの分岐とは
必ずしも対応しない。分岐がないメソッド（setterなど）でも複数のシナリオが
存在する。よって分岐網羅を最大化するアプローチは原理的に行き詰まる。

## 全体ワークフロー

```
[Input] フォーカルメソッド + 初期テスト + コードベース
   │
   ├─ Stage 1: シナリオ理解の強化（MOM）
   │    オラクル変異エクササイズで理解度を試験し、不足知識を取得
   │
   ├─ Stage 2: シナリオ汎化
   │    テンプレート生成 → 変動点設定 → インスタンス化
   │    （プロンプトに変動点識別ルールを組み込む）
   │
   └─ Stage 3: テスト生成
        インスタンスごとにテスト生成 → 実行 → エラーフィードバックで修正
   │
[Output] 多様なシナリオを網羅した実行可能テスト群
```

## Stage 1: シナリオ理解の強化（Masked Oracle Modeling）

**目的**: LLMが要件とテストシナリオを十分に理解しているかを「試験」し、
不足している場合はプロジェクト知識を取得する。

### なぜ「試験」が必要か

LLMに「お前はこのメソッドを十分理解しているか？」と直接問うと、幻覚で
「理解している」と答える。理解度は決定論的に測れる方が信頼できる。
オラクル選択という具体的タスクで間違うかどうかは、行動として観測可能。

### 手順

1. **誤オラクル候補の生成**
   - 初期テスト中の各アサーションについて、最大10個の「誤った」オラクルを生成
   - 重要な制約: 構文上はコンパイル可能であること（存在しないAPIを捏造しない）
   - 期待値の改変、引数値の変更、比較演算子の反転などで生成

2. **誤オラクルのフィルタリング**
   - コンパイルエラーや実行時エラーになるものは除外
   - 「アサーション失敗」を引き起こすものだけ残す
   - 残らなければ、生成し直し

3. **多肢選択試験**
   - LLMに正しいオラクルを選ばせる
   - **重要なプロンプト指示**: 
     - 「自信がある場合のみ回答する」
     - 「APIやフィールドの存在・値を推測してはいけない」
     - 「判断に必要な情報が不足していると思う場合は、回答せず必要な情報を列挙する」

4. **知識取得のトリガー**
   - LLMが「情報不足」を申告した場合、または不正解を選んだ場合 → 知識取得
   - 取得対象: フォーカルメソッドや初期テストが直接参照するシンボル
     （親クラス、オーバーライドされたメソッド、呼び出されているヘルパーメソッドなど）の定義
   - 範囲を限定する理由: コンテキスト長を抑えつつ意味的完全性を保つため

5. **反復ループ**
   - 回答 → 知識取得（必要なら）→ 再評価
   - 最大3回で打ち切り

### 設計上のポイント

- **誤オラクル生成の質**: 「実行可能だがアサーション失敗」を満たすことが重要。
  この条件はLLMにフォーカルメソッドの実際の挙動を考えさせる効果がある。
- **取得粒度**: シンボル全体を取得するよりも「定義 + 使用例数件」が良い。
  特に分岐の多いヘルパーメソッドは、本体を見ないと挙動が読めない。

## Stage 2: シナリオ汎化

**目的**: 初期テストから「シナリオテンプレート」を生成し、それを複数の
「シナリオインスタンス」に具体化する。

### 用語の整理

| 用語 | 定義 |
|------|------|
| 変動点（VP） | シナリオを区別する要因。コード要素または高レベルの設計選択。具体的な値を割り当てると個別シナリオになる |
| シナリオテンプレート | フォーカルメソッドを多様なシナリオで検証するための半構造化計画。ステップの列で構成される |
| シナリオインスタンス | テンプレートのすべてのVPに具体値を割り当て、対応するオラクルを決めたもの |
| 主オラクル | 実装と取得した知識から導出したオラクル |
| 代替オラクル | 一般的な要件知識から推論したオラクル。実装にバグがあれば設計欠陥を露見させうる |

### Step 2.1: テンプレート生成

LLMに以下の3要素を持つステップ列を出力させる。

- **Act（行動）**: テスターが行うべき命令文（自然言語）
- **VP（変動点）**: 0個以上の変動可能な要素
  - コード要素（特定のAPI、パラメータ）または抽象オブジェクト（「描画形状」など）
  - 各VPには候補設定リストを伴う
- **DP（依存関係）**: 先行ステップで定義されたVPへの参照（任意）

テンプレートは初期テストに見られるパターンを抽象化し、開発者が想定しうる
シナリオすべてを派生できる粒度で書く。

### Step 2.2: 変動点識別の精度を高める2つの仕掛け

#### 仕掛けA: 自動チューニングされた識別ルール

変動点識別の精度はプロンプト中の「ルール」に強く依存する。手作業で
ルールを書くと網羅性が低く、矛盾も生じやすい。これを自動化する。

**チューニング手順**:

1. データセット準備
   - フォーカルメソッド、初期テスト、グラウンドトゥルーステンプレートの組
   - グラウンドトゥルーステンプレートは複数の既存テストの差分から構築し、人手で検証する
2. プロジェクト単位で訓練/テストに分割（Leave-One-Project-Outを推奨）
3. 各エポックで以下を反復：
   - 現プロンプトでテンプレート生成
   - グラウンドトゥルースとの差分から「足りない/余分なVP」を特定
   - LLM自身に「ルールをどう調整すべきか」のフィードバックを生成させる
   - バッチ内のフィードバックを統合（補完的な提案を併合し、矛盾は最も
     一般的な提案を残す。特定のフォーカルメソッドに過適合させない）
4. 全エポックで記録したプロンプトをテストセットで評価し、F1最大のものを採用

**経験則**: 

- ハイパーパラメータの目安はエポック3、バッチサイズ5
- ゼロショット・少数ショット・手書きルールよりも自動チューニング後が
  精度・再現率ともに優位（2〜3割の精度向上が期待される）
- 少数ショットは参照例の選び方に影響され、3例より2例の方が良い場合もある
  （文脈長の制約とのトレードオフ）

#### 仕掛けB: プロジェクト知識の能動的取得

VPやその候補値は、フォーカルメソッドや初期テストの外側にあることが多い。
LLMにプロンプトの中で能動的にクエリさせる。

**クエリの典型例**: 

- 引数の型がインタフェース／抽象クラスなら、サブタイプ一覧を取得
  （例: `Paint`型の引数 → `Color`, `GradientPaint`, `RadialGradientPaint`, `TexturePaint`）
- 引数として使われているオブジェクトのファクトリメソッドを取得
- 類似機能のAPI（`fillRect` → `fillOval` のような兄弟関係）を取得
- 同一クラス内の関連メソッド（`set`系と`get`系のペアなど）

**実装基盤**: CodeQLでオフラインに全クラス・コンストラクタ・メソッド・
フィールドの定義と呼び出し関係を索引化しておく。クエリに応じて関連
シンボルを返す。プロジェクト全体を毎回スキャンする必要はない。

### Step 2.3: 構造化インスタンス化

テンプレートからインスタンスを作る際、自然言語で全文を生成させない。
**構造化された設定だけ**を出力させ、決定論的にテンプレートに埋め込む。

LLMに出力させるもの：

- 各VPに対する選択された設定
- 設定間の依存関係
- 対応する主オラクル
- 候補となる代替オラクル

検証ロジック（決定論的処理側）：

- すべての設定が宣言済みのVPを参照しているか
- すべての参照が有効なテンプレートステップを指しているか

### 設計上のポイント

- **なぜ構造化を分離するのか**: LLMに「テンプレートとインスタンス両方を
  自由形式で出せ」と頼むと、ステップ構造との整合性が崩れたり、
  存在しないVPに値を割り当てたりする。意思決定（設定選択）と
  自然言語生成（テンプレート埋め込み）を分けることで両方の質が上がる。
- **代替オラクルの価値**: 主オラクルが実装由来である以上、実装のバグは
  検出できない。代替オラクルが主オラクルと食い違う場合、それは
  「実装が要件を満たしていない可能性」の警告として機能する。

## Stage 3: テスト生成と修復

**目的**: 各シナリオインスタンスを実行可能なテストコードに変換する。

### 手順

1. **初回生成**
   - 入力: フォーカルメソッド、初期テスト、関連知識、シナリオインスタンス
   - LLMに具体的なJavaテストコード（または対象言語のテスト）を生成させる

2. **コンパイル・実行**

3. **エラーがあれば修復ループ**:

   a. **エラーメッセージの抽出**
      - プロジェクト外（サードパーティ依存）のメッセージは除外
      - 正規表現でエラー対象のプログラム要素と位置を特定

   b. **位置ベースの知識取得**
      - JDTLS（Eclipse JDT Language Server）等のLSPで、エラー位置から
        該当メソッドの実装などを取得
      - CodeQLとの違い: CodeQLは「シンボル名→定義」、JDTLSは「位置→定義」に強い

   c. **修復プロンプト構築**
      - フォーカルメソッド、生成テスト、エラーメッセージ、取得した知識を統合
      - LLMに「このエラーをこの知識を使って直せ」と指示

   d. **再試行**: パスするか、最大3回まで

### 設計上のポイント

- エラーメッセージ駆動の知識取得は既存研究でも有効性が確立されている
- このステージはStage 1-2の質が低いと効果が薄い。Stage 3で何度も
  修復が走る場合、シナリオ自体が無理筋である可能性が高い
- 修復で「エラーを消すために本来のシナリオから逸脱した」テストが生まれることがある。
  完成したテストが元のインスタンスと整合しているかの確認が必要

## チェックリスト

### 入力品質
- [ ] フォーカルメソッドが少なくとも1つの開発者作成テストでカバーされているか
- [ ] フォーカルメソッドがトリビアル（単純なgetter/setter）でないか
- [ ] 初期テストがフォーカルメソッドを直接または単純なラッパー経由で呼んでいるか

### Stage 1
- [ ] 誤オラクルがコンパイル可能でアサーション失敗を引き起こすものに限定されているか
- [ ] LLMが「不確実」と申告できる選択肢を与えているか
- [ ] 知識取得を初期テスト/フォーカルメソッドが直接参照するシンボルに限定しているか

### Stage 2
- [ ] テンプレートのVPは「シナリオを区別する要因」に絞られているか
- [ ] 些末な値（`fillRect`の座標など）をVP扱いしていないか
- [ ] 候補設定がプロジェクト固有の知識に裏付けられているか
- [ ] 主オラクルと代替オラクルを両方提示しているか

### Stage 3
- [ ] 修復が3回以上走るインスタンスは設計を見直しているか
- [ ] 生成されたテストが本来のシナリオと整合しているか（修復で別物になっていないか）

### 出力評価
- [ ] グラウンドトゥルーステストとの突合（mutation-basedとLLM評価の両方）
- [ ] 既存テストスイートに対する増分（追加で殺せるmutant、追加カバレッジ）

## 制限事項と注意点

### 1. オラクル品質はメソッドの正しさに依存する
フォーカルメソッドにバグがある場合、主オラクルも誤る可能性がある。
代替オラクルで緩和するが、完全な解決ではない。重要なメソッドでは
人間によるオラクル確認の介入ポイントを設ける。

### 2. 知識取得の取りこぼしリスク
Stage 1の「試験」でLLMが偶然正解した場合、本来取得すべき知識が
取得されない。改善方向: プロジェクトの知識グラフを能動的に探索する、
試験を複数の異なる角度から行う、など。

### 3. 言語汎化性
パイプライン自体は言語非依存だが、自動チューニングしたルールは
対象言語の慣習に依存する。新しい言語に適用する際は、その言語の
データセットでルールを再チューニングする必要がある。CodeQL/LSPは
複数言語をサポートしているのでツール側の障壁は低い。

### 4. 初期テストの品質への依存
オラクルが除去された初期テスト、変数名が一般化された初期テストでも
ある程度動作するが、品質の良い初期テストほど良い汎化が得られる。
スモークテスト程度の最小入力でも約60%のシナリオカバレッジは
維持できることが報告されている（緩やかな劣化）。

### 5. コスト
1テストあたり約12Kトークン、約2分の処理時間が目安。Stage 1の
LLM呼び出しを静的解析やミューテーション解析で部分的に置き換える
余地がある。

## 評価方法

シナリオカバレッジを以下の2つの指標で測定する。両指標を併用する理由は、
それぞれに長所と短所があるため。

### Mutation-based シナリオカバレッジ
- 各テストが殺せるmutantの集合の重なりで類似度を測る
- ground-truthテストと生成テストの最大重みマッチングを取り、平均する
- 連続値[0, 1]で部分的な一致も検出できる
- 1つのground-truthテストが複数シナリオを兼ねている場合、過小評価になる

### LLM-Assessed シナリオカバレッジ
- LLMに「生成テストのいずれかがこのground-truthシナリオを満たすか」を
  二値判定させる
- 1つのテストが複数シナリオを兼ねる場合や、変異キル集合が違っても
  シナリオ的に等価な場合に有効
- 一致と判定されたテストは次の評価から除外（ダブルカウント防止）
- LLMの非決定性を抑えるため温度0、複数回実行で平均化を推奨

### 補助指標
- ブランチカバレッジ・行カバレッジ・ミューテーションスコア
- 既存テストスイートへの増分（augment後の改善）
- 個別テストではなく**テスト群全体**で評価する

## 落とし穴とアンチパターン

### 落とし穴1: 「changeableなものは何でもVP」病
変更可能なコード要素を片っ端から変動点と見なすと、テンプレートが
冗長になり、本当に重要なVPが希釈される。

**典型例**: モックされた引数をVP扱いしてしまう。モックされている時点で
開発者はその振る舞いをシナリオの一部と見なしていないというシグナル。

**典型例**: 接続タイムアウト値などの「他のVPで決まれば自動的に決まる」
パラメータを独立VP扱いしてしまう。

### 落とし穴2: 依存VPの独立扱い
他のVPの設定から従属的に決まる値（例: ファイルパスがdrawing操作に
依存）を独立VPと誤認すると、無意味な組み合わせ爆発が起きる。
依存関係（DP）を明示する。

### 落とし穴3: コードカバレッジの誘惑
シナリオカバレッジを上げる過程で、副次的にコードカバレッジが上がる
ことがあるが、シナリオに無関係なクラスを巻き込んでカバレッジを稼ぐと
「メンテしにくい・本質が見えにくい」テストになる。シナリオへの
忠実性を優先する。

### 落とし穴4: テンプレートの粒度ミス
テンプレートが細かすぎる（実装に張り付きすぎ）と汎化できず、粗すぎると
意味のあるシナリオを生成できない。良い目安: 「同じテンプレートで
3〜10個のシナリオが派生できる」程度の粒度。

### 落とし穴5: グラウンドトゥルーステンプレートの質不足
プロンプト自動チューニングはグラウンドトゥルースの質に強く依存する。
複数テストの差分を機械的に取るだけでなく、人手で「これは本当に
シナリオを区別する要因か？」を確認する工程は省略しない。

## 発展的応用

### 応用1: ツール組み立て
このスキルは「初期テストありき」だが、初期テストを別の自動生成
ツール（EvoSuiteなど）に作らせ、その出力を本スキルに渡す合成
ワークフローが可能。完全自動でのシナリオ網羅テスト生成パイプラインに
近づく。

### 応用2: レビュー支援
プルリクエストでテストが追加された際、本スキルを使って
「同じパターンで他にこれだけのテストがありうる」をレビュアーに
提示できる。レビュー観点の網羅性チェックに使える。

### 応用3: シナリオドキュメンテーション
生成されたシナリオテンプレートそのものが、フォーカルメソッドの
ふるまい仕様の半形式的記述として価値を持つ。テストの傍らに
ドキュメントとして保管する。

### 応用4: フィールド検証
本スキルで生成したテストの一部は、ground-truthに含まれない
「開発者が見落としていたシナリオ」を捉える。実際のOSSプロジェクトに
PRとして提出することで、有用性を経験的に検証できる。
論文の事例では27件中16件が受理されたと報告されている。

### 応用5: 要件発見
代替オラクルが主オラクルと食い違う、あるいは「対応するfunctionalityが
未実装」のためテストが失敗するケースは、しばしば「未文書化の要件」や
「実装の取りこぼし」を露見させる。テスト生成の副産物として要件レベルの
気づきが得られる。

## このスキルが向く場面・向かない場面

| 向く場面 | 向かない場面 |
|----------|--------------|
| 既に1つ良質なテストがある | テスト皆無で、ゼロから生成したい |
| 高レベル設計選択（パラメータ、API選択）に意味がある | 純粋な計算ロジック（数値範囲を網羅したい） |
| プロジェクト固有の慣習・APIファミリーが豊富 | 標準ライブラリのみで完結する単純メソッド |
| ブランチが少ないがシナリオは多い | ブランチが多くカバレッジ駆動で十分 |
| 要件が暗黙でドキュメント化されていない | 形式的仕様書がある（プロパティベーステストの方が適切） |

## 参考情報

このスキルは、LLMベースのテストケース汎化に関する研究領域に基づく。
特に以下の3つのアイデアを核としている：

1. 「シナリオカバレッジ」を「コードカバレッジ」と区別する考え方
2. プロンプト自動チューニングによるVP識別ルールの最適化
3. Masked Oracle Modeling（MOM）による理解度試験

関連領域として以下がある：

- コードカバレッジ駆動のテスト生成（記号実行・探索ベーステスト・EvoSuite等）
- LLMベースのテスト生成（ChatTester、IntUT等）
- プロパティベーステスト（Hypothesis等）
- パラメータ化単体テスト（PROZE等）

このスキルは、コードカバレッジ駆動とプロパティベースの中間に位置する
「初期テストを介して開発者意図を読み取り汎化する」アプローチである。
