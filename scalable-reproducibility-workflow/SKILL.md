# 大規模再現性ワークフロー: エージェント型AIによる実証研究の体系的再分析

実証研究のレプリケーションパッケージ（データ＋コード）を入力とし、
所定の診断テンプレートに基づいて推定値の再現・診断レポートの生成までを
自動化するマルチエージェントパイプラインの構築手法。

## このスキルを使うタイミング

- 数十〜数百本の実証論文を、同一の診断基準で体系的に再分析したい
- レプリケーションパッケージの取得・環境復元・実行・検証を自動化したい
- 異なるソフトウェア（Stata, R, Python）・ディレクトリ構造・命名規則の
  レプリケーション資材を統一的に処理する仕組みが必要
- 因果推論手法（IV, DID, 交互作用モデル等）の大規模メタ検証を行いたい
- ジャーナルや研究機関の再現性チェック体制を効率化したい

## 前提知識

### なぜ「科学的判断」と「計算実行」を分離するのか

大規模再現性の核心的な課題は、**異質性と決定性の両立**にある。
レプリケーション資材はソフトウェア・ディレクトリ構造・コーディング慣習が
論文ごとに大きく異なる。一方で再現性には決定性が必要で、同じパイプライン
バージョンと同じ入力に対して常に同一の数値結果を返さなければならない。

この緊張関係を解決する鍵が「分離」である。

- **診断テンプレート**（何を測り、どう評価するか）は人間の研究者が設計する。
  現状のAIシステムは、計量経済学・統計理論が要求する精度水準を満たす
  診断ツールの設計には不向き。
- **実行**（資材の取得・環境復元・コード修正・推定・レポート生成）は
  エージェントが自動化する。診断テンプレートが固定された後の作業は
  ほぼ手続き的であり、自動化の恩恵が大きい。

### 適応性と決定性を両立させる仕組み

新しいレプリケーションパッケージに遭遇すると未知の障害が発生する。
対処法をその場で場当たり的に適用すると、数値的な挙動が実行ごとに
変わるリスクがある。

解決策は、**バージョン管理された適応**。障害パターンを汎用ルールとして
コード化し、実行間（between runs）で更新する。実行中（within run）には
コードを変えない。これにより各バージョンの数値的挙動は固定されつつ、
バージョン間でカバレッジが拡大する。

## 全体フレームワーク: 3層アーキテクチャ

```
┌─────────────────────────────────────────────────┐
│  第1層: LLMオーケストレータ                        │
│  ・タスクの振り分け・エラー解釈・パイプライン制御    │
│  ・数値計算は絶対に行わない                        │
│  ・ログと中間成果物を検査し、次のアクションを決定    │
└────────────────────┬────────────────────────────┘
                     │ 参照↓  ↑ログ・成果物
┌────────────────────┴────────────────────────────┐
│  第2層: スキル記述 & ナレッジベース (SKILL.md群)     │
│  ・各エージェントの入出力契約（インタフェース仕様）   │
│  ・蓄積された障害パターンと解決ルール               │
│  ・バージョン管理される                            │
└────────────────────┬────────────────────────────┘
                     │ 実行指示↓  ↑結果
┌────────────────────┴────────────────────────────┐
│  第3層: 決定的エージェントコード & 診断スクリプト     │
│  ・R, Stata, Pythonによるファイル操作・統計計算      │
│  ・標準化された中間ファイル（JSON, CSV, ログ）で通信  │
│  ・エージェント間で隠れた状態を共有しない            │
└─────────────────────────────────────────────────┘
```

情報の流れは、指示は上→下、ログ・成果物は下→上。
適応は第2層（スキル記述）と第3層（コード）のバージョン間更新のみ。

## 7段階パイプラインの詳細

### Stage 1: メタデータ抽出 (Profiler)

**入力:** 論文PDF
**出力:** `study_info.json`（タイトル、著者、年、ジャーナル、データリポジトリURL）

やるべきこと:
- PDFをプレーンテキストに変換する（pdftotext等）
- タイトル・著者・出版年・ジャーナル名を構造化抽出する
- 「Data Availability Statement」等のセクションからリポジトリURLを探す
- URL検出は決定的なパーサ（正規表現等）を基本とし、
  フォーマットが非標準な場合のみLLMを補助的に使う

設計判断のポイント:
- キーワード検索によるデータセット探索は、類似タイトルの無関係な
  データセットを返すことが多い。**PDF内のURLを最優先**（PDF-first戦略）し、
  URL未記載時のみキーワード検索にフォールバックする。
  この切り替えだけで成功率が約63%→89%に改善した実績がある。

### Stage 2: レプリケーションパッケージ取得 (Librarian)

**入力:** `study_info.json`のリポジトリURL
**出力:** ローカルにバージョン管理されたレプリケーションパッケージ一式

やるべきこと:
- 対応プラットフォームごとにAPIを使い分ける
  - Dataverse → Dataverse API でファイルリスト取得→個別ダウンロード
  - GitHub → ZIPアーカイブとしてダウンロード
  - OSF → OSF API でプロジェクトファイル取得
  - 直接HTTP → 標準HTTPリクエスト
- 自動取得失敗時は手動供給のフォールバックを用意する

既知の障害パターン:
- Dataverse APIのURLに末尾スラッシュがあると404を返す→URL整形で対処
- 古い論文ではリポジトリが非公開化されている場合がある
  →アーカイブコピーの手動投入パスを設ける

### Stage 3: 仕様の特定 (Profiler 再呼出)

**入力:** ダウンロードされた .do, .R, .py スクリプト群
**出力:** `metadata.json`（最大3つの主要仕様の構造化表現）

やるべきこと:
- 言語固有の決定的パターンでIV推定コマンドを検出する
  - Stata: `ivreg2`, `ivregress 2sls`, `reghdfe ... (D = Z)`, `ivprobit`
  - R: `ivreg()`, `iv_robust()`, `feols()` のIV構文
  - Python: `IV2SLS()`
- 検出した各コマンドから、結果変数(Y)・内生変数(D)・操作変数(Z)・
  統制変数(X)・クラスタリング変数・固定効果・ソーススクリプトを
  構造化抽出する
- 複数仕様がある場合の選別手順:
  1. (Y, D, Z, X) の組み合わせで重複排除
  2. ヒューリスティックでランク付け（表参照の有無、メイン結果スクリプト内か、統制変数の充実度）
  3. 論文あたり最大3仕様を保持

設計判断のポイント:
- 初期段階でLLMに解釈を依頼する必要があったパターンも、繰り返し遭遇した
  時点で決定的パーサに移行する。LLM依存度を漸減させることで再現性が向上する。
- Stataの時系列演算子（`l.`, `l4.`, `F2.`, `D.`等）は変数名に埋め込まれた
  形で出現し、データセット上の実変数名へのマッピングが必要。
  3段階の解決を行う: 完全一致 → ドット除去 → アンダースコア区切り → 基底変数から再計算

### Stage 4: コード整備 (Janitor)

**入力:** 元のスクリプト群
**出力:** 整備済みスクリプト、`cleaning_log.json`

やるべきこと:
- **パス修正:** 絶対パスを正規表現で検出し、ワークスペース相対パスに置換する。
  Stataのグローバルマクロ（`$datadir`等）のインライン展開を含む。
- **グラフィックス抑制:** `graph export`, `pdf()`, `png()`, `plt.show()` 等を
  コメントアウトする。ただし `estimate_plot_data()` のような関数名の部分一致に
  注意し、完全な関数呼び出しパターンのみマッチさせる。
- **依存パッケージ処理:** CRAN非推奨パッケージ（rgdal, rgeos, maptools等）の
  `library()` 呼び出しをコメントアウトする。
- **Stata固有の修正:**
  - `#delimit ;` モードの追跡（セミコロンが文末記号になる）
  - `#delimit` の省略形（`#d`, `#delim`等）対応
  - 旧merge構文（pre-Stata 11）の自動変換
  - `capture drop X; gen X = expr` パターンの修正（バックアップ→生成→失敗時復元）
- **データ形式変換:** `.tab` ファイル（Dataverse TSV）の CSV/DTAへの変換

コード注入のルール:
- 分析データのエクスポートコマンドを挿入する際は、
  現在のデリミタモード（改行 or セミコロン）を検出して適合させる
- 複数行コマンドの途中に注入しない（コマンド終端まで前方スキャン）
- 行番号ベースではなくコンテンツベースのアンカーを使う
  （先行する編集で行番号がずれるため）

### Stage 5: コード実行 & データ抽出 (Runner)

**入力:** 整備済みスクリプト、`metadata.json`
**出力:** `analysis_data.csv`, `execution_log.txt`, クロス言語バリデーション結果

やるべきこと:
- `metadata.json` のソフトウェア種別に応じてインタプリタを選択
  （`stata -b do`, `Rscript`, `python3`）
- 推定コマンドにマーカーを挿入し、係数・標準誤差をログからプログラム的に抽出する
- 分析データセットをCSVとして書き出す
- **クロス言語バリデーション（Stata研究の場合）:**
  Stata IV コマンドを等価な R 仕様に翻訳し、同一データで再推定する。
  係数の一致判定基準: `max(0.01 × |β̂|, 10⁻⁶)` 以内

`e(sample)` の取り扱い:
- Stataの `if e(sample)` は直前の推定のサンプル制約を参照する。
  正しいサンプルを保持するには、条件付き推定を先に実行し、
  後続コマンドがサンプル指標を上書きする前にデータを書き出す必要がある。
- フルパネルをエクスポートし、推定サンプルフラグ列を付与して
  R側でラグ計算後にフィルタする方式が安定する。

### Stage 6: 診断分析 (Skeptic)

**入力:** `analysis_data.csv`, `metadata.json`
**出力:** `diagnostics.json`（全統計量 + 警告フラグ + 信頼性レーティング）

やるべきこと:
- 人間が設計した診断テンプレートをスタンドアロンのRスクリプトで実行する
- LLM呼び出しは一切行わない。全手続きは決定的かつバージョン管理される
- 診断テンプレートは研究デザインごとに異なるが、実行器は設計不問
  （テンプレートを入力として受け取る）

IV研究における診断項目の例:
- 操作変数の強度: 有効F統計量（Montiel Olea & Pflueger基準）、F < 10 で警告
- 頑健推論: Anderson-Rubin検定、ブートストラップ信頼区間、tF手続き
- 感度分析: ジャックナイフ（クラスタ単位の逐次除外）
- 2SLS–OLS比較: 同一仕様でのOLS推定と比較

信頼性レーティングの例:
| レーティング | 条件 |
|------------|------|
| High | 警告なし |
| Moderate | 警告1-2件 |
| Low | 警告3-4件 |
| Very Low | 警告5件以上 |

注意: レーティングは補助的なスクリーニング指標。個々の診断項目の
実質的な重要性は異なりうる（極端に弱い操作変数は複数の軽微な
警告より深刻）。

### Stage 7: レポート生成 (Journalist)

**入力:** `diagnostics.json`
**出力:** 標準化されたMarkdownレポート + 可視化

やるべきこと:
- 仕様ごとにセクションを構成する
- エグゼクティブサマリー表（仕様一覧 + レーティング）を冒頭に置く
- 各仕様について4種の標準チャートを自動生成する:
  係数比較プロット、第一段階F統計量、ブートストラップ信頼区間、ジャックナイフ感度
- フォーマットは全論文で同一にし、横断比較を容易にする

## 適応メカニズム: 4フェーズの解決サイクル

新しい障害に遭遇したときの対処手順:

### フェーズ1: 異常検出

- 実行ログの検査
- クロス言語バリデーションでの不一致
- 中間ファイルの内部整合性チェック

**重要:** 深刻な障害の多くは明示的なエラーメッセージを出さない。
例: Rのバッククォート問題（`_`始まりの列名でcoef()がNAを返す）は、
第一段階統計量は正常に計算されるが下流の推定値が欠損する形で顕在化する。
検出には**ステージ間のクロスフィールド整合性チェック**が不可欠。

### フェーズ2: 根本原因の診断

- コマンドの再実行ではなく、複数ステージ・複数言語をまたいで障害を追跡する
- 例: クロス言語での符号逆転（R: +2.15, Stata: −2.24）は、
  ラグ制御変数の欠落→変数名省略→不完全パネルエクスポート→
  `e(sample)` メモリとの相互作用という7層にわたる原因連鎖だった

### フェーズ3: 汎用的な修正の実装

修正は特定の論文へのパッチではなく、汎用ルールとしてコード化する。

3つのパターン:
- **単一障害→汎用ルール:** `#delimit`の省略形認識漏れ → 全有効省略形をカバーする正規表現に拡張
- **反復障害→構造的再設計:** キーワード検索の誤取得 → PDF-first取得アーキテクチャへ移行
- **注入エラー→注入ロジック改善:** デリミタモード検出、複数行コマンド検出、コンテンツベースアンカーの導入

### フェーズ4: 知識の記録

各解決を以下の形式でナレッジベースに追記する:

```
[日付] [障害の短い見出し]
Context: どのような状況で発生するか
Problem: 何が起こるか
Fix: どう修正したか
Impact: 他の論文への汎用性
```

## チェックリスト

### パイプライン構築時

- [ ] 診断テンプレートが研究者によって事前に設計・固定されているか
- [ ] 数値計算（推定・診断）がすべて決定的コードで実行されているか（LLM非介入）
- [ ] 全エージェントがディスクベースの標準ファイル（JSON, CSV, ログ）のみで通信しているか
- [ ] 各ステージが独立して再実行可能か（障害ステージから再開できるか）
- [ ] パイプラインバージョンが明示され、同一バージョン＋同一入力で同一出力が保証されるか
- [ ] 適応（コード修正・ルール追加）が実行間でのみ行われ、実行中に変更されないか

### 各実行サイクルで

- [ ] 全修正がcleaning_log等の監査証跡に記録されているか
- [ ] クロス言語バリデーションが実施されているか（Stata→R等）
- [ ] 中間成果物のクロスフィールド整合性がチェックされているか
- [ ] レポートフォーマットが全論文で統一されているか

### 新しい研究デザインへの拡張時

- [ ] 実行器ではなく診断テンプレートだけを変更しているか
- [ ] ベンチマーク推定量（対象デザインの中核的な推定値）が明確に定義されているか
- [ ] 含有基準が文書化されているか

## 制限事項と注意点

### この手法が機能する条件

- レプリケーション資材（データ + コード）が公開されていること
- 対象の研究デザインに対して、標準化された診断テンプレートが定義できること
- 分析の透明性に関する規範が分野に確立していること

### この手法が対処できないこと

- 識別戦略の妥当性の判断（操作変数の不偏性・排除制約は検定不能な仮定）
- 資材が不完全・欠落・根本的に欠陥のある場合の結果回復
- ブートストラップ・ジャックナイフ等で乱数シードの可搬性がプラットフォーム間で
  保証されない場合の完全な数値一致
- 研究デザイン自体の信頼性評価（それは研究者の実質的判断に属する）

### 見かけの成功率に関する注意

条件付き成功率（データ＋コードがアクセス可能な場合）と
無条件成功率（全論文対象）を区別して報告する。
資材の入手可能性が最大のボトルネックになることが多い。

## 発展的応用

### 他の研究デザインへの展開

パイプラインの実行器は設計不問。診断テンプレートを差し替えることで
以下に展開可能:
- パネルデータの二元固定効果（TWFE）モデル: ベンチマーク推定量はTWFE係数、
  診断目標は異質な処置効果への頑健性評価
- 交互作用モデルによる異質処置効果推定: ベンチマーク推定量は条件付き限界効果
- 回帰不連続デザイン（RDD）: バンド幅選択とローカル多項式推定の診断

### 診断から完全再現へ

- 個別仕様の再現から、表・図の完全再構築と内部整合性検証へ拡張可能
- 例: 2つの表が同一サンプルと記載しながら観測数が異なる場合の検出
- クラスタジャックナイフ、レバレッジ、Cook距離、代替ウィンソライズ閾値、
  置換推論の標準化・並列化も実行コストが大幅に低下する

### 研究インフラとしての統合

- 著者がレプリケーション資材を機械可読な標準構造で準備する支援ツールに
- ジャーナルの投稿時に依存関係の欠落・パス未解決・文書不備を自動検出
- 第三者検証チームによる標準化された診断出力の活用

## 10種の障害クラスと対処パターン集

実際の92論文から遭遇・解決した障害を類型化したもの。
新しいパイプラインを構築する際、事前に対応を組み込むべきパターン。

| クラス | ステージ | 代表的パターン |
|-------|---------|-------------|
| パス・環境 | Janitor, Runner | 絶対パス、グローバルマクロ、サブファイル不一致 |
| ソフトウェア・言語 | Profiler, Runner, Skeptic | 多言語コードベース、演算子翻訳 |
| データ形式・エンコーディング | Janitor, Runner, Skeptic | .tab形式の曖昧性、ファクタエンコーディング |
| 変数名不一致 | Skeptic, Profiler | タイポ、プレフィックス一致、未展開マクロ |
| Stata構文方言 | Janitor | #delimitモード、旧merge構文、e(sample)処理 |
| モデル仕様構造 | Skeptic, Profiler | パネル固定効果、サブセット条件、バンド幅ルール |
| 実行時リソース制約 | Skeptic | メモリ上限、ジャックナイフタイムアウト |
| グラフィックス・対話コマンド | Janitor | グラフィックスデバイス、出力テーブルパッケージ |
| データ取得 | Librarian | 非推奨リンク、誤ダウンロード |
| コード注入ロジック | Janitor | デリミタモード、行番号ドリフト |

変数名不一致の解決には4段階の照合が有効:
完全一致 → 大小文字無視 → レーベンシュタイン距離≤2 → プレフィックス一致

大規模データセットのジャックナイフでメモリ不足になる場合:
観測数10万超ではサンプリングキャップ（固定シード）を設け、
クラスタ数過多ではクラスタレベルから観測レベル（200件）へフォールバック。
