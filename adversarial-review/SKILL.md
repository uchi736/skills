# 敵対的レビューによる技術文書の品質向上

生成モデルが作った技術文書を、独立した複数のレビュアーモデルが「批判」し、
意見が割れた箇所を第三のモデルが裁定することで品質を上げる手法。
ただしこの手法には明確な適用境界があり、**使う前にタスクタイプを見極めること**が
成否を分ける。

---

## このスキルを使うタイミング

- 技術文書の初期生成物が「盛りすぎ（過剰設計・不要コンポーネント・流行り技術の濫用）」に
  なりがちで、それを削って引き締めたいとき
- セキュリティの盲点や障害シナリオを、設計時点で潰しておきたいとき
- 単一モデルの自己レビューでは盲点を見落とす（生成者とレビュアーが同じ弱点を共有する）
  問題を回避したいとき

**ただし最初に必ず「適用判断」セクションでタスクタイプを判別すること。**
網羅性が成功の鍵となるタスク（要件定義など）では、この手法は逆効果になる。

---

## 前提知識：なぜ敵対的レビューが「削る」方向に働くのか

このスキルの核心は、レビュアーへの指示の「フレーミング」が出力の方向性を決めるという点にある。

- レビュアーに「改善せよ」と指示すると、機能を**足す**方向に動きやすい
- レビュアーに「挑め・粗を探せ」と指示すると、何を**削れるか・簡素化できるか**を
  自然に見つけ出す

つまり敵対的レビューは本質的に「精度（precision）を上げる」装置である。
悪い内容・余計な内容を取り除くことには強いが、
**必要な内容を網羅する（recall）方向には働かない**。むしろ網羅性を削り落とす。

この精度／再現率のトレードオフが、後述するタスクタイプ依存性のすべての根源になっている。
この一点を理解していれば、適用判断の大半は自分で導ける。

もう一つの設計原理は「自己審判の回避」である。生成モデルと同じモデルにレビューさせると、
同じ盲点を共有してしまう。独立した（できれば訓練分布の異なる）モデルにレビューさせ、
意見対立は当事者以外のモデルに裁定させることで、この問題を構造的に防ぐ。

---

## 適用判断：タスクタイプの見極め（最重要）

スキルを実行する前に、対象タスクを次の3類型のどれかに分類する。
これが品質を上げるか下げるかを左右する、最も重要な判断である。

### 判断フロー

```
対象タスクの初期生成物を想像する
        │
        ▼
  そのタスク自体が「批判・評価・査読」か？
        │
   ├─ Yes ─→ 【Neutral型】 敵対的レビューは冗長。効果ほぼゼロ。適用しない。
        │
   └─ No
        │
        ▼
  初期生成物は「盛りすぎ」か「足りない」か？
        │
   ├─ 盛りすぎる傾向（過剰設計・不要要素が混入しやすい）
        │      └─→ 【De-fatting型】 敵対的レビューが有効。適用する。
        │
   └─ 不足しがち（網羅性・抜け漏れ防止が成功の鍵）
              └─→ 【Completeness型】 敵対的レビューは有害。原則適用しない。
                   （どうしても使うなら後述の「網羅性モード」に切り替える）
```

### 各類型の特徴と期待される効果

| 類型 | 特徴 | 代表タスク | 敵対的レビューの効果 |
|------|------|-----------|-------------------|
| De-fatting（引き締め） | 初期出力が過剰生産になりやすい | アーキテクチャ設計／コード生成／セキュリティ監査 | 強い改善（経験則として +約20%） |
| Neutral（中立） | レビュー・評価がタスクそのもの | 提案書レビュー | ほぼゼロ（冗長） |
| Completeness（網羅） | 抜け漏れが最大のリスク | 要件定義・要求分析 | 悪化（経験則として -約7〜8%） |

### 判別の問いかけ

迷ったら次を自問する。

- 「このタスクで失敗するとき、原因は"盛りすぎ"か"抜け漏れ"か？」
  - 盛りすぎが主因 → De-fatting → 適用する
  - 抜け漏れが主因 → Completeness → 適用しない
- 「このタスク自体に批判・査定の性質が含まれているか？」
  - 含まれる → Neutral → 適用しても無駄

**De-fatting型での内訳の傾向（参考）：** セキュリティ監査での改善が最も大きく、
次いでコード生成、アーキテクチャ設計の順で効果が出やすい。
特にセキュリティ監査では、境界・障害視点のレビュアーが単一モデルの見落とした
セキュリティギャップを補い、複数の評価軸で同時に改善する傾向がある。

## 全体フレームワーク

採用する場合のパイプラインは「生成 → 並列レビュー → 三角審判 → 反復」の4フェーズ。

```
ユーザープロンプト
        │
        ▼
   ┌─────────────┐
   │ 生成モデル   │  初期文書を生成
   └─────────────┘
        │
        ├──────────────┬──────────────┐
        ▼              ▼              │
 ┌────────────┐  ┌────────────┐      │
 │ レビュアーA │  │ レビュアーB │      │
 │（工学視点） │  │（境界視点） │      │
 └────────────┘  └────────────┘      │
        │              │              │
        └──────┬───────┘              │
               ▼                      │
        生成モデルが各提案を          │
        採用 / 却下                   │
               │                      │
        却下された提案 ──→ ┌──────────┐│
                          │ 三角審判  ││
                          │（当事者外）││
                          └──────────┘│
               │                      │
               ▼                      ▼
        確定した変更指示 ──→ ┌──────────┐
                            │ 反復改善  │ → 最終出力
                            │（既定2周）│
                            └──────────┘
```

### モデルの役割（モデル非依存）

特定の製品名に依存せず、次の4つの「役割」を、できれば訓練分布の異なる
複数のモデルに割り当てる。同系統のモデルだけで構成すると盲点を共有しやすい。

- **生成役**：初期文書を作り、フィードバックを受けて改稿する。最終的な工学判断の主体。
- **レビュアーA（工学ロバスト性視点）**：設計判断に挑み、過剰設計を指摘する。
  追加だけでなく**削除・簡素化**も提案する。
- **レビュアーB（境界・破壊視点）**：システムがクラッシュする／データを失う／
  セキュリティが破られるシナリオを能動的に探す。
- **審判役**：意見対立を裁定する。固定の専任ではなく、対立ごとに「当事者でない側」が務める
  （次節参照）。

---

## 各フェーズの詳細

### フェーズ1：生成

生成役モデルに、構造化された要件プロンプトから初期文書を作らせる。
この時点では通常の単一モデル生成と同じ。

### フェーズ2：並列レビュー

両レビュアーに同じ初期文書を渡し、**並列に**レビューさせる。

**入力の扱い：** レビュー効率のため、長大な文書は冒頭の一定量
（原典では約3,000文字相当）に切り詰めてレビュアーに渡してよい。
全文を毎回渡す必要はない。

**出力フォーマット：** 各レビュアーには、散文ではなく構造化された提案リストを
出力させる。各提案は次のフィールドを持つJSON配列とする。

```json
[
  {
    "id": "A1",
    "severity": "critical | major | minor",
    "suggestion": "具体的で実行可能な改善内容",
    "reasoning": "この変更がないと現状の設計がなぜ破綻するか"
  }
]
```

`reasoning` を「なぜ現状だと失敗するか」の形で書かせるのが要点。
単なる感想ではなく、失敗シナリオに紐づいた指摘を引き出す。

**レビュアープロンプトの設計原則（逐語コピーではなく構造を踏襲する）：**

- レビュアーAには「設計判断に異議を唱える批判者」として振る舞わせる。
  追加提案だけでなく、**何を削れるか**を必ず1つ以上挙げさせる。
- レビュアーBには「この設計を壊すならどこか」を探す役割を与える。
  クラッシュ・データ損失・セキュリティ侵害につながる具体的シナリオを列挙させる。
- どちらも重大度（critical/major/minor）を自己申告させ、後段の優先順位付けに使う。

### フェーズ3：三角審判（自己審判の回避）

生成役が**却下した**提案だけが審判にかかる（採用された提案はそのまま実装へ）。

**最重要ルール：審判役は、その提案を出したレビュアー自身であってはならない。**
3者を循環させ、対立ごとに当事者でない第三者が裁く。

```
レビュアーAの却下提案  →  レビュアーBが裁定
レビュアーBの却下提案  →  生成役が裁定
生成役の却下提案        →  レビュアーAが裁定
```

この循環トポロジーにより、自分の提案を自分で裁く事態を防ぎ、
各対立を必ず異なる視点のモデルに評価させる。
（多数決ではなく第三者裁定を使う理由がこれ。多数決は視点の独立性を保証しない。）

審判は次の3判定のいずれかを返す。

- **提案採用（suggestion_wins）**：生成役の反論を退け、レビュアーの提案を採る。
- **生成役支持（main_wins）**：生成役の却下判断を支持する。
- **折衷（compromise）**：どちらも当初提案しなかった中間案を作る
  （例：機能は残すがセキュリティ監査を追加する）。

**運用上の勘所（判定分布の傾向から）：**

- 実際には**生成役支持が最多（約6割）**になりやすい。
  → システム全体は「生成役の判断をデフォルトで尊重する」設計にする。
    レビュアーを権威にせず、安全網として位置づける。
- **折衷が約1/4**を占め、二者択一では出なかった良案が生まれる。
  → 審判には「勝ち負け」だけでなく折衷案を積極的に作らせる。
- **提案採用は少数（約15%）だが価値が高い**。
  → これらは多くがセキュリティや過剰設計に関する致命的な指摘。
    数は少なくてもここを取りこぼさないことが手法の主たる効用。

**注意：単一レビュアーの自動採用は避ける。** レビュアー1体の提案を
無審判で機械的に採用する構成は、改善幅が小さく（経験則として +数%程度に留まる）、
誤った指摘もそのまま通してしまう。**対立は必ず審判を通す**こと。
2体レビュアー＋審判の構成の方が、単一レビュアー自動採用より明確に効果が大きい。

### フェーズ4：反復改善

既定で2周。各周で生成役に次を渡す。

1. **採用された提案**（必ず実装する）
2. **裁定済みの対立**（判定どおりに実行する）
3. **過去に却下された提案の記憶**（同じ対立の蒸し返しを防ぐ）

3番目の「却下記憶」が、周回をまたいだ堂々巡りを防ぐ鍵。
生成役は、強制された変更を反映しつつ、対立のない部分では自らの工学判断を保つ。

## Completeness型タスクへの対処（網羅性モード）

要件定義のように網羅性が命のタスクでどうしても多モデルレビューを使いたい場合、
標準の敵対的フレーミングのままでは内容が縮小する
（周回ごとに文書長が縮み、網羅性スコアが最も大きく落ちる）。

**緩和策：レビュアーAのフレーミングを反転させる。**
「既存要素に異議を唱える」のをやめ、「**欠けている要件を指摘する**」役割に切り替える。
削る指摘ではなく、抜け漏れの指摘をさせる。

**ただし正直な限界：** このプロンプト適応は劣化を**部分的にしか**緩和しない。
反転させても単一モデル単独に及ばないことがある。
→ 結論として、網羅性が成功の鍵となるタスクでは、敵対的レビューは
  原則として使わないのが安全。使うなら「削る」モードと「足す」モードは
  別物だと割り切り、フレーミングを根本から変えること。

## チェックリスト

**適用前：**
- [ ] タスクを De-fatting / Neutral / Completeness に分類したか？
- [ ] Completeness型なら、適用を見送るか「網羅性モード」に切り替えたか？
- [ ] Neutral型なら、冗長なので適用しないと判断したか？

**構成：**
- [ ] 生成役・レビュアー2体・審判の役割を、できれば異なる訓練分布のモデルに割り当てたか？
- [ ] レビュアーAに「削除・簡素化」を、レビュアーBに「破壊・障害シナリオ」を担わせたか？
- [ ] 提案を構造化フォーマット（id/severity/suggestion/reasoning）で出力させているか？

**審判：**
- [ ] 却下された提案だけを審判にかけているか？
- [ ] 審判役が当該提案の発案者と別モデルになる循環を組んだか？
- [ ] 単一レビュアーの無審判自動採用になっていないか？
- [ ] 折衷判定を許容し、積極的に中間案を作らせているか？

**反復：**
- [ ] 既定2周で、採用提案・裁定結果・却下記憶を毎周渡しているか？

## 制限事項と注意点

- **タスク多様性の限界**：効果の検証は少数のタスク類型に基づく。
  自分の対象タスクが3類型のどれにも素直に当てはまらない場合は、
  小規模に試してから本適用すること。
- **評価の循環バイアス**：改善幅をLLM自身に採点させると、構造化・改稿された出力を
  好む傾向があり、効果を過大評価しうる。可能なら採点モデルを2種以上使い、
  方向性が一致するかで割り引いて解釈する。実効果は採点者間で幅が出る前提で見る。
- **コスト**：多モデル＋反復構成は、単一モデルに対して**数倍（経験則として約7倍）**の
  実行コストになる。品質改善はトークン量だけの関数ではない（質あたりコストでも上昇する）が、
  全タスクに一律適用するのは非効率。
- **サンプルの揺らぎ**：1回の実行結果には確率的なばらつきがある。
  重要な判断に使うなら複数回実行して安定性を確認する。

## 発展的応用

- **タスクタイプの自動判別**：対象タスクが De-fatting か Completeness かを
  自動推定し、レビュアーのフレーミング（削る／足す）を切り替える仕組みにする。
- **選択的レビュー（コスト最適化）**：初期生成物の品質をまず簡易評価し、
  一定の閾値を下回ったときだけ敵対的レビューを起動する。全件レビューを避けてコストを抑える。
- **人手評価との突き合わせ**：LLMによる採点を、専門家の評価と照合して妥当性を確認する。
- **モデル規模によるスケール検証**：より大規模なモデルでもレビューの効用が残るか、
  あるいは生成役が賢くなるほどレビューの限界効用が下がるかを検証する。
- **多周回の収束性**：反復回数を増やしたとき、品質が収束するのか、
  それとも網羅性タスクのように単調に劣化するのかを調べる。

## 参考情報

本スキルは、多モデルによる敵対的レビューと三角審判機構を扱った技術文書生成の研究
（triangular adversarial review、2026年公開のarXiv論文）の知見に基づく。
原典は、生成モデル＋2レビュアー＋第三者審判の構成を5種の技術文書タスクで評価し、
「過剰生産タスクでは有効・網羅性タスクでは有害」という適用境界を実証的に示した。

スキル化にあたり、特定のモデル製品名・プロンプト文面・図表・統計表は再現せず、
手法のワークフロー構造、設計判断の根拠、適用境界の知見のみを抽出して
実行可能な形に再構成している。数値は厳密な実測値ではなく「経験則として期待される傾向」
として参照すること。

関連する研究領域：マルチエージェントLLMシステム、LLM同士のディベート・相互批判、
自己改善（self-refine / reflexion 系）、自己無撞着性（self-consistency）。
これらと本手法の差分は、推論精度ではなく**技術文書の工学的品質**を対象とし、
自己審判を構造的に防ぐ正式な対立解決プロトコルを持つ点にある。
