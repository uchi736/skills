# 階層認識チャンキング：産業文書RAGのための構造保存型チャンク設計

長く複雑な産業文書を対象とする RAG において、従来のテキストベースのチャンキング
（固定長分割、埋め込み類似度ベースの意味分割、LLM によるトピック分割）は、
視覚的レイアウトとセクションの親子関係を保持できず、文脈の断絶と検索精度の
低下を招く。このスキルは、視覚レイアウト検出 → 構造再構築 → 階層を反映した
チャンク生成、という 4 段階パイプラインの設計原則・判断基準をまとめたもの。

## このスキルを使うタイミング

以下のいずれかに当てはまる場合に参照する：

- 長い PDF やスキャン文書を RAG で扱い、検索精度や回答品質が頭打ちになっている
- 技術文書・契約書・財務報告書・試験仕様書など、階層的セクション構造を持つ
  文書が対象
- 表・図・本文が入り混じる複雑なレイアウトを含む文書を処理する必要がある
- 既存のチャンキング（固定長・意味分割・LumberChunker・Perplexity chunking 等）
  で検索精度が物足りない
- GraphRAG の前段として、文書から階層構造グラフを抽出したい
- クライアント向け RAG PoC の評価設計・ベンチマーク設計を行う

## 前提となる核心的知見

この領域で押さえるべき判断の核は以下の 4 点。

**1. テキストのみのチャンキングは産業文書で破綻する**

固定長分割や意味的類似度分割は、セクション「1.2」と「1.2.1」のような親子関係を
保持できない。表や図がページをまたぐとさらに悪化する。LLM ベースのチャンキング
（LumberChunker、Perplexity chunking 等）は、トピックシフトは検出できても
「どの階層の下にあるコンテンツか」は復元できない。構造認識チャンキングの
価値はここにある。

**2. 視覚レイアウト検出だけでも不十分**

物体検出ベースの文書パーサー（DETR・DiT・VGT 等）は、タイトル・ヘッダー・
表・図を矩形として抽出できるが、「Section 1.2 は Section 1 の子である」
という論理的階層は復元しない。視覚情報と階層情報は別の再構築ステップが必要。

**3. フォントや書式に依存する階層推定はスキャンで失敗する**

フォントサイズや字体から階層を推定する手法は、スキャン文書や OCR 結果では
テキストレイヤーが失われているため機能しない。言語モデルでヘッダーリストから
親子関係を推論する方が、文書種類を問わず頑健。

**4. 親ヘッダー文脈をチャンクに重複させるのが効く**

DFS で木を辿りながら親の見出しテキストを子チャンクに繰り返し含める設計は、
インデックスサイズが増える代償を払ってでも、検索時の文脈適合度を改善する。
これはこのスキルの最も重要な設計判断。

## 全体フレームワーク（4 段階パイプライン）

```
長尺産業文書
    │
    ▼
[1] 視覚レイアウト検出 (Document Parsing)
    │   ページごとにタイトル・ヘッダー・テキストブロック・表・図を検出
    │   → セグメント ID・タイプ・バウンディングボックス座標
    ▼
[2] OCR（テキスト抽出）
    │   各バウンディングボックス内のテキストを抽出して紐付け
    │   → 注釈付きレイアウト（Annotated Layout）
    ▼
[3] 階層ツリー再構築（DSHP: Document Section Hierarchical Parsing）
    │   (3a) ヘッダーリストから親子関係を LLM で推論（Header Tree）
    │   (3b) 一般ノード（表・図・本文）を空間順にヘッダーへ紐付け
    │   → 文書階層ツリー（Document Hierarchical Tree）
    ▼
[4] DFS ベースのチャンク構築
    │   木を深さ優先で走査、親文脈を子に重複させながら集約
    │   max_len を超えたら分割
    │   → Markdown ヘッダー付き階層チャンク
    ▼
RAG 検索・QA 用コーパス
```

## 各フェーズの詳細

### フェーズ 1：視覚レイアウト検出

**目的**：ページごとに「どこに何があるか」を矩形とタイプで特定する。

**モデル選択の指針**：
- DETR・DiT・VGT いずれも実用的。DocLayNet 等でファインチューニング済みの
  物体検出モデルを使う
- 後段のチャンキング設計が頑健であれば、DP 精度の多少の差は吸収される
  傾向がある

**出力の必須フィールド**：
- `page_number`
- `segment_id`
- `segment_type`（title / section_header / text / table / figure 等）
- `bounding_box`（座標と幅・高さ）

**判断基準**：
- 表や図をどれだけ精度よく検出できるかが下流の質を左右する
- ページ境界を跨ぐセクションへの頑健性を代表文書で目視確認する

### フェーズ 2：OCR

**目的**：各矩形内のテキストを抽出してレイアウトに紐付ける。

**モデル選択の経験則**：
- EasyOCR：産業文書で比較的安定した精度を出す傾向
- Tesseract：多言語対応とコストのバランス
- TrOCR：手書きや特殊フォントが多い場合の候補
- 日本語文書を扱う場合、これらとは別に日本語対応の OCR（PaddleOCR 等）の
  選定が必要。論文のベンチマークは英語・中国語・韓国語が中心である点に注意

**判断基準**：
- 対象文書の言語・フォント・スキャン品質に応じて選定
- 図表内のテキストも抽出対象に含めるか事前に決める
- OCR 精度は後段の階層推論精度に直接響くため、劣化が大きい場合は
  サンプルでプリプロセス（傾き補正・ノイズ除去）を検討する

### フェーズ 3：階層ツリー再構築（最重要ステップ）

**目的**：ヘッダーリストから親子関係を LLM で推論し、一般ノードを空間順に
ぶら下げて完全な文書ツリーを組み立てる。

#### サブステップ 3a：Header Tree の構築

LLM に「セクションヘッダーのリスト」を渡し、各ヘッダーに一意 ID・親 ID・
Root フラグを付与した JSON を返させる。

**プロンプト設計に含めるべき構造要素**（逐語コピーではなく、自分で書き直す）：

1. **役割定義**：文書のセクション階層を解析する専門家という設定
2. **入力仕様**：ヘッダー候補のリスト（各要素に ID・テキスト・ページ番号・
   座標を持たせた JSON 配列）
3. **推論ガイド**：
   - 番号付きの場合、「3.1」は「3」の子、「3.1.1」は「3.1」の子という
     標準ルールに従う
   - 番号がなくても、文脈・命名パターン・インデントから階層を推定
   - トップレベル（Title 直下など）は `parent = null` または Title の ID
4. **出力仕様**：`[{"id": "...", "parent": "..."}]` の厳密 JSON のみを返す。
   説明文・コードフェンスを付けない
5. **例示**：最低 2 パターン（番号あり・番号なし）を含める。
   番号なしのケースを含めないと精度が落ちる傾向

**モデル選択とファインチューニングの判断**：

- 汎用 LLM（GPT-4 等）を素で使うと、多様なレイアウトの文書では精度が伸び悩む
  傾向がある
- 階層ラベル付きデータ（DocHieNet や HRDH が代表例）で instruction-tuning
  すると、TEDS スコアで大幅な改善が期待できる
- 小型 LLM（3B〜8B クラス）+ LoRA/QLoRA で、汎用 LLM より高精度になる例が
  報告されている
- 一般に、モデルサイズよりタスク特化の訓練の方が効きやすい

**コスト制約別の推奨構成**：

| 状況 | 推奨アプローチ |
|------|--------------|
| PoC・少量検証 | 汎用 LLM を zero-shot、プロンプトを磨き込む |
| 中規模運用 | 汎用 LLM + few-shot（代表ケース 5〜10 件を文脈に） |
| 本番運用 | 小型 LLM を階層ラベル付きデータで fine-tuning（LoRA 併用） |

#### サブステップ 3b：一般ノードの紐付け

フェーズ 1 で得た全セグメントリストを、ページ番号とバウンディングボックス座標で
ソートしておく。ヘッダーツリーを走査しつつ、次のヘッダーに到達する前に出現する
テキスト・表・図を、直前のヘッダーノードの子として付加する。

これにより「Section 1.1 の下にある表」「Section 2 の冒頭テキスト」といった
空間的・意味的関係を両方保持したツリーが完成する。

### フェーズ 4：DFS ベースのチャンク構築

**目的**：完成した文書ツリーを深さ優先で走査し、親文脈を保持したチャンク群を
生成する。

**アルゴリズムの骨子**（疑似コード）：

```python
def dfs_chunking(node, inherited_context, chunks, max_len):
    # 継承文脈に現在ノードのテキストを追加
    current = inherited_context + node.text
    
    # 長さチェック
    if length(current) > max_len:
        # max_len 単位で分割して chunks に追加
        for piece in split_by_length(current, max_len):
            chunks.append(piece)
    else:
        chunks.append(current)
    
    # 子ノードに、自分まで含んだ文脈を伝播
    for child in node.children:
        dfs_chunking(child, current, chunks, max_len)

# 仮想ルート FAKE_ROOT から開始
dfs_chunking(root, "", chunks=[], max_len=550)
```

**重要な設計判断**：

- **Markdown ヘッダーで階層を明示**：チャンク内のテキストに `#`, `##`, `###` を
  木の深さに対応させて埋め込む。これにより埋め込みモデルが階層情報を
  実質的に利用できるようになる。人間が目視デバッグする際にも読みやすい。
- **親文脈の重複を許容**：同じ親を持つ複数の子チャンクに、親見出しテキストが
  重複して含まれる。インデックスサイズは増えるが、検索クエリが親の概念を
  含んでいるときに適合度が上がる。
- **max_len を超えたら途中で切る**：長大なセクション本文は、親ヘッダー情報を
  保持したまま分割される。

**チャンクの出力形式の例**：

```markdown
# Document Title
## Section 1: 背景
### Section 1.1: 従来手法の課題
Section 1.1 の本文テキスト...
```

**パラメータ設定の目安**：
- `max_len`：550 トークン（多くの埋め込みモデルの文脈長に収まる実用的な値）。
  使用する埋め込みモデル（BGE、E5 等）の最大トークン長から逆算する
- `top-k`（retrieval 時）：4 を開始点とする。文書の性質・質問の複雑さにより調整
- BM25 を併用する場合：`k1 = 1.2`, `b = 0.75` が妥当な初期値

## 評価の設計

チャンキングの善し悪しを判断するための指標と見方。

**検索（Retrieval）側の指標**：
- Recall@k：該当チャンクが top-k に含まれる率
- Precision@k：top-k 中の該当チャンク比率
- nDCG@k：順位を考慮した精度

**生成（QA）側の指標**：
- ANLS（Average Normalized Levenshtein Similarity）：短答の類似度
- ROUGE-L：長めの回答の語彙重複
- METEOR：意味類似度を加味した指標

**評価設計の指針**：
- 複数文書を跨ぐ「コーパスレベル」設定で評価する。単一文書内に閉じた評価は
  実運用条件を反映していない
- DP・OCR・埋め込みモデルを差し替えて、チャンキング設計が各変数に頑健かを
  アブレーション検証する
- ベースラインとして最低 4 つは比較する：固定長、意味分割、LLM ベース
  （LumberChunker 等）、構造ベース（階層推論なし）

**経験則としての期待値**：
- 単純な固定長チャンキングに対し、階層チャンキングは Precision で 5〜15% 改善
- QA 評価では ANLS で 2〜3% 改善
- 文書構造が複雑なほど効果が顕著に出る
- 同じ構造ベースでも、階層推論なし vs あり（DSHP 相当）で 5% 前後の差が出る

## 制限事項と注意点

**エラー伝播**：DP → OCR → 階層推論 → チャンク生成が直列なので、前段の誤りが
累積する。特に OCR 精度が低いと階層推論精度も連動して落ちる。将来的には
VLM ベースのエンドツーエンドモデルへの置き換えが有力な選択肢。

**視覚特徴の未活用**：この設計の LLM 階層推論は、テキストと粗い座標のみで
親子関係を推論する。フォントサイズ・色・インデント・罫線といった視覚手がかりを
取り込めていない。複雑なスキャン文書では、マルチモーダルなエンコーダや
VLM バックボーンでの拡張が有効と期待される。

**ストレージと計算コスト**：親文脈を重複させるため、従来チャンキングより
インデックスが大きくなる。チャンク総数が 2〜3 倍に増えるケースがある。
コスト制約が厳しい場合は、階層圧縮・重複除去・ノードキャッシュを検討する。

**日本語・多言語での検証不足**：元研究のベンチマークは英語・中国語・韓国語中心。
日本語文書での効果は同様に期待されるが、日本語 OCR と日本語対応 LLM の選定・
チューニングは別途必要。AIDB R&D 案件など日本語産業文書に適用する際は、
自前の代表サンプルでのアブレーションが必須。

**グラフ検索は未検証**：このパイプラインは親子関係・読み順の型付き辺を持つ
文書グラフを暗黙に生成しているが、GraphRAG として検索・推論する構成は
未検証（元論文でも将来課題として言及）。期待はあるが、効果は実証すべき。

## 発展的応用

**GraphRAG 化**：階層ツリーをそのままグラフとして永続化し、ノードとパスを
検索・推論対象にすると、マルチホップ質問や複数ページ跨ぎの根拠集約に
強くなる可能性がある。エッジに型（`parent_of`, `precedes`, `refers_to`）を
持たせる拡張が有効。

**段階的抽象化による階層要約**：階層ツリーの各レベルで要約を生成し、
親ノードに子ノードの要約を格納する設計にすると、粒度を選んで検索できる
RAG になる。「章レベルの概要 → 節レベルの詳細」という絞り込みが可能。

**エンドツーエンド VLM への置換**：DP・OCR・階層推論を VLM ベースの単一
モデルに置き換えることで、エラー伝播を抑え、モーダル間の一貫性を
高められる可能性がある。ただし制御性・解釈性とのトレードオフに注意。

**PoC 時の簡易版**：小規模プロトタイプなら、階層推論 LLM の fine-tuning を
省略し、GPT-4 や Claude の zero-shot で代用できる。精度は落ちるが、
設計原則の価値検証には十分。本番化の際に fine-tuning 版へ切り替える
段階的ロードマップを組める。

**ドメイン特化 fine-tuning**：業界固有のフォーマット（例：プラント運転マニュアル、
医薬品添付文書、規格書）では、そのドメインの階層アノテーション付きデータで
LLM を追加学習すると精度が伸びやすい。
