# LM-CC コード診断スキル

コードがLLMにとってどれだけ「迷子になりやすいか」を診断し、
具体的な改善案を提示するスキル。

## 背景知識

上海交通大学の研究（Xie et al., 2026, arXiv:2602.07882）により、
以下のことが実証されている：

- 循環的複雑度など従来の指標は、コード長を制御するとLLMの正答率との相関が消える
- LLMにとっての真の困難は**意味の非線形性**——ネストの深さと分岐の多さの組み合わせ
- この2軸を捉える新指標LM-CCは、全タスクで-0.92〜-0.97の強い偏相関を示した
- LM-CCを下げるリライトで、プログラム修復+20.9%、コード翻訳+10.2%の改善

**重要：** このスキルは論文のLM-CC計算（エントロピー計算にLLMが必要）を
そのまま再現するものではない。論文の知見を実用的な構造分析に落とし込んだ
近似的な診断ツールである。

---

## 診断の実行手順

### Step 1: コードの受け取り

ユーザーからコードを受け取る。以下のいずれかの形式：
- チャットに直接貼り付けられたコード
- ファイルパスの指定
- 「このプロジェクトの〇〇ファイル」といった参照

コードが長い場合（100行超）は、関数単位で分割して診断する。

### Step 2: 構造分析（5つの診断軸）

以下の5軸でコードを分析する。各軸は論文のLM-CCが捉える
「意味の非線形性」の構成要素に対応している。

#### 軸1: ネストの深さ（論文のcompositional level）

コードの入れ子構造の深さを分析する。

- **何を見るか：** if/for/while/try/withなどの制御構造のネスト段数
- **なぜ重要か：** 論文により、同じ分岐数でもフラット構造 vs 深いネストで
  LLMの処理困難度に劇的な差が出ることが示されている
- **危険水準の目安：**
  - 3段以下：LLMにとって問題なし
  - 4〜5段：注意が必要。可能なら浅くする
  - 6段以上：LLMが高確率で混乱する。リファクタリング強く推奨

#### 軸2: 分岐の密度（論文のbranching factor）

同一階層での分岐の多さを分析する。

- **何を見るか：** if-elif-elseチェーンの長さ、match/case文の分岐数、
  条件式内の論理演算子の数
- **なぜ重要か：** 分岐が多いほどLLMは「どのパスの話をしているか」を
  見失いやすくなる
- **危険水準の目安：**
  - elif 3個以下：問題なし
  - elif 4〜6個：やや注意
  - elif 7個以上、または複雑な条件式の連鎖：リファクタリング推奨

#### 軸3: 意味の詰め込み度

1行あたりの意味密度を分析する。

- **何を見るか：** 
  - 多重ネストしたリスト内包表記
  - 三項演算子の連鎖
  - 複数の代入や演算を1行に詰めた式
  - ラムダ式の入れ子
- **なぜ重要か：** 論文のFigure 1で示された通り、同じ循環的複雑度でも
  意味が詰め込まれたコードはLLMのエントロピー（予測の迷い）が
  跳ね上がる。LM-CCが1.3 vs 20.9と16倍差が出た主因
- **危険水準の目安：**
  - リスト内包表記のネストが2段以上
  - 1行に3つ以上の演算や代入がある
  - 三項演算子が入れ子になっている

#### 軸4: 変数スコープの距離

変数の定義位置と使用位置の距離を分析する。

- **何を見るか：** 
  - 関数冒頭で定義された変数が何十行も後で使われるケース
  - 外側のスコープの変数を深いネスト内で参照するケース
  - グローバル変数への依存
- **なぜ重要か：** LLMには「長い文脈の途中にある情報を見失いやすい」
  傾向がある（lost in the middle現象）。論文のAssumption 3.1
  （深さに依存するコンテキスト劣化）に対応
- **危険水準の目安：**
  - 定義と使用が20行以上離れている
  - 3段以上外側のスコープの変数を参照している

#### 軸5: ネスト×分岐の相互作用

軸1と軸2の掛け合わせを評価する。

- **何を見るか：** 深いネストの中に多数の分岐がある構造
- **なぜ重要か：** 論文のLM-CCの定義式そのものが、ネストの深さと分岐の多さの
  加重和である。この2つが同時に高いコードがLLMにとって最も困難
- **危険水準の目安：**
  - ネスト3段以上 × 分岐3つ以上 が同時に存在する箇所

### Step 3: 診断レポートの出力

簡潔でカジュアルなトーンで出力する。長々と書かない。
問題がないコードには「問題なし、このままでOK」と端的に伝える。

出力フォーマット：

```
## 🔍 LLM向け診断: [スコアのアイコンと一言]

[1〜2文で総評]

[問題がある場合のみ]
### ここが引っかかります
- **L[行番号]** [何が問題か一言] → [どう直すか一言]
- **L[行番号]** [何が問題か一言] → [どう直すか一言]

### リライト案
[改善後のコードを提示。変更箇所にコメントを添える]
```

**スコアの目安（内部判定用、ユーザーには自然な言葉で伝える）：**

- ✅ このままでOK — 全軸で問題なし
- ⚠️ ちょっと注意 — 1〜2箇所でLLMが躓くかも
- 🔴 リライト推奨 — 複数箇所でLLMが混乱しそう

3段階でシンプルに。中間の細かいグラデーションは不要。
ユーザーにとって大事なのは「直すべきか否か」の判断。

### Step 4: 改善提案の詳細

問題箇所ごとに、以下のパターンから適切なリライト案を提示する。

#### ネストが深い場合の改善パターン

**早期リターン（ガード節）への変換：**
```python
# Before: ネスト3段
def process(data):
    if data is not None:
        if data.is_valid():
            if data.has_items():
                return calculate(data)
    return None

# After: フラット化
def process(data):
    if data is None:
        return None
    if not data.is_valid():
        return None
    if not data.has_items():
        return None
    return calculate(data)
```

**関数抽出：**
深いネストの内側の処理を別関数に切り出す。

#### 分岐が多い場合の改善パターン

**辞書ディスパッチへの変換：**
```python
# Before: 長いif-elifチェーン
if action == "create":
    handle_create()
elif action == "update":
    handle_update()
elif action == "delete":
    handle_delete()
# ...さらに続く

# After: 辞書マッピング
handlers = {
    "create": handle_create,
    "update": handle_update,
    "delete": handle_delete,
}
handler = handlers.get(action, handle_default)
handler()
```

#### 1行に詰め込みすぎの場合の改善パターン

**リスト内包表記の分解：**
```python
# Before: 多重ネスト内包表記
result = [f(x, y) for x in items if g(x) for y in x.children if h(y)]

# After: ステップ分解
valid_items = [x for x in items if g(x)]
result = []
for item in valid_items:
    valid_children = [y for y in item.children if h(y)]
    result.extend(f(item, y) for y in valid_children)
```

**複合式の分解：**
```python
# Before: 意味が詰まった1行
s = ((1 + y) * y // 2) * (x + 1) + ((1 + x) * x // 2) * (y + 1)

# After: 意味ごとに分割し名前をつける
triangle_y = (1 + y) * y // 2
triangle_x = (1 + x) * x // 2
s = triangle_y * (x + 1) + triangle_x * (y + 1)
```

#### 変数スコープが遠い場合の改善パターン

- 変数の定義を使用箇所の直前に移動する
- 長い関数は責務ごとに分割する
- 中間変数に意味のある名前をつけて、文脈を自己説明的にする

### Step 5: リライトの実行（ユーザーが希望した場合）

ユーザーが「直して」「リライトして」と言ったら：

1. 動作を変えずにリライトする（これが最優先）
2. 変更箇所に短いコメントで理由を添える
3. Before/Afterを並べて見せる
4. テストがある場合はテスト実行を促す。ない場合はその旨を伝える

## 対応言語

Python, JavaScript/TypeScript, Java, C/C++, Go, Rust など
主要な言語に対応する。言語固有のイディオム（Pythonのリスト内包表記、
Rustのmatch式など）も考慮して診断する。

## このスキルの限界

- 論文のLM-CC（エントロピー計算にLLMを使用）の厳密な再現ではなく、
  構造分析に基づく近似である
- LLMの処理困難度は使用モデルやタスクによっても変わる
- コードの意味的な複雑さ（アルゴリズムの難しさ等）は
  構造分析だけでは完全には捉えられない
- 非常に短いコード（10行以下）では診断の意味が薄い

## 参考情報

本スキルは以下の研究知見に基づいている：
- LLMの処理困難度はネストの深さ（compositional level）と分岐の多さ
  （branching factor）の組み合わせで決まるという知見
  （コード理解に関する上海交通大学の研究グループによる実証研究、2026年）
- LLMが長い文脈の途中の情報を見失う「lost in the middle」現象
  に関する先行研究
- トークンレベルのエントロピーがコードの構造的に重要な箇所と
  対応するという知見
