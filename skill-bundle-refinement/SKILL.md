# スキルバンドル改善: 失敗駆動リファインメント

既に存在するスキルを、実際のタスク失敗から出発して段階的に改善する手順。
新規作成ではなく「既にあるスキルをどう直すか」に特化している。

## このスキルを使うタイミング

- 既存スキルの成功率が頭打ち、もしくは期待より低い
- スキルが肥大化してコスト・実行時間が重い
- スキル内のどの部分が効いていて、どこが冗長か判別できない
- 「とりあえず指示を足したが効果が見えない」状態になっている

## 前提知識（最も重要な発見）

既存スキルの改善には3種類の編集操作がある。
SkillMOO の実証研究では、3操作の効果に大きな差があった。

| 操作 | 内容 | 成功率向上 | コスト削減 |
|------|------|-----------|-----------|
| Pruning（削除） | 不要なスキル・記述を取り除く | 5/7 | 7/7 |
| Substitution（置換） | 誤った／ずれた記述を書き直す | 5/7 | 7/7 |
| Expansion（追加） | 新しい指示を書き足す | **0/5** | 5/5 |

**核心**: 「足りないから書き足す」は直感的だが、多くの場面で誤り。
既存スキルで成功率を上げたければ、まず削除と置換を疑う。
追加は最後の手段。

この非対称性の背景には、LLMの注意分散がある。
長い指示は短い指示より実行されにくく、
ノイズが混じった指示は正しい部分の効きを下げる。

## ワークフロー

### Step 1: ベースライン測定

改善に着手する前に、現状を数値で固定する。

記録すべき3指標：
- **成功率** (pass rate): 検証用タスクセットでの合格率
- **コスト** (cost): LLM推論コスト（USD/ドル単位）
- **実行時間** (runtime): タスクあたりの所要秒数

合わせて、失敗した個別タスクごとに：
- エラートレース（最終出力とスタックトレース）
- エージェントの中間思考（あれば）
- どのスキル節を参照していたかの痕跡

**注意**: 少なくとも10回は評価実行する。
1回の実行だけで判断すると確率的な揺れに騙される。

### Step 2: 失敗の分類

失敗トレースを読んで、以下に仕分ける。
各分類に対応する推奨操作も併記する。

| 失敗の根本原因 | 推奨される編集操作 |
|---------------|-------------------|
| スキル内の記述が誤り・時代遅れ・対象環境とずれている | Substitution |
| スキルが長大で、関連しない部分がエージェントを迷わせている | Pruning |
| スキル全体がタスクと無関係（適用ミス） | スキル差し替え（本スキルの範囲外） |
| モデル性能・ツール設定の問題 | スキル改善では解けない（先に環境を疑う） |
| 本当にスキルに載っていない情報が必要 | 最後にExpansion を検討 |

**判断のコツ**:
エージェントが間違った指示に従って失敗しているなら Substitution。
エージェントが散漫で指示に従えていないなら Pruning。
エージェントが「情報がないので推測した」と明示的に言っているときだけ Expansion。

### Step 3: 編集の優先順位

上記の分類に従い、以下の順で手を打つ。
順番を守るのが重要。

1. **まず Pruning** — 明らかに使われていない／今回のタスクと無関係な節を削る
2. **次に Substitution** — 誤った指示、曖昧な指示、対象環境とずれた指示を書き直す
3. **最後に Expansion** — 1,2で手が尽きた場合のみ、ピンポイントで追加

1回のイテレーションでは **1種類の操作のみ** を行う。
Pruning と Substitution を同時にやると、どちらが効いたか分からなくなる。

### Step 4: Pass-preservation guard（品質保全ガード）

編集後のスキルを測定し、以下の条件を満たさなければ **採用しない**。

- 成功率の低下が 0.05（5ポイント）以内
- 可能ならコストも同等以下

「少し悪くなったが後でリカバーする」は禁止。
バージョンを戻して別の編集を試す。

この guard がないと、イテレーションの途中で気づかないうちに品質が落ち、
最後に気づいた時には何が悪手だったか追跡できなくなる。

### Step 5: 反復と停止条件

Step 1〜4 を、予算（試行回数・時間）の範囲で反復する。

**停止条件の目安**:
- 連続2〜3回のイテレーションで成功率が上がらない
- 成功率が 0.95 以上に到達した（改善余地はコスト側へ移る）
- Pareto最前線（成功率とコストのトレードオフ境界）が動かなくなった

## 最終選択の優先順位

複数の改善候補が残ったときの選択基準（辞書順）:

1. **成功率** を最大化
2. 同率なら **コスト** を最小化
3. さらに同等なら **実行時間** を最小化

成功率を最優先にするのは、コストの削減は使われないスキルでは無意味だから。

## チェックリスト

改善イテレーションに入る前と後に確認する。

- [ ] ベースラインの成功率・コスト・実行時間を10回以上の実行で記録したか
- [ ] 失敗タスクのトレースを個別に保存し読んだか
- [ ] 「追加したい」と思う前に、削除・置換で解けないか検討したか
- [ ] 1回のイテレーションで1種類の操作に絞ったか
- [ ] 編集後に成功率が5ポイント以上落ちていないか確認したか
- [ ] 成功率が上がらないイテレーションが続いたら止めたか

## 制限事項と注意点

- **「Pruning優先」は既に肥大化したバンドルでの経験則**。
  最小構成の小さなスキル（~500トークン以下）では、削る余地がなく、
  Substitution かタスク自体の見直しが主戦場になる。
- **成功率が極端に低い（<0.2）タスクでは、スキルの外側をまず疑う**。
  モデルの適合性、ツール呼び出し設定、評価基準そのものの妥当性など、
  スキル改善では解けない問題が支配的なことが多い。
- **失敗トレースだけから改善点を特定するのは難しい場合がある**。
  エージェントが「なぜそう動いたか」を明示しないため、
  編集仮説が外れることは普通にある。採用／棄却を数値で判断する仕組み（guard）が機能する理由。
- **単一タスクでの改善は他タスクへ波及しない**ことが多い。
  汎用スキルなら複数タスクの加重平均で評価する。

## 発展的応用

### LLMを使った編集提案の自動化

人間がトレースを読んで編集案を考える代わりに、
もう一体のLLMエージェント（skill optimizer）に提案させる方法がある。

- 入力: 現在のスキル本文 + 失敗したタスクのトレース群
- 出力: 「どの節を削る／書き換える／追加する」という具体的な編集案
- 重要: 編集案そのものも品質ガードで検証してから採用する

これを数世代繰り返すと、人手では到達しにくい最適化が進む。

### 多目的最適化としての定式化

改善を「成功率を上げながらコストも下げる」多目的問題として扱うと、
単一の最良案ではなく **Pareto最前線**（トレードオフ曲線）が得られる。

本番の要件に応じて、
「成功率重視の重い版」と「コスト重視の軽い版」を用意できる。

## 参考情報

本スキルは以下の研究で報告された実証結果に基づく：

- SkillMOO: Multi-Objective Optimization of Agent Skills for Software Engineering (Gong et al., 2026, SBSE)
- SkillsBench ベースライン3タスク（Python build fix, Python→Scala変換, Spring Boot→Jakarta移行）で、
  成功率 +2.1%〜+131.2%、コスト -5.4%〜-31.7% の改善を報告
- Bundle pruning / substitution / expansion の3操作別の効果差が主要な知見であり、
  Expansion が 0/5 で成功率を上げなかった点は特に注目に値する

NSGA-II による探索アルゴリズム自体は本スキルでは採用していない（人手のイテレーションを想定）。
完全自動最適化を行う場合は原論文を参照すること。
