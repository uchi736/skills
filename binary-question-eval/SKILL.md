# 二値質問分解による文章評価と自己改善

「この文章は総合的に何点か」と一発で聞く代わりに、評価基準を
小さなYes/No質問の束に分解して独立に判定させ、Yesの割合を
スコアとして集計する。各判定に理由が付くため、スコアの根拠を
追跡でき、失敗の記録をプロンプト改善の入力に再利用できる。

## このスキルを使うタイミング

- LLM採点のスコアが高得点側に張り付き（天井効果）、まずまずの文章と明確に問題のある文章を判別できない
- スコアはあるが低評価の理由（事実誤認か、構成の乱れか、情報の欠落か）が分からず、改善につながらない
- 事実整合性・ハルシネーションのチェックを、主張単位で厳密に行いたい
- 評価器プロンプトや生成プロンプトを、失敗データに基づいて体系的に改善したい
- 人間が書いた原稿（委託原稿、蓄積コンテンツ等）の一次チェックを機械化したい

### 使わない・単独では使わないタイミング

- 全体の要旨を掴めているかのような、印象で決まる基準を単独で厳密化したい場合（過分解のリスク。制限事項を参照）
- 1つの致命的な誤りで全体を不合格にすべきタスクに、線形集計をそのまま適用する場合（拒否権付き質問などの集計の工夫が必要）

## 前提知識（なぜ有効か）

3つの機構が働く。

1. 判断の単純化。「事実整合性を1〜5点で採点せよ」より「すべての固有名詞が原文どおりか」の方が判定がぶれない。複雑なタスクを部分課題に分解すると精度が上がるという、プロンプト設計の一般知見の評価版。
2. 分散の低減。互いに相関の弱い判定をN個平均すると、個々の揺らぎが打ち消される。
3. 失敗モードの網羅。チェック観点を明示的に列挙することで、総合判断では埋もれる欠陥（綴りと句読点のような独立した失敗）を個別に拾う。

一発採点は表面的な自然さに引きずられ、正しい固有名詞が並んでいるだけで満点をつける。また満点か最低点かの両極に振れやすく、部分的な欠点と致命的な欠陥を区別できない。分解方式は満たした項目と落とした項目の比率で中間の評価を出せる。

評価対象の縛りはない。枠組みが規定するのは「入力と出力のペア（原文と要約、会話履歴と応答、指示文と完成文など）に質問を当てる」形だけで、出力の書き手は問われない。人間の執筆物にも同じ質問セットが適用できることが検証で確認されている。

## 全体フレームワーク

```
Phase A: 質問生成（タスク種別ごとに1回、使い回し可）
  タスク指示文 → 要件リスト → 評価軸ごとの二値質問セット
        ↓
Phase B: 評価と集計（対象1本ごと）
  入力＋出力＋質問セット → 各質問のYes/No＋理由 → 軸別・総合スコア
        ↓
Phase C: 質問セットの品質点検（Phase A直後と定期的に）
  Yes率の散らばり・質問間相関を診断 → 必要なら質問を再設計
        ↓
Phase D: 改善ループ（任意）
  失敗記録 → 教訓抽出 → 重複統合 → プロンプト書き換え → 再評価
```

最小構成はPhase A＋B。実行用のプロンプト全文は templates/prompts.md を参照。

## Phase A: 二値質問の生成

1. タスク指示文を評価用LLMに渡し、先に要件のリストへ要約させる。いきなり分解せず全体像を先に掴ませるのは、細分化時の取りこぼしを減らすため。
2. 各要件をYes/No質問に変換させる。ルールは3つ。「Yes＝要件充足」に向きを統一する。複数の確認事項を含む要件は質問を分ける。各質問に「No」に該当する具体的な違反例を1つ添えさせる（判定基準のぶれ防止）。
3. 質問を評価軸（一貫性、事実整合性、流暢さ、関連性など）に割り当てる。

質問設計の基準:
- 1問につき検証可能な性質1つだけを問う
- 「〜は高品質か」のような曖昧な問いを避け、具体的に問う
- 同じ軸の質問どうしが別々の失敗を拾うよう設計する（例: 綴りの質問と句読点の質問を独立させる）

質問数の目安は1軸あたり5〜8問。メタプロンプトはタスク非依存で、タスク指示文の差し替えだけで要約・対話・指示遵守に共通利用できる。

## Phase B: 評価と集計

1. 採点対象1本ごとに、各質問を独立に判定させる。判定（1/0）とあわせて理由を1文添えさせる。この理由がスコアの追跡可能性と、Phase Dの改善材料の源泉になる。
2. 集計する。軸別スコア＝その軸の質問のYes率、総合スコア＝全質問のYes率。既存の尺度と比較する場合は `score × (b − a) + a` でa〜b点に換算する。

判定時の原則（評価器プロンプトに明記する）:
- 省略と誤りを区別する。原文の情報を出力が省いただけなら減点しない。出力に書かれていて根拠がない、または矛盾する記述だけを違反とする（この混同は評価器の代表的な系統誤りで、明記しないと再発しやすい）
- 意味的に等価な変換（時刻表現の算術的な言い換え等）はハルシネーションとしない
- 文が再構成されている場合、主語と役割の対応（誰が何をしたか）を原文と突き合わせる

再現性の設定: temperature 0。揺らぎを抑えたい場合は2回実行して平均する。

## Phase C: 質問セットの品質点検

生成された質問セットが機能するかを、本運用の前に少数サンプルで診断する。

- Yes率の散らばり: 質問間でYes率がばらけているか確認する。全質問が同じような高いYes率に張り付く軸は、分解しても判別に寄与しない
- 質問間相関: 質問ペアの相関（φ係数）を測る。|φ| < 0.3程度の弱相関ペアが多い軸ほど、分散低減と網羅の効果が出る。高相関のペアばかりの軸は、質問が同じものを重複して見ているため作り直す

経験則: 事実整合性系の質問は本質的に相関しやすい（「事実誤りがないか」と「歪曲がないか」は連動する）が、それでも判断の単純化効果だけで一発採点より大きく改善する傾向がある。相関が高いからといって、この系統の分解を諦めない。

## Phase D: 改善ループ（任意）

評価器プロンプトまたは生成プロンプトを、質問単位の失敗記録から改善する。

### 自己改善（基準＝人間評価や検証関数）

1. 開発セットを評価し、基準との乖離が大きい事例を集める（正規化スコアの乖離が0.3を超える事例を対象とする目安）
2. 記録係のLLMに、失敗した質問と理由を文脈ごと分析させ、他のケースにも通用する一般化された教訓を抽出させる
3. 意味の重なる教訓をLLMで統合し、最大10件程度に絞る
4. 更新係のLLMに、現行プロンプト内の該当する一節を特定させ、教訓を織り込んだ文面へ置換させる（全体の書き直しではなく一節単位の置換）
5. 評価器を改善した場合は、更新後プロンプトから質問セットを再生成する。質問の再生成を伴う周は改善幅が大きい傾向がある

### 他モデル基準（クロスモデル）

強いモデルを基準に据え、質問単位の判定不一致だけを教訓抽出の材料にする。総合点の差と違い「どの基準の解釈がずれているか」を質問単位で特定できるため、省略と矛盾の混同のような概念レベルの系統誤りを直接あぶり出せる。モデルを別系統へ移行する際、プロンプトを新モデル向けに調整する用途にも使える。

### 停止基準と安全弁

- テストセットの性能が前の周より下がったら即停止する。改善の大半は最初の1〜2周で得られ、回しすぎると教訓どうしが競合して劣化する
- ループを回す前に、失敗を「指示不足」と「能力不足」に分類する。書式指定のように明確な指示で守れる失敗は改善が期待できる。カウント維持・比率維持のように生成中の正確な計算を要する失敗は、指示を足しても直らない（「内部でカウンターを維持せよ」の類いは診断として正しくても実行できない）。能力不足の失敗はループの対象から外す
- プロンプト長を毎周監視する。実行不能な指示が蓄積して数千文字規模に膨張すると、以前は守れていた正しい指示まで機能しなくなる（プロンプトの積載量には上限がある）

## チェックリスト

Phase A完了時:
- [ ] 全質問が「Yes＝充足」に統一されているか
- [ ] 複合的な要件が複数の質問に分割されているか
- [ ] 各質問に違反例が付いているか
- [ ] 各質問が評価軸に割り当てられているか

Phase B運用時:
- [ ] 各質問を独立に判定させているか（一括判定にしていないか）
- [ ] 全判定に理由が付いているか
- [ ] 省略と誤りの区別が評価器プロンプトに明記されているか
- [ ] temperature 0で実行しているか

Phase C:
- [ ] Yes率の散らばりを確認したか
- [ ] 質問間相関の高すぎる軸を特定し、再設計したか

Phase D:
- [ ] 失敗を指示不足と能力不足に分類したか
- [ ] 教訓を10件程度に絞ったか
- [ ] テスト性能低下で停止する仕組みがあるか
- [ ] プロンプト長を監視しているか

## 制限事項と注意点

- 質問セットの品質がスコアの上限を決める。大事な基準が質問に含まれていなければ、その欠陥は最後まで検出されない
- Yes率が品質に線形対応するという仮定を置いている。致命的な誤り1つで全否定すべきタスクでは、特定質問がNoなら総合スコアを floor に落とす等の集計の工夫を別途設計する
- 採点役のLLMの読解力に依存する。弱いモデルに載せ替えると相関は全体に低下する（それでも同一モデル内の比較では一発採点より優位になる傾向）。分解は設計として有効だが、モデルの地力を代替しない
- 印象型の基準の過分解に注意。全体の要旨把握のような基準を「登場人物・動機・背景事象を一つ残らず確認」する類の質問に落とすと、人間より厳しすぎる評価器になり、相関が改善どころか大きく悪化した失敗例がある。印象型の基準は粗い粒度の質問に留めるか、一発採点との併用を検討する
- コストは質問数に比例する。1本の評価に質問数ぶんのモデル呼び出しが発生するため、大量評価では呼び出し回数と料金を事前に見積もる
- 評価器はベースのLLMの偏りを引き継ぐ。影響の大きい用途では人間の確認と組み合わせる

## 発展的応用

- 人間執筆物への適用: 委託原稿の検収、翻訳の品質チェック、蓄積コンテンツの品質棚卸し。基準を質問に書き下ろせるテキストであれば同じ設計が使える
- 編集ガイドラインの質問化: 文体規定・表記ルールなどの既存チェックリストは、そのままPhase Aの「要件リスト」として流用できる（タスク指示文からの自動抽出を省略できる）
- エージェント・マルチターンタスクへの拡張: どのステップで何が失敗したかの主張単位フィードバックとして、二値質問をステップごとに当てる方向が示唆されている（未検証領域）
