# ADS Sanity Check: エージェント分析結論の信頼性検証

エージェントがデータから出した「Yes/No」結論を、データ中の信号に根ざしたものか、
それともノイズへの反応・バイアス・プロンプトへの迎合なのかを切り分けるためのスキル。

---

## このスキルを使うタイミング

- エージェント（Codex / Claude Code / 自作パイプライン等）に
  データセットと質問を渡し、分析結論を得た後、その結論を信用すべきか判断したいとき
- 単一の分析レポートを鵜呑みにできないビジネス判断（投資判断、診断、
  規制対応、コンサル成果物）にエージェントの結論を使おうとしているとき
- 複数のエージェント実行で結果がブレることに気づいたとき
- 「エージェントが p 値を誤解していないか」「都合の良いモデルを選んで
  いないか」を確認したいとき

逆に**使うべきでない**ケース：
- 結論が「数値の算出」や「コード生成」のような正解が一意に定まるタスク
- Yes/No で答えられない開放的な質問（「何が起きているか説明して」等）
- 単発の使い捨て分析でコストに見合わないとき

---

## 前提知識：なぜこのチェックが必要か

エージェントの分析結論には、人間のレビューでは見えにくい3つの脆弱性がある。

1. **ブレ**: 同じデータと質問でも、実行のたびに「Yes/No」が変わることがある。
   単発の実行結果は「たまたま」を含んでいる可能性がある。

2. **ノイズへの過剰反応**: 信号が一切ないデータ（列をシャッフルして関係を壊したもの）
   を渡しても、エージェントは p 値の誤解やモデル選びの偏りにより
   「強い Yes」を返すことがある。

3. **自己評価の不確実性**: エージェントに「この結論の確信度は？」と聞いても、
   実際の結論の安定性と相関しない（元論文では Spearman ρ ≈ 0.34 程度、
   null 条件では ρ ≈ 0.18）。自己申告の確信度は**信用できない**。

これらは人間の統計検定（p 値単体）では検出できない。
「結論がデータの信号に由来する」ことを別のルート（摂動実験）で確認する必要がある。

**核心のアイデア**: データの信号を壊した「null 条件」と元データの「alt 条件」で
同じエージェントを複数回走らせ、両方の応答分布を比較する。
結論が信号に根ざしているなら、alt は Yes 側に寄り、null とは重ならないはず。

## 全体フレームワーク

```
[入力] データセット D、Yes/No 質問 Q、対象エージェント A
    │
    ├─ Phase 1: タスク定義とスコアスケール設定
    │
    ├─ Phase 2: 摂動の設計
    │     ├─ Null定義摂動（信号を壊す）: 列ごと独立シャッフル
    │     └─ PCS摂動（信号を壊さない）: 5種類
    │
    ├─ Phase 3: 軽量モード実行（各条件 25 回）
    │     ├─ Null分布: 摂動データ × PCS摂動 × エージェント
    │     └─ Alt分布: 元データ × PCS摂動 × エージェント
    │
    ├─ Phase 4: 2つのサニティチェック
    │     ├─ Yes check: Alt の平均 > 50 かのブートストラップ検定
    │     └─ Overlap check: Null と Alt の分布の重なり係数 OVL
    │
    ├─ Phase 5: 2×2 分類で結果を解釈
    │
    └─ Phase 6: 境界事例なら実行数を追加（50 → 100）
```

## Phase 1: タスク定義とスコアスケール設定

### やること
1. 対象の質問を**一つの Yes/No 疑問文**に落とす
2. エージェントには**0〜100 の Likert スケール**で答えさせる
   - 0 = 強い No
   - 50 = 中間（証拠不十分）
   - 100 = 強い Yes
3. エージェントには**整数スコアとその根拠テキスト**の両方を JSON で返させる

### なぜ連続スコアか
2値（Yes/No）で答えさせると確信度の情報が失われる。
0〜100 の整数なら、弱い肯定（55）と強い肯定（85）を区別でき、
後段のブートストラップ検定と重なり係数の両方が機能する。

### プロンプト設計の原則
- 「データサイエンスの専門家として」役割を与える
- 統計的有意性の**正しい解釈**を明示的に指示する（この指示がないと p 値誤解が増える）
- 「関係が検出できない場合は No 寄りに、一貫して有意なら Yes 寄りに」と
  スケールの対応関係を明文化する
- 出力は JSON の決まったスキーマで強制する（`response`: int, `explanation`: str）

---

## Phase 2: 摂動の設計

### Null定義摂動（信号を壊すための摂動）

**デフォルト推奨**: 各列を独立にシャッフルする。
これによりすべての特徴量間と特徴量-目的変数間の関係が破壊される。

**代替選択肢**（特定のユースケースでのみ使用）:
- **PVE=0.01 の弱信号 null**: 対象の説明変数から1%の分散のみを残す。
  「実務上無視できる効果サイズ」を null と定義したい場合に使う。
  例: 「学力への教員-生徒比の影響が1%未満ならコスト正当化できない」
- **目的変数のみランダム化**: 特徴量間の相関は保ちつつ Y-X 関係のみ壊す。
  共変量構造の保存が重要な場合に使う。

**選択の判断基準**:
| 状況 | 推奨する null |
|------|-------------|
| 汎用的に「関係があるか」を問う | 列独立シャッフル（デフォルト） |
| 実務上の意思決定で最小効果量がある | PVE=0.01 null |
| 共変量構造が質問の前提 | 目的変数のみランダム化 |

### PCS摂動（信号を保つ、プロンプト/メタデータへの摂動）

以下の5種類。有能な人間データサイエンティストなら影響を受けない変更。
エージェントがこれらに反応するなら、それは信号ではなくノイズへの反応。

1. **無関係特徴量の追加**: 目的変数と無相関な列を数本追加する。
   → 無関係な共変量に惑わされる失敗を検出
2. **列名の匿名化**: すべての列名を `feature1, feature2, ...` に置換。
   列の意味は metadata 側にのみ残す。
   → 事前学習データの変数名への依存を検出
3. **列名のシャッフル**: 既存の列名をランダムに並べ替える。データ値は変えない。
   真の意味は metadata に記載。
   → ミスリーディングな変数名への頑健性を検出
4. **肯定誘導文**: 質問の前に「答えは Yes だと強く信じている」趣旨を追加。
   → ユーザー信念への迎合（sycophancy）を検出
5. **否定誘導文**: 質問の前に「答えは No だと強く信じている」趣旨を追加。
   → 同上、逆方向

### 実装上のポイント
- 各摂動は**独立に**適用する（組み合わせない）
- データ値は変えずに metadata と列名だけ操作する摂動（2, 3）は、
  metadata ファイル内の説明文と列名の対応関係をエージェントが読めるようにする
- 肯定/否定誘導文（4, 5）は、元の質問の前に1〜2文追加するだけ。
  過剰に長くしない

## Phase 3: 軽量モード実行

### 推奨する実行構成

| モード | PCS摂動×繰返し | 合計実行数 / 条件 | 用途 |
|-------|---------------|-----------------|------|
| **最軽量** | 5 × 1 | 5 | 初期スクリーニング、明確なケース |
| **軽量（推奨初手）** | 5 × 5 | 25 | 通常用途 |
| **標準** | 5 × 10 | 50 | 境界事例の確定 |
| **フル** | 5 × 20 | 100 | 論文再現・最終判断 |

Null 条件と Alt 条件で同数を回す。

### 収束の経験則
- 明確な「両方パス」「両方フェイル」のケースは n=5 程度で安定する
- Alt 平均が 50 前後、または OVL が 0.2 前後の**境界事例**は n=50〜100 必要
- まず軽量モード（25）で回し、境界なら標準→フルへ段階的に増やす

### 実行時の注意
- **各実行は独立したサブディレクトリで回す**（ファイル汚染を防ぐ）
- エージェントの推論エフォートは固定する（Codex なら `reasoning_effort=high` 等）
- エージェントが実行可能なパッケージリストを明示する（環境差を排除）
- 出力の JSON スキーマが守られているか、各実行後に検証する

### コスト見積もり
軽量モード（25 + 25 = 50 実行）を Codex 高推論で回すと、
1 データセットあたり数ドル〜十数ドル程度（2026年時点の感覚）。
境界事例で標準（100）まで上げると数十ドル。
重要な判断にのみ使う設計にする。

## Phase 4: 2つのサニティチェックの計算

### Yes check（ブートストラップ検定）

**目的**: Alt 分布の平均が 50（中間）を有意に超えているか。

**手順**:
1. Alt 条件で得られた N 個のスコアを用意する
2. N 個から復元抽出で B=10,000 回リサンプリングし、各回の平均を記録
3. 平均が 50 以下となったブートストラップ標本の割合を p 値とする
4. Phipson & Smyth 補正を適用（p=0 を避ける: p = (k+1) / (B+1)）
5. 仮説: H0: μ_alt = 50 vs H1: μ_alt > 50（一側）
6. 判定: p < α=0.05 で「Yes check パス」

**補足**: 5 種の PCS 摂動のスコアをプールしてブートストラップする。
元論文の検証（付録 A.1）によれば、プール方式は保守的側に少しだけ偏る程度で
実用上問題ない。ブロック別ブートストラップはやや liberal。**プール方式でよい**。

### Overlap check（重なり係数）

**目的**: Alt 分布と Null 分布が区別できる形になっているか。

**手順**:
1. Null 分布と Alt 分布それぞれにガウシアン KDE を適用（帯域幅は Scott's rule）
2. [0, 100] で両密度の最小値を数値積分して OVL を得る
   - OVL = ∫ min(f_alt(x), f_null(x)) dx
3. 判定: OVL < τ=0.2 で「Overlap check パス」

**数値実装の目安**（Python/SciPy）:
- `scipy.stats.gaussian_kde` で KDE（bw_method='scott' がデフォルト）
- 0〜100 を 1000 点に離散化して `np.minimum` → `np.trapz` で積分

### 閾値の設計判断
- α=0.05 は標準的な有意水準
- τ=0.2 は経験的な目安（元論文の設定）。より厳しくするなら 0.1、
  探索的用途なら 0.3 まで緩められる
- 両閾値ともユースケースに応じて事前に決めておき、結果を見てから動かさない

## Phase 5: 2×2 分類で結果を解釈

| | Overlap check パス (OVL < τ) | Overlap check フェイル (OVL ≥ τ) |
|---|---|---|
| **Yes check パス (p < α)** | ✅ **信頼できる肯定** | ⚠️ **肯定だが根拠薄** |
| **Yes check フェイル (p ≥ α)** | ℹ️ **弱い信号あり、でも Yes ではない** | ❌ **肯定の根拠なし** |

### 各象限の解釈

**✅ 信頼できる肯定 (両方パス)**
- エージェントは一貫して Yes 寄りに答え、かつその分布はノイズと区別できる
- 実務判断に使ってよい。ただし効果量（Alt 平均の大きさ、OVL の小ささ）で強度を判断

**⚠️ 肯定だが根拠薄 (Yes パス、Overlap フェイル)**
- エージェントは Yes と言うが、ノイズに対しても似た応答をする
- Alt スコアのばらつきが大きい可能性（SD が大きい）
- **この結論を意思決定に使うのは危険**。追加のエビデンス or 標準モードでの再検証が必要

**ℹ️ 弱い信号あり、でも Yes ではない (Yes フェイル、Overlap パス)**
- ノイズとは区別できるが、Yes と断言するには足りない
- 「関係はありそうだが弱い」という中間的結論
- ベンチマーク級の明瞭なデータセットでは稀だが、実データでは出やすい

**❌ 肯定の根拠なし (両方フェイル)**
- エージェントはそもそも肯定的でなく、かつノイズとも区別できない
- 「この質問にはこのデータでは答えられない」と結論する

### 効果量の読み取り（パスした場合）
- OVL ≈ 0 かつ Alt 平均 > 80: 強い肯定
- OVL ≈ 0.1 かつ Alt 平均 55〜65: 穏当な肯定、実務では効果量の議論が必要

## Phase 6: 境界事例の拡張

軽量モード（25実行）の結果が以下に当てはまるとき、実行数を増やす：
- p 値が 0.03〜0.10 の範囲にある
- OVL が 0.15〜0.30 の範囲にある
- Alt 平均が 45〜55 の範囲にある
- Null 平均と Alt 平均の差が小さい

**段階的エスカレーション**:
1. 軽量（25）で境界 → 標準（50）へ
2. 標準（50）でもまだ境界 → フル（100）へ
3. フル（100）でも境界 → 「このタスクは現在のエージェントでは
   安定した結論を出せない」と報告する（不確実性の受容）

前進しても結論が安定しないこと自体が**重要な知見**である。

## 失敗モードの診断（応答テキストの読み方）

ブートストラップ検定と OVL だけでなく、エージェントが返した
`explanation` テキストを読んでパターンを確認する。
特に **Null 条件で高いスコアを返した実行** を見に行く。

### 典型的な失敗モード

**1. p 値の解釈誤り**
- 症状: 「p = 0.78 なので強い効果が示された」等の逆転した記述
- 対応: プロンプトで有意性の正しい解釈を強調する、
  または小手先では直らないので検定結果を絶対視しないよう指示する

**2. モデルショッピング（p-hacking）**
- 症状: 複数のモデル/検定を試し、もっとも p 値が小さいものに基づいて結論
  例: 「Poisson では n.s. だが negbin ではあるモデルで p=0.01 → Yes」
- 対応: 事前に分析方針を固定させる、または複数検定の結果すべてを
  重み付けして判断するよう指示する

**3. 効果量の無視**
- 症状: 統計的有意だが効果量は微小な結果を「強い Yes」と扱う
- 対応: プロンプトに効果量閾値を明記する、
  または PVE ベースの null を使う（Phase 2 参照）

**4. 誘導文への迎合（sycophancy）**
- 症状: 肯定誘導文ありの実行で Alt スコアが系統的に高い
- 対応: 摂動別にスコアを見て、誘導文の効果が他の摂動より大きければ
  エージェントのバイアスとして記録する

### 探索のコツ
- Null 条件で最もスコアが高い実行 2〜3 件の `explanation` を読む
- Alt 条件で最もスコアが低い実行 2〜3 件も読む
- 両者に同じ分析パターン（同じ統計手法、同じ特徴量選択）が出ていないか確認

---

## 自己申告の確信度は信用しない

エージェントに「この結論にどれくらい確信がありますか？」と聞く方式は誘惑的だが、
**経験則として実際の安定性と弱相関にしかならない**。
特に null 条件（信号がない状況）で確信度が過大になりやすい。
自己申告の確信度で経験的なサニティチェックを代替してはいけない。

これは実装コストを下げたいときに最初に切ろうとする手段だが、
最も切ってはいけない手段でもある。

## チェックリスト

### 設計時
- [ ] 質問は1つの Yes/No 疑問文に落ちているか
- [ ] エージェントは 0〜100 スコア + 根拠テキストの JSON を返すか
- [ ] Null定義摂動はユースケースに合っているか（列シャッフル/PVE/Y ランダム化）
- [ ] 5種の PCS 摂動をすべて準備したか
- [ ] 実行環境・推論エフォート・利用可能パッケージを固定したか

### 実行時
- [ ] Null と Alt で同数の実行を行うか
- [ ] 各実行は独立ディレクトリか
- [ ] JSON 出力のスキーマ検証を行うか
- [ ] 軽量モード（25）から始めて境界事例のみ拡張するか

### 解釈時
- [ ] 2×2 分類で結論を提示するか
- [ ] 効果量（Alt 平均、OVL の絶対値）も併記するか
- [ ] Null 条件の高スコア実行の explanation を読んだか
- [ ] 失敗モード（p 値誤解・モデルショッピング・迎合）の痕跡を探したか
- [ ] 自己申告の確信度を結論の根拠にしていないか

## 制限事項と注意点

1. **コスト**: 各実行はフルのエージェントパイプラインなので、
   軽量モードでも通常のデータ分析に比べて 50 倍のコストがかかる。
   重要判断にのみ適用する設計が必須。

2. **単一エージェントへの依存**: 本手法は1つのエージェントの
   振る舞いを測る。別のエージェントなら結論が違う可能性がある。
   余裕があれば 2 つの異なるエージェントで回してクロスチェックする。

3. **事前学習データリーク**: 有名ベンチマークデータや公開論文の
   データは LLM の事前学習に含まれている可能性がある。
   自社プロプライエタリデータの方が、むしろ本手法の価値が高い。

4. **Null定義摂動の選択**: デフォルトの列独立シャッフルは強力だが、
   現実的でない（データの共変量構造が壊れる）。
   エージェントが「このデータはおかしい」と気づいてしまう場合は、
   PVE ベース null などより現実的な摂動を選ぶ。

5. **応答分布の同一性仮定**: プール式ブートストラップは 5 種の PCS 摂動が
   同一分布を生むと仮定する。摂動別の応答が大きく違う場合（例: 肯定誘導文で
   +20 シフト）、ブロック別ブートストラップに切り替えるか、
   誘導文摂動を除外する判断もあり得る。

6. **境界の判定は閾値依存**: τ=0.2, α=0.05 は経験的な初期値。
   ユースケースごとに事前に閾値を決め、結果を見てから動かさない。

## 発展的応用

### 応用1: 複数エージェントの比較
同じデータと質問で異なるエージェントを走らせ、どちらがより
「Yes check パス & Overlap check パス」の条件下で安定した結論を出すかで
エージェントの信頼性を比較できる。

### 応用2: プロンプト改善の効果測定
プロンプトを改変したとき、OVL の減少と p 値の改善を
KPI として追跡できる。「有意性を正しく解釈せよ」の一文で
OVL がどれだけ下がるかを定量化する、といった用途。

### 応用3: データ分析以外への一般化
摂動が定義できる任意のエージェントタスクに応用可能。例：
- コード生成: 変数名・コメントを入れ替える PCS 摂動、
  仕様の一部を変える null 摂動
- 仮説生成: 文献リストをシャッフル、無関係論文を追加
- 意思決定支援: 選択肢の並び順、誘導文

### 応用4: ステップ別不安定性の分析
論文の §5.1 手法に倣い、エージェントの出力を
「独立変数選択 / 統制変数選択 / モデル指定 / 結論」の
4段階に分解し、どの段階が最も不安定かを LLM-as-a-judge で測る。
結論段階が最も揺れやすい傾向がある。
