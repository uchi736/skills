# コードとドキュメントの整合性チェック

関数のドキュメントに書かれている挙動と、実際の実装コードの挙動がズレていないかを検出するスキル。たとえばJavadocには「大文字小文字を区別しない」と書いてあるのに、実装は区別している、といった意味的な食い違いを見つける。

誤報を抑える設計に全振りしているので、ズレを報告したときの信頼性は高い。代わりに取りこぼしは構造的に発生する。すべてのズレを網羅したい用途には向かない。

## このスキルを使うタイミング

- ライブラリやAPIのドキュメント品質をレビューしたい
- リリース前にdocstringと実装の乖離がないか確認したい
- 既存コードベースでドキュメントのドリフト（コードだけ更新されて説明が置き去り）を洗い出したい

## 単純なアプローチがうまくいかない理由

LLMに「このドキュメントとコード、合ってますか？」と直接聞く方法は機能しない。同じ質問を少し言い換えただけで答えが変わる程度にはLLM判定が不安定で、誤報が大量に出るか、逆に見逃しが頻発する。

素朴な静的解析もパターンが限定的で、意味的なズレ（仕様と実装の食い違い）の多くを拾えない。

## 仕組み: 二重生成クロスチェック方式

考え方は単純で、ドキュメントから2つの独立した成果物（テストと参照実装）をLLMに別々に生成させ、両者を突き合わせる。手順は以下のとおり。

1. 調べたい関数のドキュメントだけをLLMに渡し、ユニットテストを生成させる
2. 生成したテストを既存コードに対して実行し、各テストの合格・不合格を記録する
3. 同じドキュメントから、今度はLLMに関数のコード本体を書かせる（以下「新コード」）。このとき既存コードは見せない
4. ステップ2で使ったのと同じテストを、新コードに対しても実行する
5. 各テストを「既存コードでの結果」と「新コードでの結果」の組み合わせで4分類する
6. 特定のパターンに当てはまったときだけ、ズレとして報告する

肝はステップ5以降。各テストは次の4通りのどれかに当てはまる。

| 既存コード | 新コード | 分類 | 意味 |
|---|---|---|---|
| 合格 | 合格 | p2p | 両方とも仕様通り。何も起きていない |
| 合格 | 不合格 | p2f | 新コードの生成が失敗している疑い |
| 不合格 | 合格 | f2p | 既存コードが仕様からズレている本命 |
| 不合格 | 不合格 | f2f | テストの生成が失敗している疑い |

報告するのは、次の2条件を同時に満たすときだけに限定する。

- f2p（既存コードで不合格、新コードで合格）のテストが1つ以上ある
- p2f（既存コードで合格、新コードで不合格）のテストが1つもない

この厳しい条件設定が誤報を劇的に減らす鍵。テスト側が誤解していたケース（f2f）も、新コード側の生成が失敗していたケース（p2f ≥ 1）も、自動的に除外される。2つの独立生成物が同じ仕様を表現できているという証拠が揃ったときだけ報告する、という設計。

## 具体例

Javadocに「大文字小文字を区別しないプレフィックス判定」と書かれたメソッドがあり、実装は区別していた場合。

- テスト: 大小区別しないプレフィックス一致を検証するテスト
- 既存コード: 大小区別するのでテストは不合格
- 新コード: ドキュメント通りの大小区別しない実装が生成されるのでテストは合格
- → f2pに該当、p2fは発生せず → ズレとして報告

逆にテスト生成側が誤解していた場合（例: 「全prefixと一致すべき」という誤解釈）は、既存コードでも新コードでも不合格 → f2fに分類されて自動で除外される。この除外機構が、単発の「このドキュメントとコード合ってる？」という問いより大幅に誤報を減らす。

## 実装上の勘所

独立性の確保が最重要。テスト生成と参照実装生成は必ず別のLLM呼び出しにする。同一セッションで連続生成すると、相関した誤りを持ちうる。

既存コードを見せないことも鉄則。テスト生成時と参照実装生成時、既存コードの中身をLLMに見せてはいけない。見せると「既存コードに合わせた」成果物が生成され、検証の意味が消える。

テストがコンパイル・実行できない場合は、最大3回程度の修復試行を行う。それでも動かないなら「判定不能」として見送る。無理に判定を出すより、精度を守るために諦める方がよい。

テスト項目の粒度は、細かい検証項目を多数生成するほど4象限の判定が情報量を持つ。経験則として1関数あたり5〜20項目が目安。

## 言語対応

原論文ではJava, C#, Rustで動作が確認されている。他の言語でも、以下の3要素が揃えば原理的には適用可能。

- ドキュメントを関数単位で抽出できる
- 単体テストを自動実行できる環境がある
- LLMがその言語のテストとコードを生成できる

## 制限事項

再現率は構造的に低い。誤報を減らす設計のため、本物のズレを見逃すことがある。網羅性重視の用途には向かない。

仕様が曖昧な場合も機能しにくい。ドキュメントが何通りにも解釈できる書き方だと、テストも参照実装もばらついて判定不能のケースが増える。

ベースLLMの性能にも依存する。仕様が複雑すぎて正しいテストを生成できないと機能しない。逆にいえばLLMが賢くなるほど有効性は上がる。

## アンチパターン

1. 既存コードを文脈に含めてテストや参照実装を生成する。検証の独立性が壊れる
2. テストと参照実装を同一LLM呼び出しで生成する。相関誤りが起きる
3. f2p > 0 だけで報告する。p2fチェックを省くと誤報が残る
4. 再現率を上げようとして判定ルールを緩める。このスキルの設計意図（精度優先）に反する

## 他の検証タスクへの応用

同じ「仕様から2つの独立した成果物を生成して突き合わせる」考え方は、コードとドキュメントの整合性以外にも転用できる。

- 仕様書と実装の照合: 仕様からテストとプロトタイプを独立生成して突き合わせる
- リファクタリング前後の挙動保存確認: 旧コードを「仕様」として扱い、そこからテストと等価実装を生成
- LLM出力の自己検証: 元のプロンプトから評価ルーブリックと別セッション再生成の出力を生成して突き合わせ

応用する場合も、独立性の確保と既存成果物を見せないというルールは共通。
