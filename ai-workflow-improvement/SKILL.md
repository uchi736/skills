# AIワークフロー改善スキル

検索・推論・整形などの複数ステップが連鎖するAIワークフロー（LLMパイプライン）を、
各ステップの中間出力を証拠として記録し、失敗の原因をステップ単位で特定したうえで、
最小の変更から段階的に改善する手順。「1つのプロンプトを良くする」のではなく
「1つのデプロイ可能なワークフロー全体を、評価セット全体で底上げする」ためのレシピ。

## このスキルを使うタイミング

- 複数のLLM呼び出しとコードステップが連鎖するワークフロー（RAG、多段検索QA、
  検証付き生成、分類、エージェントワークフロー等）の精度を上げたい
- 単一プロンプトのチューニングでは頭打ちになっている
- どのステップが失敗の原因か分からず、闇雲にプロンプトを書き換えている
- スコア関数（評価指標）が定義済みで、それに対して系統的に改善したい

逆に、単一ステップ・単一プロンプトの単純なタスクには重すぎる。その場合は普通の
プロンプト改善で十分。

## 前提知識：なぜこのアプローチが有効か

多段パイプラインの失敗は、個々のステップ単独ではなく**ステップ間の相互作用**で起きる。
検索が薄ければ推論が破綻し、整形が甘ければ正しい答えがスコアラに弾かれる。1つの
プロンプトを単独でチューニングしても、鎖の別の場所にあるボトルネックは見えない。

核心は4つの原則。

1. **共有テスターとタスクを分離する。** 評価ランナー（ケース読み込み、実行、採点、
   成果物記録）は再利用可能な共有基盤にし、各タスク固有のプロンプト・データ・
   採点ルール・変更可能範囲はタスク側に閉じ込める。同じランナーで複数タスクを評価できる。

2. **判断を記録された証拠に接地する。** 各ステップの入力・出力・診断ログを必ず記録する。
   そうすれば、誤答が検索・推論・整形・最終応答のどこで生まれたかを実際に見て判断できる。
   証拠なしの推測でプロンプトを書き換えない。

3. **最小の有効な変更を優先する。** プロンプト編集から始める。設定変更や構造変更へ
   進むのは、記録された失敗が「プロンプトでは直らない」と示したときだけ。

4. **最適化を境界内に保つ。** 何を変えてよいか・いけないかを事前に明文化し（スコープ契約）、
   提案された変更は評価前に必ず独立にレビューする。制約なしの自動最適化は
   サンプルへの過学習に陥りやすい。

**最重要の経験則。** このスキルの元になった研究では、最大の改善はプロンプトではなく
**構造変更**から得られた（多段検証タスクで平均+30pp超）。一方で、プロンプトだけで
十分に改善するタスクも多い。したがって最も価値ある判断は「いつプロンプトに留まり、
いつ構造へ拡大するか」の見極めにある。プロンプトを延々といじり続けるのも、
最初から構造を作り込むのも、どちらも非効率になる。

## 全体フレームワーク

最適化は「現状を測る → 原因を突き止める → 1つだけ直す → 検証して残すか捨てる」の
反復。1ラウンドで変える箇所は常に1つに絞る。

```
[Phase 0] セットアップ
  ├─ スコープ契約を書く（許可する最適化レベル：プロンプト文 / チェーンパラメータ / チェーン構造）
  ├─ パイプラインを「観測可能」にする（各ステップの入出力・診断・所要時間を記録）
  └─ スコア関数を固定する（[0,100]の比較可能な単一指標）
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  最適化ループ（予算が尽きるまで反復）                       │
│                                                          │
│  1. 評価   現バリアントを訓練スプリットで実行              │
│            → 最終出力・スコア・中間ステップ出力を記録      │
│              ↓                                           │
│  2. 帰属   失敗をステップ単位・修正タイプ別に分類          │
│            （プロンプトで直る / 構造でしか直らない）        │
│              ↓                                           │
│  3. 提案   支配的な失敗クラスタに対し、スコープ内の変更を   │
│            1つだけ提案（プロンプト優先）                   │
│              ↓                                           │
│  4. レビュー 独立にチェック（スコープ遵守・データ漏洩・     │
│            プレースホルダ整合・スコアラ互換）              │
│              ↓ (合格)                                    │
│  5. 比較   提案バリアントを検証スプリットで評価し、         │
│            これまでのベストと集計スコアで比較              │
│              ↓                                           │
│  6. 判定   改善→採用して反復 / 退行→棄却 /                │
│            プロンプトが頭打ち かつ 構造的ボトルネックを     │
│            帰属が示す→構造変更へ拡大                       │
└──────────────────────────────────────────────────────────┘
```

## 各フェーズの詳細

### Phase 0: セットアップ

最適化を始める前に、3つを固める。これを飛ばすと後のフェーズが機能しない。

**スコープ契約を書く。** 許可する変更レベルを明示する。レベルは3段階。
- プロンプト文（最も安全・最初に試す）
- チェーンパラメータ（検索深度、リトライ回数などの設定値）
- チェーン構造（ステップの追加・分岐・後処理ノードの挿入）

タスクの制約に応じてどこまで許可するか決める。たとえばセキュリティ分類タスクで
「パイプライン構造は固定、プロンプトのみ変更可」とするなら、契約にそう書く。
契約は最も優先される方針文書であり、ループ中の判断を上書きする。

**パイプラインを観測可能にする。** 各ステップが名前付きの中間出力を必ず書き出すように
する。最低限、以下の状態を保持する。

| フィールド | 内容 |
|-----------|------|
| context | 評価ケースの入力 |
| output_text | 採点対象の最終出力 |
| step_outputs | ステップ名をキーとした中間結果（ノードごと） |
| diagnostics | デバッグトレース・警告 |

ステップごとに名前付き出力を残すことで、パイプラインを「1つの不透明な文字列」ではなく
「型付きの中間成果物の列」として検査できる。実行は一括invokeではなくストリーミングにし、
各ノードの更新と所要時間を逐次記録すると、後段の解析が楽になる。

**スコア関数を固定する。** [0,100]の比較可能な単一の合成スコアを定義する。タスク固有の
補助指標（完全一致、F1、フォーマット妥当性、LLM判定など）は追加してよいが、
最適化対象となる比較可能な目的関数は1つに保つ。

### Phase 1: 評価

現バリアントを**訓練スプリット**で実行する。テストスプリットでは実行しない（後述の
ガードレール参照）。各ケースについて、最終答え・スコア・中間ステップ出力・
ステップ所要時間を記録する。チェーンが例外を投げたら、診断に記録し空出力で採点して、
残りのケースは継続する（1件の失敗で評価全体を止めない）。

### Phase 2: 帰属分析（このスキルの心臓部）

失敗の原因をステップ単位で特定する。ここが手戻りを減らす最大の鍵。深いLLM解析の前に、
まず軽量・決定的なヒューリスティックで一次分類する。

**手順：**
1. スコア閾値を下回るケースを抽出する
2. 各失敗を、可能性の高いステップに割り当てる
3. 失敗を「プロンプトで直るもの」と「構造でしか直らないもの」に振り分ける

**失敗原因 → ステップ・修正タイプの対応表（一次分類のヒューリスティック）：**

| 観測される失敗パターン | 疑うステップ | 一次的な修正タイプ |
|----------------------|-------------|------------------|
| 必要な根拠が出力に含まれていない | 検索 | まずプロンプト、繰り返すなら構造 |
| 中間ステップの出力が空 | 該当ステップ | 構造（カスケード失敗の起点） |
| 早い段階の空出力が後段に波及 | 上流ステップ | 構造 |
| 冗長な答え（正解を含むが余分が多い） | 最終応答 | プロンプト（簡潔さ制約） |
| 不当な棄権（答えられるのに答えない） | 最終応答 | プロンプト（必答ルール） |
| フォーマット不正（正解は出ているが余計な文字付き） | 最終応答 | プロンプト→効かなければ構造（決定的後処理） |
| 最終指示が弱く回答が安定しない | 最終応答 | プロンプト |

検索ステップは、ステップ名に検索系の語が含まれることで認識できる。検索ステップでは
「質問→出力のトークン重複」を計算し、検索品質を hit / partial / miss に分類すると、
検索が薄いのか推論が悪いのかを切り分けられる。

**失敗を支配的なクラスタにまとめる。** 個別の失敗を、原因カテゴリ（根拠不足・不当な棄権・
冗長回答・不正フォーマット・弱い最終指示など）ごとに件数で集計する。最も件数の多い
クラスタが、次に直すべき対象。

### Phase 3: 提案（変更は常に1つ）

**支配的な失敗クラスタ1つ**だけを対象に、スコープ内の変更を1つ提案する。複数同時に
変えると、何が効いたか分からなくなる。

**プロンプト優先。** まずプロンプト編集を試す。プロンプトは最も安く・最もリスクが低い。
代表的なプロンプト修正パターン（具体的な文面ではなく、変更の方向性）：

| 失敗モード | プロンプト修正の方向性 |
|-----------|---------------------|
| 冗長な答え | 最短回答を求める簡潔さ制約を加える（エンティティ名・数値・日付・yes/noのみ等） |
| 不当な棄権 | 「常に答えを出す／『不明』『該当なし』を言わない」必答ルールを加える |
| 不正フォーマット | 出力形式を厳密に指定する（最終行にIDのみ、完全文を出さない等） |
| ドメイン固有の取り違え | 混同しやすいペア限定の慣習・規則を追加する（カテゴリAではなくBを使う等） |

**経験則1：ルールは「狙い撃ち」で。** 広い網羅的ルール（「迷ったら万能カテゴリXを使う」
のような catch-all）は退行しやすい。混同しやすい特定ペアに絞った規則の方が効く。
規則を足し続けても、ある点を超えると効果は逓減する。「足す」だけでなく「正しい点で
止める」判断が要る。

**経験則2：最適プロンプトはモデルごとに違う。** 同じタスクでも、効くプロンプトはモデルで
異なる。あるモデルでは詳細な規則を加えると精度が上がり、別の（特に小型の）モデルでは
同じ規則がフォーマット抽出を壊して精度を下げる。プロンプトは**モデルごとに独立に
最適化する**。1つのモデルで作ったプロンプトが他のモデルでも最良という前提を持たない。
小型モデルではむしろ短いプロンプトが最良になることがある。

**経験則3：修正には順序がある。** たとえば「冗長を簡潔さ制約で直す→次に棄権を必答
ルールで直す→再度帰属分析」のように、1つ直すごとに帰属をやり直す。帰属が
「残りは検索起因（構造的）」と示したら、プロンプト反復はそこで打ち切る合図。

**構造へのエスカレーション。** プロンプトで直らないと証拠が示し、かつスコープ契約が
許可している場合のみ、構造変更へ進む。ボトルネック種別と構造的修正の対応：

| 構造的ボトルネック | 構造的修正パターン |
|------------------|------------------|
| 検索カバレッジ不足（多段検証・多ホップQA） | 検索ホップ数を増やす（例：3ホップ→4〜5ホップ）、マルチクエリ検索、エンティティ単位の救済検索を加える |
| プロンプトで制御しきれないフォーマット不正 | 制約を強制する決定的な後処理ノードを追加する |
| 上流の空出力による連鎖失敗 | 該当ステップに代替経路・フォールバックを構造的に組み込む |

### Phase 4: レビュー（評価の前に独立チェック）

提案された変更を、評価にかける**前に**独立にチェックする。最適化を行うエージェント
自身とは別の視点で検証するのが望ましい。確認項目：

- スコープ遵守（契約で許可された範囲内の変更か）
- データ漏洩がないか（検証・テストの情報やラベルを混入していないか）
- プレースホルダ整合（テンプレートの変数が壊れていないか）
- スコアラ互換（採点契約を変えていないか、出力形式が採点可能か）
- 状態プロトコル遵守・インポート安全性（構造変更の場合）

合格した提案だけを評価に進める。

### Phase 5: 比較

提案バリアントを**検証スプリット**で評価し、これまでのベストと**集計スコア**で比較する。
個別ケースではなく集計値で判断する。

### Phase 6: 判定と反復

- 改善したバリアントは採用し、ループを続ける
- 退行したバリアントは棄却する
- プロンプトレベルの探索が頭打ちになったら、その理由を記録する
- プロンプトが頭打ち かつ 帰属が構造的ボトルネックを示している かつ スコープが許可、の
  3条件が揃ったときだけ構造変更へ拡大する

予算（バリアント数 or ラウンド数）が尽きたら終了。検証で選ばれた最良バリアントを
最終成果とし、テストはこの時点で初めて測る。

## パラメータと設定の目安

元研究で用いられた設定。タスクに応じて調整するが、出発点として有用。

| 項目 | 目安 | 根拠・注意 |
|------|------|----------|
| temperature | 1.0 | 探索のため高めに設定 |
| top_p | 0.95 | 同上 |
| 最適化予算 | 50バリアント または 10ラウンド（先に達した方） | 範囲内で早期停止しない |
| 試行回数 | 3回以上、平均±標準偏差で報告 | 経路依存で分散が大きいため（後述） |
| データ分割 | dev（評価・帰属用）/ val（選択用）/ test（保留） | 例：dev 150 / val 300 / test 300 |
| 推論モデルのトークン予算 | 推論モデルでは「隠れ推論＋可視出力」の合算で消費される点に注意 | 可視出力のみと誤認すると予算不足で短い・不正な答えになる |

推論モデル（思考過程を持つモデル）を使う場合、トークン上限が隠れ推論と可視出力の
合算予算になることがある。これを見落とすと、可視出力が極端に短くなり厳格な
答え抽出スコアラを通らず、本来の実力より低いスコアに見える。予算を上げ、推論努力を
適切に設定して初めて競争力が出ることがある。

## ガードレール（過学習を防ぐ4点）

制約なしの自動最適化は、評価サンプルへの過学習に陥る。以下を必ず仕込む。

1. **スプリットアクセス制御。** 最適化エージェントには個別の訓練ケースのみ見せる。
   検証・テストは集計スコアだけを返す。個別の検証・テストケースを見せると、そこに
   過学習する。

2. **スコープ制約。** タスクごとに許可・禁止の変更を定義し、最適化側とレビュー側が
   独立に強制する。二重チェックにする。

3. **反復メモリ。** バリアント・スコア・打ち切り理由を構造化ログに記録する。同じ
   失敗を繰り返さず、何を試して何が枯渇したかを残す。

4. **バリアント不変性。** 採用・棄却にかかわらず、試行ごとに新しいバリアントファイルを
   作る。既存ファイルを上書き編集しない。構造バリアントも複製し、親チェーンと仮説を
   メタデータに記録し、プロンプトパスは設定から取得する（ハードコードしない）。

## 制限事項と注意点

- **経路依存による分散。** 構造変更へのエスカレーションを許可すると、試行ごとのばらつきが
  大きくなる。ある試行では構造変更を発見し、別の試行ではプロンプトレベルに留まる。
  標準偏差が大きいのは「構造的介入を発見したか否か」の差であり、1つの典型解の周りの
  滑らかな散らばりではない。だから複数試行を回し、平均±標準偏差で報告する。

- **小サンプルでの過学習。** 問題空間に対してサンプルが小さいタスク（競技数学のような
  短答・少数事例）では、プロンプト最適化が単にノイズに過学習することがある。結果が
  試行間でばらつき、ベースラインに対して±数ppで揺れる場合は、改善と断定せず
  「結論保留」として扱う。

- **スコープの広さと比較の公平性。** プロンプトのみの最適化器（探索空間が狭い）と比べると、
  構造変更まで許す本手法は探索空間が広い分有利になる。手法間の比較は「探索空間の
  異なる再現比較」として読み、厳密な公平比較とは区別する。

- **境界はワークスペース上の規約。** タスク間の分離はディレクトリ構成・設定ローカルな
  パス・不変バリアント規約・最適化器の自己チェック・レビュー検証で担保される。
  OS レベルのサンドボックスではない。機密データの実分離が必要なら別途仕組みを足す。

## 発展的応用

- **マルチテナント運用。** 複数のタスクを1つの共有ランタイムの下で「テナント」として
  分離管理する。各テナントが独自のパイプライン・採点・データ・最適化履歴を持ちつつ、
  評価基盤を共通化できる。業務単位・顧客・セキュリティドメインごとに要件が異なる
  企業環境で有用。

- **長いエージェントトレースの証拠拡充。** 採点契約を変えずに、より豊かな証拠を後付けで
  添付できる。各ケースの結果行と実行ログを結合し、ターン・ツール呼び出し・ツール結果・
  エラー・トークン数・所要時間・期待答え・最終出力を含むコンパクトな軌跡を作る。
  ログがなければ中間出力と所要時間から軌跡を合成して劣化対応する。

- **セキュリティ分類への適用。** CVE記述をCWE IDに対応づけるような分類タスクでは、
  パイプライン構造を固定しプロンプトのみに最適化を制約する運用が有効。混同しやすい
  カテゴリペアに絞った慣習規則の追加が効きやすい。
