# LLM-as-Judge + 実行可能証拠による検証

大量の候補アイテム（仕様候補、分類結果、抽出結果、エージェントの判断）
に対してLLMで妥当性を判定させる場面で、LLM判断の偽陽性を機械的に
排除するための設計パターン。

## このスキルを使うタイミング

- LLMに「valid/invalid」「正解/不正解」「採用/棄却」の判定をさせたい
- 判定対象が大量で、人手での確認が現実的でない
- 偽陽性（valid なものを誤って棄却）のコストが高い
- LLM単独の判断（素の LLM-as-Judge）では適合率が不十分と予想される
- 判定の裏付けとなる「実行可能な成果物」をLLMに生成させうる領域

適用が見込める例：
- 動的仕様推論における spurious assertion の除去
- エージェントのツール呼び出し結果の妥当性検証
- 生成された単体テストの有効性確認
- RAG における retrieval 結果の関連性判定
- ファクトチェック結果の二重確認
- 生成物に対する品質ゲートの自動化

---

## 前提知識：なぜ「証拠」を要求するのか

LLMを判定器として使う場合、典型的に次の非対称性が観察される。

- **再現率は高い**：invalid なものを「invalid」と呼ぶ率は90%程度に達しうる
- **適合率は低い**：「invalid」と呼ばれたもののうち実際に invalid なのは半分前後

この状態でLLMの判断だけを根拠に行動すると、valid なものまで大量に
捨ててしまう。一方、LLMの判断を無視すれば、せっかくの再現率の高さが
活かせない。

**解決策**：LLMに判断だけでなく「その判断が正しいことを示す実行可能な
証拠」を生成させ、証拠を独立な仕組みで検証する。検証を通過した判断のみ
に基づいて行動する。

この設計が効く理由：

1. LLMの偽陽性は、証拠が検証を通らないので自動的に弾かれる
2. LLMの真陽性は、証拠が検証を通るので確実に捕捉される
3. 最終的な行動の根拠は「機械検証された事実」になり、LLMの主観判断に
   依存しない

経験則として、素の LLM-as-Judge では適合率が中程度（6割前後）に留まる
のに対し、本パターンでは適合率を大きく引き上げられる（7割前後以上）。
代わりに実装の複雑さと実行コストが増える。

## 基本フレームワーク：5段階パイプライン

```
[1] 既存の安価なフィルタリング
     ↓ (通過した候補のみ)
[2] LLMに構造化フォーマットで判定＋証拠を要求
     ↓ (invalid と判断された候補＋証拠)
[3] 証拠の構文的検証（コンパイル・パース・型チェック）
     ↓ (構文的に有効な証拠)
[4] 証拠の意味的検証（実行・外部ソルバ・独立チェッカ）
     ↓ (意図した invalid を実証した証拠)
[5] 確定した証拠を既存パイプラインに差し戻す
```

重要な設計判断：

- **[1] を省略しない**：LLM呼び出しはコストが高い。確実に捨てられる/
  残せるものは事前に処理する
- **[2] と [4] を分離する**：LLMは信頼できる判定器でない前提で、判定の
  根拠を必ず外部から確認する
- **[5] で既存パイプラインを置き換えない**：LLMの出力（検証済み証拠）
  を既存の検証機構に「入力」として与える。既存機構の代替ではなく補強
  として使う

## 各段階の詳細

### 段階1：既存パイプラインでの事前フィルタリング

LLMに渡す前に、安価で信頼できる方法で明らかに正しい/間違っているもの
を除外する。これはLLMの入力量を減らすだけでなく、「LLMは難しいケース
だけを担当する」という役割分担を明確にする。

経験則として、既存パイプラインを強化してから LLM を適用する方が、
LLM で既存パイプラインを置き換えるより効率が良い。

### 段階2：LLMへの判定要求（プロンプト設計）

プロンプトは次の4層構造にする。

**層A：役割と全体タスク**
- LLMの役割を具体的に指定する（例：「プログラム検証と試験の専門家」）
- 2段階タスクであることを明記：①判定、②invalid の場合のみ証拠生成
- 判定と証拠の対応関係を強調する（valid なら証拠は不要）

**層B：入力フォーマットの仕様**
- 入力をタグ付きセクションで構造化する
  （例：`[[CONTEXT]]` `[[TARGET]]` `[[CANDIDATE]]`）
- 各セクションが何を含むかを明記する
- 領域固有の記号・述語（例：`old(x)`、`size(s)` 等のクエリ関数）が
  あれば、意味をここで定義しておく

**層C：出力フォーマットの仕様**
- 出力もタグ付きで構造化する（例：`[[VERDICT]]` `[[EVIDENCE]]`）
- 判定が一方の値の場合のみ証拠を出力する、という条件分岐を明記する
- 証拠は「機械的に抽出・実行可能な形式」（JUnit テストコード、
  JSON Schema、SMT-LIB 式等）であることを強制する

**層D：Few-shot 例**
- valid のケースと invalid のケースの両方を含める
- invalid のケースでは、証拠がどのような形式かを具体的に示す
- 例は2〜3件で十分。多すぎるとコストが嵩み、判定の偏りの原因にもなる

最後に、本番の入力を同じタグ構造で与える。

パラメータの目安：
- 温度は 0.1 程度の低温にして、出力のブレを抑える
- max_tokens は証拠を含められる余裕を持たせる（テストコード数百行分等）
- top_p は既定値でよい

### 段階3：証拠の構文的検証

生成された証拠を、独立したツールで構文的に検証する。

| 証拠の形式 | 検証ツールの例 |
|-----------|--------------|
| コード（テスト） | コンパイラ、リンタ |
| 構造化データ | JSON Schema、型チェッカ |
| 論理式 | SMT ソルバのパーサ |
| SQL | クエリパーサ |

失敗時の対応：
- **最大3回までリトライする**：LLMに失敗メッセージを返して修正させる
- **3回超えたら破棄する**：無限リトライは、もともと筋の悪い判定で時間
  を浪費する。この破棄された判定は「行動の根拠にしない」
- **破棄された判定は元の候補を valid 扱いに戻す**：証拠が出せないなら
  invalid だという主張を受け入れてはならない

### 段階4：証拠の意味的検証

構文的に正しい証拠を実際に実行・評価し、「本当に主張された invalid を
示すか」を確認する。

この段階は**LLMには担当させない**。LLMは自分の判断の誤りを自分では
見つけにくい。外部の決定論的な仕組み（テスト実行、SMT ソルバ、
シミュレータ、独立に書かれたチェッカ等）で検証する。

実践上の注意：
- 証拠が実行できても、意図した invalid を示さない場合がある
  （LLMの推論誤り）
- 経験則として、構文検証を通った証拠のうち、実際に invalid を示すのは
  半分程度に留まる
- 意味検証を通過したものだけを「確定した invalid 判断」として扱う

### 段階5：既存パイプラインへの統合

確定した証拠を、既存の処理パイプラインの入力として差し込む。
LLMの「判断」そのものを差し込むのではなく、「判断の裏付けとなる実行
可能な成果物」を差し込む点が重要。

この設計の利点：
- 既存パイプラインはLLMの存在を知らなくてよい
- LLMステージを有効化/無効化しても、他の部分は動く
- 複数のLLMを並列に動かしても、出力形式が同じなら統合できる
- LLMを差し替えても、パイプラインの形は不変

## 既知の限界

- **証拠を生成できない領域には適用できない**：判定の根拠を「実行可能
  な形」で表現できる領域でのみ有効。主観評価（文章の好み、美観等）
  には直接適用できない
- **生成側の失敗率**：LLMが妥当な判定をしても、証拠の生成に失敗する
  ことがある。経験則として、妥当な invalid 判定のうち半分前後しか
  意味検証を通る証拠までは到達しない（つまり拾える invalid は
  全体の一部に留まる）
- **データ漏洩のリスク**：評価対象がLLMの訓練データに含まれている
  可能性がある。候補アイテムを実行時に生成する、構文を変える、
  構文的ではなく意味的な等価性で検査する、等で軽減する
- **コスト**：大量の候補にLLM呼び出しをするとコストがかさむ。段階1
  の強化、キャッシュ、バッチAPI 等を検討する
- **反復をしない場合、発見しきれない**：1回のパイプライン実行では、
  証拠をパイプラインに差し戻した後に現れる「新しい偽陽性」を捉えられ
  ない。精度を追求するなら段階5の後に段階2からのループを組む

---

## 発展方向

- **反復的な適用**：1回のパイプライン実行で終わらせず、検証済み証拠を
  既存パイプラインに戻して再実行し、新たに浮かび上がった候補を再度
  LLM に渡す、というループを回す
- **LLM-as-Judge 単独モードとの併用**：証拠生成ができないケースでは、
  素の LLM-as-Judge を「下位の選抜層」として使い、証拠生成可能な
  ケースでは本パターンを使う、というハイブリッド構成
- **複数LLMの投票**：同じ構造のプロンプトを複数LLM（異なるファミリ）
  に送り、判定が一致したケースだけを採用する。OSS モデルと商用モデル
  の併用はコストと多様性のバランスが取りやすい
- **証拠の再利用**：一度生成・検証に成功した証拠は、同系統の候補を
  判定するレグレッションテスト資産として蓄積する

## アンチパターン

1. **LLMの `[[VERDICT]]` だけで判定を確定する**
   → 証拠検証を省略すると、適合率が半分程度のLLM判定をそのまま
   受け入れることになる。素のLLM-as-Judgeと区別がつかない

2. **LLMに証拠の検証まで任せる**
   → LLMは自分の誤りを自分では見つけにくい。「このテストは本当に反例
   か確認して」と聞いても信頼できない。必ず外部ツールで検証する

3. **リトライを無制限にする**
   → 筋の悪い判定で無限にトークンを消費する。3回程度で打ち切る

4. **証拠が出せないケースを invalid と見なす**
   → 「LLMが証拠を出せなかった＝invalid」ではない。証拠が出ないなら
   行動を保留する（valid 扱いに戻す）のが安全側

5. **既存パイプラインを置き換える**
   → 既存の安価で信頼できる検証機構を捨ててLLMに全てを任せると、
   コストが嵩み精度も安定しない。補強として使う
