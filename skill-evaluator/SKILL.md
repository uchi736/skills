# Skill品質評価スキル：Skillsを評価するSkill

対象のSkillファイルを読み取り、13の評価項目で採点し、グレード判定と改善提案を出力する。

## このスキルを使うタイミング

- 新しく作ったSkillの品質を自己チェックしたいとき
- 他者が作ったSkillの採用可否を判断したいとき
- 既存のSkillを改善したいが、どこを直すべきかわからないとき
- 複数のSkill候補を比較して最適なものを選びたいとき

## なぜこの評価方法が有効か

SkillsBench（Li et al., 2026）は、84タスク・7つのAIモデル構成で7,308回の試行を行い、「どんなSkillが効果的で、どんなSkillが逆効果か」を大規模に検証した研究である。主な発見は以下の通り。

- 良いSkillは成功率を平均+16.2ポイント改善するが、悪いSkillは逆効果になる（84タスク中16タスクで悪化）
- 2〜3テーマに絞ったSkillが最も効果的（+18.6pp）で、4テーマ以上は効果が急落する（+5.9pp）
- 程よく詳しいSkillが最良で、網羅的に全部書いたSkillはむしろ悪化する（-2.9pp）
- AIに自分でSkillを書かせても効果がない（平均-1.3pp）。人間のキュレーションが必須
- AIが苦手な専門分野ほどSkillsの効果が大きい（医療+52pp、プログラミング+5pp）

このスキルは、これらの知見を13の採点項目に変換したものである。

---

## 評価ワークフロー

### 全体の流れ

```
対象Skillを読む → 13項目で採点 → 合計・グレード算出 → 改善提案を生成
```

### Step 1: 対象Skillの読み取り

対象のSkillディレクトリを確認し、以下の情報を収集する。

```
確認すること：
├── SKILL.md が存在するか
│   ├── YAMLフロントマター（---で囲まれた冒頭の名前・説明欄）があるか
│   ├── name フィールドがあるか
│   └── description フィールドがあるか
├── 付属ファイル（scripts/, references/, templates/ 等）があるか
├── SKILL.md の文字数・トークン数（目安：日本語1200〜3000文字が最適）
├── テーマ数（大見出しの数で概算。2〜3が理想）
└── 具体例（コードブロックや入出力例）の有無
```

### Step 2: 13項目の採点

各項目を0〜3点で採点する。以下の採点基準に従うこと。

---

#### カテゴリA：ファイル構成（3項目、9点満点）

**A1. 説明書ファイルと冒頭の名前・説明欄（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | SKILL.mdファイルが存在しない |
| 1 | SKILL.mdはあるが、冒頭に名前（name）や説明（description）の記載がない |
| 2 | name と description の両方があるが、descriptionが曖昧または短すぎる（10文字未満） |
| 3 | name と description が的確に記載されており、このSkillが何に使えるかが一読でわかる |

**A2. 付属ファイルの整備（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | 手順の中で外部ファイルを参照しているが、そのファイルが存在しない |
| 1 | SKILL.md単体で完結しており、付属ファイルは不要（この場合1点が妥当） |
| 2 | 付属ファイルがあるが、一部動作未確認またはパスが間違っている |
| 3 | 必要な付属ファイルが揃い、参照パスも正しく、そのまま実行できる |

注意：SKILL.md単体で十分なSkillの場合、A2は1点とする。付属ファイルが「あるべきなのにない」場合のみ0点。

**A3. 環境非依存性（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | 特定のエージェントハーネス専用の記法・機能に強く依存している |
| 1 | 一部に環境固有の記述があるが、手動修正で他環境に移植可能 |
| 2 | ほぼ環境非依存だが、パス指定等に軽微な依存がある |
| 3 | ファイルシステムだけで完結し、どのエージェントでもそのまま利用可能 |

---

#### カテゴリB：手順の質（4項目、12点満点）

**B1. 手順の具体性（0-3点）**

これは最重要項目の1つ。研究でAIの自己生成Skillが失敗した主因は「曖昧すぎる手順」であった。

| 点数 | 基準 |
|-----|------|
| 0 | 「データを処理する」「適切に設定する」のような曖昧な指示のみ |
| 1 | やるべきことは書かれているが、具体的なコマンド名やAPI名がない |
| 2 | 主要なステップでコマンド名・API名が記載されているが、パラメータや設定値が一部不足 |
| 3 | 各ステップで具体的なコマンド、API名、パラメータ、設定値まで記載されている |

採点の補助：SKILL.md内で以下のような表現を探す。
- 0点の兆候：「適切に」「必要に応じて」「一般的な方法で」
- 3点の兆候：具体的な関数名、コマンドライン例、パラメータ値の明示

**B2. テーマ数の絞り込み（0-3点）**

研究では2〜3テーマが最適（+18.6pp）、4+で効果急落（+5.9pp）。

| 点数 | 基準 |
|-----|------|
| 0 | テーマが6つ以上あり、焦点が定まらない。または内容が1行だけで不足 |
| 1 | テーマが4〜5つ。やや多いが、それぞれに意味はある |
| 2 | テーマが2〜3つだが、一部に冗長なセクションがある |
| 3 | テーマが2〜3つに明確に絞られ、各テーマが互いに補完し合っている |

採点の補助：SKILL.mdの大見出し（##）の数を数える。##が2〜4個（前書き・手順・注意点程度）なら良好。

**B3. 文書の長さ（0-3点）**

研究では「程よく詳しい」「コンパクト」が最良（+17〜19pp）、「網羅的」は悪化（-2.9pp）。

| 点数 | 基準 |
|-----|------|
| 0 | 100文字未満（短すぎ）、または10,000文字超（長すぎ） |
| 1 | 100〜800文字（やや短い）、または5,000〜10,000文字（やや長い） |
| 2 | 800〜1,200文字、または3,000〜5,000文字（許容範囲だが最適ではない） |
| 3 | 1,200〜3,000文字（日本語の場合。英語なら800〜2,000トークン） |

採点の補助：`wc -m SKILL.md` で文字数を計測する。

**B4. 動く具体例の有無（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | 具体例がまったくない |
| 1 | 例はあるが擬似コードや説明文のみで、そのまま実行できない |
| 2 | 実行可能な例があるが、入力データが省略されている等で単体テスト不可 |
| 3 | コピペで実行できる具体例が最低1つあり、期待出力も明示されている |

---

#### カテゴリC：分野との相性（3項目、9点満点）

**C1. 対象タスクの明確さ（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | 特定の1つの問題に対する答えになっている（レシピではなく解答） |
| 1 | 汎用性は意識されているが、「いつ使うか」の条件が不明確 |
| 2 | 対象タスクの説明はあるが、適用外のケースが不明 |
| 3 | 「このSkillを使うタイミング」が明示され、適用条件と適用外が両方書かれている |

**C2. AIの苦手分野を補えているか（0-3点）**

研究でのドメイン別効果：医療+52pp、製造+42pp、サイバーセキュリティ+23pp、自然科学+22pp、プログラミング+5pp。

| 点数 | 基準 |
|-----|------|
| 0 | AIの学習データに豊富にある一般知識の繰り返し |
| 1 | 一部に専門知識を含むが、大半はAIが既に知っている内容 |
| 2 | 専門的な手順知識を含むが、AIの一般知識でも代替可能な部分が多い |
| 3 | AIの学習データに乏しい専門的な手順・ワークフロー・業界慣行を提供している |

採点の補助：「この手順をSkillなしでAIに頼んだら、正しくできるか？」を想像する。「たぶんできる」なら0-1点、「たぶん間違える」なら2-3点。

**C3. 検証手段の記載（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | 結果の確認方法が一切書かれていない |
| 1 | 「結果を確認すること」程度の曖昧な記載 |
| 2 | 確認すべきポイントは書かれているが、具体的なコマンドや正常値の範囲がない |
| 3 | 具体的な確認コマンド、正常値の範囲、またはチェックリストが記載されている |

---

#### カテゴリD：リスク管理（3項目、9点満点）

**D1. AIの既存知識との競合リスク（0-3点）**

研究では84タスク中16タスクでSkillsが逆効果。主因は既存知識との矛盾。

| 点数 | 基準 |
|-----|------|
| 0 | AIが広く知っているベストプラクティスと明らかに矛盾する指示を含む |
| 1 | 矛盾の可能性がある記述があるが、限定的 |
| 2 | 概ね矛盾はないが、AIの一般的なアプローチと異なる箇所に「なぜ」の説明がない |
| 3 | AIの既存知識と矛盾せず補完的。既存アプローチと異なる箇所には理由が明記されている |

**D2. コンテキスト効率（0-3点）**

AIの入力枠（コンテキストウィンドウ）には上限がある。Skillが長すぎるとタスク指示の余地がなくなる。

| 点数 | 基準 |
|-----|------|
| 0 | SKILL.md + 付属ファイルの合計が8,000トークン（日本語約12,000文字）を超える |
| 1 | 合計4,000〜8,000トークン。機能するが圧迫感がある |
| 2 | 合計2,000〜4,000トークン。適度な範囲 |
| 3 | 合計2,000トークン以下。入力枠の20%以下で十分な情報を提供 |

**D3. 失敗時のフォールバック（0-3点）**

| 点数 | 基準 |
|-----|------|
| 0 | エラーや想定外の状況への対処法が一切ない |
| 1 | 一部のエラーケースに触れているが、具体的な対処手順がない |
| 2 | 主要なエラーパターンに対処法が書かれているが、網羅性に欠ける |
| 3 | 主要な失敗パターンが列挙され、それぞれに具体的な代替手順が明記されている |

---

### Step 3: 集計とグレード判定

13項目の合計を算出し（39点満点）、以下のグレード表で判定する。

| グレード | 達成率 | 点数 | 意味 | 次のアクション |
|---------|-------|------|------|-------------|
| S | 80%以上 | 31-39点 | すぐ使える | そのまま運用。定期的な見直しのみ |
| A | 65-79% | 25-30点 | 少し直せば使える | 低得点の項目を重点改善 |
| B | 50-64% | 20-24点 | かなり直す必要あり | カテゴリBの手順品質を中心に大幅加筆 |
| C | 50%未満 | 0-19点 | 作り直し | 設計方針を根本から再検討 |

### Step 4: 改善提案の生成

採点結果をもとに、以下のフォーマットで改善提案を出力する。

```
## 評価結果サマリー

- 対象Skill: [名前]
- 合計スコア: [X]/39点（達成率 [Y]%）
- グレード: [S/A/B/C]

### カテゴリ別スコア
- A. ファイル構成: [X]/9
- B. 手順の質: [X]/12
- C. 分野との相性: [X]/9
- D. リスク管理: [X]/9

### 強み（高得点の項目）
- [項目名]: [なぜ高得点か、1文で]

### 改善が必要な項目（2点以下の項目）
- [項目名]（[X]点）: [何をすれば改善できるか、具体的に]

### 最優先の改善アクション
1. [最もインパクトの大きい改善を1つ]
2. [次にインパクトの大きい改善を1つ]
```

改善提案を作る際の優先度：
1. **0点の項目**を最優先で修正（致命的な欠陥）
2. **カテゴリBの低得点項目**を次に修正（研究で最も効果に直結した領域）
3. **カテゴリDの低得点項目**を修正（逆効果リスクの軽減）
4. **カテゴリC → カテゴリA**の順に改善

---

## 複数Skillの比較評価

2つ以上のSkillを比較する場合は、以下の手順で行う。

1. 各Skillに対してStep 1〜3を個別に実施する
2. 結果を横並びの表にまとめる

```
| 評価項目 | Skill A | Skill B | Skill C |
|---------|---------|---------|---------|
| A1. 説明書と冒頭情報 | 3 | 2 | 3 |
| A2. 付属ファイル | 1 | 3 | 2 |
| ... | ... | ... | ... |
| 合計 | 28/39 | 31/39 | 25/39 |
| グレード | A | S | A |
```

3. 合計点だけでなく、カテゴリBとCのスコアを特に重視して判断する

## 注意点と限界

### このスキルでできないこと

- **実効果の計測**：このスキルは設計品質の「事前評価」であり、実際にSkillを使って成功率が上がるかどうかの「事後計測」は別途必要。事後計測にはΔabs（Skillあり/なしの成功率の差）と正規化ゲインgを使う。
- **ドメイン専門性の正確な判定**：C2（AIの苦手分野を補えているか）の採点は、対象分野の専門知識がないと正確に判断しにくい場合がある。
- **ハーネス固有の問題の検出**：特定のAIツール（Claude Code, Gemini CLI等）での動作問題は、実際にそのツールで試さないと検出できない。

### 採点のばらつきを減らすコツ

- 判断に迷ったら、各項目の「採点の補助」に記載した具体的な指標を使う
- B3（文書の長さ）は `wc -m` で客観的に測れるので必ず計測する
- C2（AIの苦手分野を補えているか）は「Skillなしで同じ指示をAIに出したら正しくできるか？」を基準に判断する
