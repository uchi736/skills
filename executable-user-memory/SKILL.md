# 実行可能ユーザーメモリ：会話履歴を型付きコードに変換する

パーソナライズドエージェントの「ユーザーモデル」を、似た文章を引いてくる検索対象ではなく、
インタプリタが直接計算できる型付きコードとして持つ。会話を2フェーズで構造化することで、
通常の検索型メモリが破綻する集計問題と能動的アラートを解けるようにする設計手順。

## このスキルを使うタイミング

次のいずれかが必要なとき：

- 多数のセッションにまたがってユーザー状態を蓄積し、毎回参照する
- 単なる事実検索だけでなく**集計**が必要（「去年の海外出張は何回」「料理ジャンル別の平均外食費」）
- ユーザーが尋ねていなくても出す**能動的アラート**が必要（処方薬とアレルギーの衝突、書類の有効期限切れ、矛盾する送金指示）
- 矛盾する事実（「パクチー好き」→「やっぱり嫌い」）の解決やバージョン管理が必要
- 既存のRAG型メモリが「型付き状態への一行計算で解けるはずの問題」で精度を落としている

**逆に使わないとき：**

- 必要なのが単発の事実想起だけ（「パスポート番号は」「あの医者の名前は」）なら、構造化のコストは回収できない。素のRAGで十分。構造化状態は純粋想起ではほぼ中立であることが検証されている（後述）。

---

## 前提知識：なぜ「コード」なのか

検索型メモリ（ベクトルDB、JSONストア、知識グラフ、フラットなファクト抽出）の根本問題は2つ。

1. **保存と検証が別ステップ**。事実を保存する場所と、その事実に対してルールを当てる場所が分かれている。だから矛盾の解決、多数レコードの集計、論理ルールの強制が苦手になる。
2. **検索はランキング、集計は全列挙**。top-k検索は母集団全体を返す保証がない。件数・合計・group-by・時間窓フィルタは、関連レコードが top-k を超えた瞬間に構造的に解けなくなる。実測でも、レコード数が増えると検索型は崩壊する（一行の集計で解ける問題で正答率が一桁台まで落ちる）一方、型付きオブジェクトに対する list comprehension はほぼ完璧を保つ。

**コードはこの2つを同一媒体に統合する。** `passport.expiry_date - trip.departure_date` のような日付演算も、アレルギーと処方薬の薬効分類が一致するかの判定も、保存された型付き状態に対する1〜数行のPythonで済む。表現（representation）と検証（verification）が同じインタプリタの上で出会う。

さらに重要なのは**能動的アラート**。「処方された抗生物質が数か月前に記録したアレルギーと衝突する」を、ユーザーが尋ねる前に出す。これはクエリ駆動ではなく**状態変化駆動**であり、似た文章を探す検索メモリには原理的に提供できない。コードなら、状態が更新されるたびにインタプリタが制約をboolチェックとして決定的に実行できる。

## 全体フレームワーク

2つのパイプラインで構成する。書き込み側が会話をコードに変換し、読み込み側がそのコードの上で質問応答と能動的サービスを駆動する。

```
【書き込み側：抽出】
  生の複数セッション会話
        │
        ▼
  [Phase 1: 記憶]  セッション毎・追記専用
        │  各セッションから個別事実をフラット文字列で抽出し、走るリストに追記
        ▼
  追記専用ファクトリスト（決して上書き・削除しない）
        │
        ▼
  [Phase 2: 構造化]  定期・全ファクトから一括再生成
        │  蓄積した全ファクトから型付きPython状態を丸ごと作り直す
        ▼
  型付きPython状態（dataclassインスタンスのディレクトリ）

【読み込み側：利用】
  ① マルチストラテジ検索 ──→ 質問応答
       [STATE] 構造化コード + [FACTS] ファクトベクトル + [ARCHIVE] 生会話
  ② 生成・検証・レビューループ ──→ 能動的アラート
       制約を書く → サンドボックス実行 → 昇格判断 → ACTIVE_ALERTS に出力
```

書き込み側で最も重要な設計判断は「記憶」と「構造化」を**別々の関心事として分離する**こと。1回のLLM呼び出しで両方やらせると破綻する（理由は後述）。

## Phase 1：記憶（セッション毎・追記専用）

**やること**: 各セッションから個別の事実を1件1文字列として抽出し、走るリストに追記する。1セッションあたり概ね50〜75件。

**決定的な原則 — 追記専用にする**:
- 上書きしない、削除しない。これが全アーキテクチャで**単一最大の改善要因**（純粋想起ベンチで約+19ポイント）。
- 矛盾する事実が出ても、古い事実を消さずに両方残す。矛盾の解決は後段（構造化と検証）の仕事。

**重要な前処理 — 相対日付を絶対日付に解決する**:
- 「昨日」「先週」をセッションのタイムスタンプを使って絶対日付に変換してから保存する。
- これは最も単純な介入のひとつだが、時間推論の精度に大きく寄与する。未解決の相対日付（"yesterday"のまま）を保存する素朴なフラットファクト系は、時間系の質問で大きく失点する。

**インデックス**:
- 各事実をベクトルストア（ChromaDB等、cos類似）に1件1レコードでインデックス。
- 生会話もセッション粒度でチャンク化し、**別コレクション**にインデックスする。逐語の言い回しが必要な質問のフォールバックになる。

**パラメータの目安**: 抽出LLMは thinking（推論）を有効化、推論バジェット 8192 程度。Phase 1は軽く確率的なので、抽出件数は実行ごとに多少ぶれる。

```python
# Phase 1: 追記専用ファクトリスト（自作の例示。日付は解決済み）
facts = [
    "[2024-09-03] ユーザーはランニングを週3回行うと述べた",
    "[2024-09-03] 目標はハーフマラソン完走（2025-04 開催予定）",
    "[2025-01-12] 左膝に違和感、整形外科を受診（Dr. 佐藤）",
    # ... セッションが進むごとに末尾に追記され続ける（既存行は不変） ...
]
```

## Phase 2：構造化（定期・全ファクトから一括再生成）

**やること**: 蓄積した**全ファクトリスト**から、型付きPython状態を丸ごと再生成する。スキーマ（dataclass定義）はLLMが自分で発明する。人手でスキーマを切らない。

**決定的な原則 — 差分更新してはいけない**:
- セッション毎にコードを「書き直す（incremental rewrite）」方式は逆効果（純粋想起で約-10ポイント）。各書き直しで過去の事実が落ちる。
- さらに、型付けできない事実の受け皿として用意した `notes` フィールドが**逃げ道**になり、LLMが型付けをサボって全部を文字列でダンプし始める。
- 対策は**全コーパスからの毎回フル再生成**。差分でなく作り直しにすることで、構造化時の情報損失が最小化される（監査で約0.18%）。LLMが過負荷になると、構造や型を壊すのではなく、些末な原子的詳細を抽象化して圧縮する挙動になる。

**型付けの方針**:
- 日付は `date()` オブジェクトに（文字列の日付にしない）。
- コレクションは型付きリストに。
- どうしても型に収まらない事実は `notes: list[str]` に入れる。捨てるよりは入れる（ただし逃げ道にしない）。

**パラメータの目安**: 構造化LLMは推論バジェット 16,384 程度、出力トークン上限はかけない。生成コードのサイズは会話量に比例（数百件規模の会話で約7KB、数百レコードの集計用途で50KB前後）。

```python
# Phase 2: 全ファクトから再生成される型付き状態（自作の例示）
from dataclasses import dataclass, field
from datetime import date

@dataclass
class Injury:
    site: str
    onset: date
    clinician: str
    status: str

@dataclass
class FitnessProfile:
    weekly_runs: int
    goal_event: str
    goal_date: date
    injuries: list[Injury] = field(default_factory=list)
    notes: list[str] = field(default_factory=list)  # 型に収まらない事実の受け皿（逃げ道にしない）

profile = FitnessProfile(
    weekly_runs=3,
    goal_event="ハーフマラソン",
    goal_date=date(2025, 4, 1),
    injuries=[Injury(site="左膝", onset=date(2025, 1, 12),
                     clinician="Dr. 佐藤", status="経過観察")],
)
```

集計はこの型付き状態への一行で解ける。これが検索型との分岐点になる。

```python
# 「2024年の海外出張は何回？」── 型付きコレクションへの list comprehension
sum(1 for t in trips if t.is_international and t.departure_date.year == 2024)
# top-k検索は母集団全体を保証できないため、この種の問いは構造的に解けない
```

## 読み込み①：マルチストラテジ検索（質問応答）

クエリ時に**3チャンネルを連結**する。1つを選ぶのではなく全部入れる。リランクはしない。各チャンネルが他の失敗モードを埋め合う。

1. **[STATE] 構造化コード状態**: 該当ドメインの `state.py` 全体を逐語でプロンプトに入れる。長ければ 6,000 文字で切る。型付きインスタンスと事前計算済みアラートをパース不要で読める。
2. **[FACTS] ファクトベクトル検索**: 追記専用ファクトリストへのcos類似でtop-20。構造化で圧縮されたり別表記に正規化された**裾の事実**を拾う。
3. **[ARCHIVE] アーカイブ検索**: 生会話チャンクへのcos類似でtop-10。逐語の言い回しが鍵になる直接引用系の質問用、最後の砦。

固定ヘッダ（`[STATE]` `[FACTS]` `[ARCHIVE]`）で連結し、衝突時は**構造化チャンネルを優先**するよう回答LLMに指示する。

**正直に知っておくべき知見（チャンネル別アブレーション）**:
- 純粋想起ベンチでは、**[STATE]はほぼ中立**（除いても約-1.3ポイント、有意でない）。想起を実際に支えているのは[FACTS]（除くと約-9.3ポイント）と[ARCHIVE]（除くと約-7.3ポイント）。
- つまり構造化状態の価値は**想起ではなく集計と制約**にある。単発の事実想起しか要らないなら、Phase 2の構造化は不要。
- 逆に、集計と能動的アラートはこの構造化状態がなければ成立しない。だから「3チャンネル設計」は、2つの検索モードに構造起点の集計・制約モードを足したものとして読む。

## 読み込み②：生成・検証・レビューループ（能動的アラート）

同じコードを能動的サービスの基盤にも使う。ループは3段。

1. **生成（Generate）**: コーディングエージェントが、コード化された状態に対するPython制約を書く。
2. **検証（Verify）**: サンドボックスで実行する。結果は決定的。チェック時にLLMは不要。
3. **レビュー（Review）**: 結果を見て、精緻化するか・永続化するか・取り込むかを判断する。

有用と分かったチェックは**永続制約に昇格**させる。アラートはマニフェストの `ACTIVE_ALERTS` に書き込まれ、以降すべてのセッション冒頭で（検索なしで）エージェントに見える。

**クロスセッション制約が効く構造**: 関連する事実が別々の会話で・別々の人から・数か月離れて現れ、**スキーマ上で初めて出会う**ケースこそ本領。検索ウィンドウでは共起しない2つの事実も、共通キー（例：薬効分類）でつなげば決定的なboolチェックになる。

```python
# constraints/training_safety.py（自作の例示）
def check_training_load(profile: FitnessProfile, today: date) -> list[dict]:
    alerts = []
    for inj in profile.injuries:
        if inj.status == "経過観察":
            days_to_goal = (profile.goal_date - today).days
            if days_to_goal < 90 and profile.weekly_runs >= 3:
                alerts.append({
                    "severity": "warning",
                    "domain": "fitness",
                    "message": (
                        f"{inj.site}の経過観察中に週{profile.weekly_runs}回走行。"
                        f"目標まで{days_to_goal}日。負荷の見直しを推奨。"
                    ),
                })
    return alerts
# インタプリタが状態変化のたびに決定的に実行する
```

**注意**: バグった制約は毎回決定的に誤発火する。**正しい計算は正しいロジックを意味しない**。制約自体のテストが必要。

## 横断的な設計原則

1. **構造とデータの分離**: スキーマ（dataclass定義）と状態（インスタンス）を分ける。
2. **表現と検証の統合**: コードが保存媒体であり、同時に検証媒体でもある。
3. **ライフドメインによるモジュール化**: `domains/travel/`, `domains/health/`, `domains/finance/` のように独立パッケージに分ける。ドメイン間の漏洩を抑え、選択的ロードを可能にする。
4. **プログレッシブ・ディスクロージャー**: コンパクトなマニフェスト（約200〜300トークン、常時ロード）に、ドメインごとの一行要約と `ACTIVE_ALERTS` を載せる。詳細ドメインはオンデマンドでロードする。状態が膨らんでもプロンプト予算を有界に保つ。
5. **エージェントネイティブなファイルシステム**: ユーザープロジェクトはワークスペース内のただのディレクトリ。専用メモリAPIは不要で、ファイル操作がそのままメモリ操作になる（RL機構とも直接互換）。

### モジュール化の意外な落とし穴

数百レコード規模で3つのロード戦略を比べると、直感に反する結果になる。

| 戦略 | 精度 | コスト | 挙動 |
|---|---|---|---|
| モノリシック（毎回全ダンプ） | 97% | 高（トークン24倍） | ワーキングウィンドウ超過で自分の文脈から誤レコードを引く |
| **モジュラー（オンデマンドロード）** | **98%** | 低（約15倍安い） | 該当ドメインだけ読むので綺麗に処理できる ← 推奨 |
| マニフェスト＋ルーティング | 87%（-10pt） | 中 | 一行要約からの誤ルーティングが起きる |

**教訓**:
- 小規模（〜30ケース）ではモノリシックが勝ち、モジュラーが負ける。だが**ワーキングメモリの天井を超えると逆転**し、モジュラーがPareto優位になる。
- 要約ベースのルーティングは誤りやすい。`load_domain(name)` のように**ドメイン名を直接指定してロード**させる方が、一行要約からLLMにルート判断させるより安全。

## コスト戦略：structure-once-query-many

- 構造化のコストは**1ユーザー状態につき1回**。以降の各クエリは安い。
- 対抗馬の「毎回生レコードを全部ロードしてREPLで計算する」方式は、単発なら安くて正確だが、繰り返すと負ける（毎回レコードを再ロードするため）。
- **損益分岐は概ね3〜11クエリ**（状態が大きいほど早く回収する）。同一ユーザー状態に対して繰り返しクエリが来る本番（月に数百回）では、structure-once-query-many が正しいコスト形状。K=100回で約15倍安くなる。
- ベンチの単発クエリ設計は、この方式にとって**最悪ケース**であることを念頭に置く。実運用ほど有利になる。

## 制限事項と注意点

- **書き込みオーバーヘッド**: LLMパスが2回（フラットファクト系は1回）。構造化は状態サイズに応じてコストがかかる。書き込み側のコスト比はワークロード依存。
- **スケール天井**: Phase 2の一括再生成は数百セッションで頭打ちになる。入力に文字数キャップ（例：500K文字）をかけると、上限超過時に末尾の事実を**無言で落とす**。これが階層的・差分的構造化を将来課題とする最大の理由。本番では素朴な毎回再生成を数百セッション超で当てにしない。
- **純粋想起では構造化はほぼ中立**: 単発の事実想起しか必要ないなら、構造化ステップは要らない。価値は集計と制約に集中している（これは設計上の特性であり、欠陥ではない）。
- **バグ制約は決定的に誤発火する**: 制約のロジックは別途検証が必要。
- **能動的アラートは「パイプライン」が効いている**: 事前計算アラートを外すと能動的検出は大きく落ちる（約52.5%まで）。表現単体ではなく、生成・検証・レビューのパイプラインが決定要因。
- **サンドボックス必須**: ユーザー状態を実行可能コードとして持つ以上、サンドボックス実行と厳格な分離が前提。クロスユーザー漏洩・コードインジェクションを防ぐ。
- **メモリ安全**: 永続メモリにはクロスドメイン漏洩と追従（sycophancy）のリスクがある。ドメイン分離で漏洩を抑え、バージョン管理で監査証跡を残し、明示的なコードで選択的忘却を可能にする。

## 発展的応用

- **階層的・差分的構造化**: 一括再生成の天井を超えるためのスケール戦略。モジュール化はその部分的な一歩。
- **SOTAエピソード検索の併用**: 競合ではなく**加算**。構造化状態が詳細を圧縮で落とした難しいケースで、エピソード文脈が補う。実装上は、状態とクエリの類似度が閾値を下回ったときだけエピソードチャンネルをオンにするのが効率的。
- **RLによる制約生成**: どのad-hocチェックを永続制約に昇格すべきかを学習させる。メモリ操作がファイルシステム操作なので、RLによるメモリ訓練と直接互換。
