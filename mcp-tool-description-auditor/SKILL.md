# MCP Tool Description Auditor

MCPツール記述の品質を体系的に評価し、問題点（スメル）を特定し、
改善された記述を生成するためのスキル。

ツール記述はFM（Foundation Model）がツールを理解する唯一の手がかりであり、
「仕様書」と「プロンプト」の二重の役割を持つ。記述品質がエージェントの
ツール選択・パラメータ推論・実行効率を直接左右する。

## このスキルを使うタイミング

- MCPサーバーのツール記述をレビュー・品質評価したい
- ツール記述の問題点（スメル）を特定したい
- ツール記述を改善・リファクタリングしたい
- 新しいMCPツールの記述を書くためのガイダンスが欲しい
- CI/CDパイプラインに組み込む品質ゲートの基準を知りたい

## 前提知識

### ツール記述が持つ二重の性質

MCPツール記述は2つの役割を同時に果たす：

1. **仕様書（Specification）**: ツールの機能・制約・パラメータを定義する
2. **プロンプト（Instruction）**: FMの推論・判断・ツール選択を方向づける

この二重性により、記述の欠陥は「仕様の不備」と「プロンプトの誤誘導」の
両方として顕在化する。実世界のMCPサーバー調査では、97%以上のツール記述に
何らかのスメルが存在し、公式・コミュニティ問わず品質に統計的な差がないことが
報告されている。

### 改善効果の実態

ツール記述を全コンポーネントで改善すると、タスク成功率が中央値で約6pp向上し、
部分的なゴール達成率も約15%改善する。ただし実行ステップ数が約67%増加する
トレードオフがある。また約17%のケースでは性能が低下するため、闇雲に全てを
追加するのではなく、ドメイン・モデルに応じた最適な組み合わせを選ぶことが重要。

## 全体フレームワーク

```
入力: ツール記述（name + description + input_schema）
  │
  ▼
Phase 1: 6コンポーネント・ルーブリック評価（各1-5点）
  │
  ▼
Phase 2: スメル判定（スコア < 3 のコンポーネント → スメル）
  │
  ▼
Phase 3: 改善案の生成（スメルのあるコンポーネントを強化）
  │
  ▼
Phase 4: コンポーネント最適化（ドメイン・コスト制約に応じた取捨選択）
  │
  ▼
出力: 評価レポート + 改善されたツール記述
```

## Phase 1: 6コンポーネント・ルーブリック評価

ツール記述を以下の6コンポーネントで独立に評価する。
各コンポーネントは1-5のLikertスケールで採点し、スコア3が「最低限合格」の基準。

### コンポーネント1: Purpose（目的の明確さ）

**評価する問い**: ツールが何をするか、明確かつ完全に説明されているか？

| スコア | 基準 |
|--------|------|
| 5 | 機能・振る舞い・返却データを正確な言語で明確に説明 |
| 4 | 機能と振る舞いを説明しているが、わずかに曖昧さがある |
| 3 | 基本的な説明はあるが、振る舞いや出力の詳細が欠けている |
| 2 | 曖昧または不完全な目的の記述 |
| 1 | 目的が不明確または欠落 |

**スメル名（スコア < 3の場合）**: Unclear Purpose

### コンポーネント2: Guidelines（使用ガイドライン）

**評価する問い**: いつ使うべきか、いつ使うべきでないか、どう使うべきかが示されているか？

| スコア | 基準 |
|--------|------|
| 5 | 適切なユースケースと不適切なケースを明示。名前が曖昧な場合の区別説明あり |
| 4 | いつ使うかは記載。使わないケースの記載は最小限 |
| 3 | 使用コンテキストが暗示されるが、明示的な境界条件がない |
| 2 | 使用コンテキストが不明確、または汎用的すぎる |
| 1 | 使用ガイダンスなし |

**スメル名（スコア < 3の場合）**: Missing Usage Guidelines

**Guidelinesの2つの側面に注意：**
- **Activation Criteria（いつ）**: 適切なタスク種別の明示的リスト
- **Operational Instructions（どう）**: 使用時の行動プロトコル

### コンポーネント3: Limitations（制限事項）

**評価する問い**: 既知の制約・注意事項・失敗しうるケースが記載されているか？

| スコア | 基準 |
|--------|------|
| 5 | ツールが返さないもの、スコープの境界、重要な制約を明示 |
| 4 | 主要な制限には言及するが、エッジケースの一部を見落としている |
| 3 | 曖昧または不完全な制限の記述 |
| 2 | 最小限、または暗示的な制限のみ |
| 1 | 制限・注意事項の記載なし |

**スメル名（スコア < 3の場合）**: Unstated Limitation

### コンポーネント4: Parameter Explanation（パラメータ説明）

**評価する問い**: 入力パラメータの意味・型・振る舞いへの影響が十分に説明されているか？

| スコア | 基準 |
|--------|------|
| 5 | 全パラメータに型・意味・振る舞いへの影響・必須/デフォルト状態が説明 |
| 4 | ほとんどのパラメータが説明されているが、わずかな省略あり |
| 3 | 基本的なパラメータ情報はあるが、振る舞いへの影響がない |
| 2 | パラメータが列挙されているだけで意味のある説明がない |
| 1 | パラメータの説明なし、またはスキーマ形式のみ |

**スメル名（スコア < 3の場合）**: Opaque Parameters

**注意**: MCP protocolは入力スキーマ（パラメータ名・型）を自動提供するため、
スキーマと重複する情報よりも「振る舞いへの影響」や「暗黙の制約」の記述を重視する。

### コンポーネント5: Length and Completeness（長さと完全性）

**評価する問い**: ツールの複雑さに対して十分な分量の記述があるか？

| スコア | 基準 |
|--------|------|
| 5 | 4文以上の実質的で構造化された散文。全側面をカバー |
| 4 | 3-4文で良好なカバレッジ |
| 3 | 2-3文でやや完全 |
| 2 | 1-2文で簡潔すぎる |
| 1 | 単一フレーズまたは断片的 |

**スメル名（スコア < 3の場合）**: Underspecified or Incomplete

### コンポーネント6: Examples（例示とのバランス）

**評価する問い**: 説明は自己完結しており、例は補助的な役割にとどまっているか？

| スコア | 基準 |
|--------|------|
| 5 | 記述が自己完結。例がある場合も説明の補足として機能 |
| 4 | 主に記述的で、例への依存は最小限 |
| 3 | 記述と例が均等に混在 |
| 2 | 例に過度に依存し、散文的説明が最小限 |
| 1 | 例のみ提供され、説明的記述なし |

**スメル名（スコア < 3の場合）**: Exemplar Issues

## Phase 2: スメル判定

### 判定ルール

各コンポーネントのスコアが3未満の場合、対応するスメルを検出する。

```
スメル検出 ⟺ コンポーネントの平均スコア < 3
```

### 6つのスメルタイプ一覧

| スメル名 | 対応コンポーネント | 典型的な出現率 | 影響 |
|---------|-------------------|-------------|------|
| Unclear Purpose | Purpose | 約56% | FMがツールの基本機能を理解できない |
| Missing Usage Guidelines | Guidelines | 約89% | 不適切なタイミングでのツール呼び出し |
| Unstated Limitation | Limitations | 約90% | 予期しない失敗やエラー |
| Opaque Parameters | Parameter Explanation | 約84% | 不正確なパラメータ値の推論 |
| Underspecified or Incomplete | Length & Completeness | 約79% | 全体的な情報不足 |
| Exemplar Issues | Examples | 約78% | 正しい使用パターンの推論困難 |

### 深刻度の優先順位

改善効果の観点から、以下の優先度で対処する：

1. **最優先**: Purpose（ツールの根幹的理解に直結）
2. **高優先**: Guidelines（ツール選択判断に直結）
3. **中優先**: Limitations, Parameter Explanation（実行精度に影響）
4. **低優先**: Length & Completeness（他コンポーネントの改善で自然に解消）
5. **状況依存**: Examples（効果がドメイン依存。削除しても性能低下しない場合が多い）

## Phase 3: 改善案の生成

### 改善の基本方針

1. **元の意図を保持する**: 元の記述が伝えようとしている機能・目的を変えない
2. **事実に基づく**: 実行ログや仕様から確認できる情報のみを追加する
3. **コンパクトに保つ**: FMのコンテキストウィンドウは有限。冗長な追加は逆効果
4. **曖昧な表現を避ける**: 「状況により異なる」のような曖昧な制限記述は逆効果になりうる

### コンポーネント別の改善手法

#### Purpose改善のポイント
- ツールが何をするかを1-2文で明確に記述する
- 返却データの形式・内容を具体的に述べる
- 類似ツールとの区別がつく記述にする

#### Guidelines改善のポイント
- 「いつ使う」と「いつ使わない」の両方を明記する
- 具体的な行動指示（例：「日付範囲を指定する場合はend_dateを1日後に設定」）を含める
- 重要な操作上の注意点を含める（これが最も効果的な改善要素の一つ）

#### Limitations改善のポイント
- 明確で具体的な制約のみを記述する
- 「この矛盾は曖昧さの解消が必要」のような自己言及的・曖昧な記述は避ける
- エッジケースや失敗条件を具体的に列挙する

#### Parameter Explanation改善のポイント
- MCPが自動提供するスキーマ（型・名前）と重複しない情報を追加する
- パラメータの「振る舞いへの影響」を記述する（例：「periodを指定するとstart/endは無視される」）
- デフォルト値の振る舞いを明示する

#### Examples改善のポイント
- 実際の実行ログから成功例・失敗例を抽出する
- 例は説明の補足として配置し、例だけに依存しない
- コンテキストウィンドウのコストを考慮し、過度に長い例は避ける

### 改善記述の構造テンプレート

改善後のツール記述は以下の構造で出力する：

```json
{
  "purpose": "ツールの機能・振る舞い・返却データの説明",
  "guidelines": "いつ・どう使うか、いつ使わないかの指針",
  "limitations": "既知の制約・失敗条件・エッジケース",
  "parameter_explanation": "各パラメータの意味・振る舞いへの影響",
  "examples": "成功例・失敗例（任意）"
}
```

## Phase 4: コンポーネント最適化

### コンテキストウィンドウとのトレードオフ

全コンポーネントを含めると性能は向上するが、トークンコストが増加する。
ドメインとモデルに応じて最適な組み合わせを選ぶ。

### 推奨される組み合わせパターン

| シナリオ | 推奨組み合わせ | 理由 |
|---------|-------------|------|
| コンテキスト潤沢 | 全コンポーネント | 最大性能を狙える |
| コンテキスト制約あり | Purpose + Guidelines + Limitations | 主要な判断情報を保持しつつコンパクト |
| 最小構成 | Purpose + Guidelines | 最もコスト効率が良い場合が多い |
| 精密なパラメータ制御が必要 | Purpose + Parameter Explanation | パラメータの正確な使用を優先 |

### Examplesコンポーネントの扱い

Examplesを除去しても統計的に有意な性能低下が起きないケースが多い。
コンテキストが逼迫している場合は、Examplesを最初に削減候補とする。
ただし以下の場合はExamplesが有効：
- パラメータの組み合わせが複雑で、正しい呼び出しパターンが自明でない場合
- エラーパターンが多様で、失敗例が判断に有用な場合

## 実行手順

### ステップ1: 入力の準備

ユーザーから以下のいずれかの形式で入力を受け取る：

- MCPツール定義のJSON（name, description, inputSchema）
- ツール記述のテキスト
- MCPサーバーのソースコード（ツール定義部分を抽出）

### ステップ2: 評価の実施

各ツール記述に対して、6コンポーネントそれぞれを1-5で採点する。
採点時は以下のJSON形式で出力する：

```json
{
  "tool_name": "ツール名",
  "scores": {
    "purpose": 1-5,
    "guidelines": 1-5,
    "limitations": 1-5,
    "parameter_explanation": 1-5,
    "length_completeness": 1-5,
    "examples": 1-5
  },
  "smells": ["検出されたスメルのリスト"],
  "overall_label": "Good" または "Bad",
  "reason": "1文の根拠",
  "improvement_needed": ["スコア3未満のコンポーネントとその問題点"]
}
```

**判定ルール:**
- いずれかのコンポーネントが3未満 → "Bad"
- 全コンポーネントが3以上 → "Good"

### ステップ3: 改善案の生成

スメルが検出されたコンポーネントに対して、Phase 3の手法に基づき改善案を生成する。
元のツール記述の意図を保持しつつ、欠落情報を補完する。

### ステップ4: レポート出力

以下を含む評価レポートを生成する：
- 各ツールのスコアカード
- 検出されたスメルの一覧と深刻度
- 改善前後の記述の比較
- コンテキストコストの考慮に基づく推奨構成

## 低品質ツール記述の典型例

以下のような記述はスメルの塊であり、改善が急務：

```
❌ "Creates PayPal Invoice Link."
   → Purpose: 2, Guidelines: 1, Limitations: 1, Parameters: 1, Length: 1, Examples: 1

❌ "Retrieves the content of a specific email."
   → Purpose: 2, Guidelines: 1, Limitations: 1, Parameters: 1, Length: 1, Examples: 1

❌ "Get detailed information about a specific place."
   → Purpose: 2, Guidelines: 1, Limitations: 1, Parameters: 1, Length: 1, Examples: 1
```

いずれも「何を返すか」「いつ使うか」「制限は何か」が全く記述されていない。

---

## 高品質ツール記述のパターン

良いツール記述の構造パターン：

```
[1行目] 目的の明確な記述（Purpose）
[2-3行目] いつ使う/使わないの条件（Guidelines - When）
[4-5行目] 使用時の操作指示（Guidelines - How）
[6行目] 主要な制限事項（Limitations）
[7行目以降] パラメータの意味と振る舞い（Parameter Explanation）
[任意] 補足的な使用例（Examples）
```

## チェックリスト

### 評価時
- [ ] 6コンポーネント全てを独立に採点したか
- [ ] スコア3の基準を一貫して適用したか
- [ ] ツールの複雑さを考慮した評価をしたか（単純なツールは短い記述でも高スコアになりうる）

### 改善時
- [ ] 元の記述の意図を変えていないか
- [ ] 事実に基づかない情報（ハルシネーション）を追加していないか
- [ ] 曖昧・自己矛盾的な記述を含めていないか
- [ ] コンテキストコストに見合う改善か

### 最適化時
- [ ] ドメインとモデルの制約を考慮したか
- [ ] Purposeは必ず含まれているか（全組み合わせの必須コンポーネント）
- [ ] 不要なコンポーネントを削減してコスト効率を改善したか

---

## 制限事項と注意点

1. **ドメイン依存性**: 最適なコンポーネント組み合わせはドメイン・モデルにより異なる。
   万能の「黄金律」は存在しない。
2. **実行コストのトレードオフ**: 詳細な記述はタスク成功率を上げるが、
   実行ステップ数とトークンコストを増加させる。
3. **退行リスク**: 改善が約17%のケースで性能を低下させる可能性がある。
   特にLimitationsに曖昧な記述が含まれる場合に起こりやすい。
4. **Examples生成の難しさ**: 実際のツール実行ログなしにExamplesを生成すると、
   不正確な例が含まれるリスクがある。ログがない場合はExamplesの追加を見送る。
5. **FMの評価バイアス**: 単一モデルでの評価はバイアスを含む可能性がある。
   複数モデルでの評価（LLM-as-Jury方式）が望ましい。

## 参考情報

本スキルは、MCPツール記述の品質に関する実証研究（Queen's大学 SAILラボ、2026年）
の方法論に基づいている。同研究は103のMCPサーバー・856ツールを対象に、
ツール記述のスメルの蔓延度と、記述改善がFMベースエージェントの性能に与える影響を
体系的に調査した。ルーブリックはAnthropicの公式MCPドキュメント、
実務者ガイドライン、学術文献から統合された6コンポーネントに基づく。
