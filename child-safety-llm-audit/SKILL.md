# Child-Safety LLM Audit: 子供向けLLMアプリのプライバシー検証フレームワーク

子供向け（または子供が利用する可能性のある）LLMベースアプリケーションを、
Privacy by Designの原則に基づいて体系的に監査し、プライバシーリスクと
規制コンプライアンスの両面から評価するスキル。

## このスキルを使うタイミング

- LLMベースの子供向けアプリ（教育チューター、対話ボット、ストーリーテリング等）の設計レビュー
- 既存アプリが子供のプライバシー規制（COPPA/GDPR/PIPEDA）に準拠しているか検証
- 子供向けAIサービスのリスクアセスメントを実施
- アプリの設計書・仕様書・プライバシーポリシーに対する監査レポートを作成
- 子供がアクセスする可能性のある汎用LLMアプリの安全性評価

---

## 前提知識

### なぜこの監査が必要か

子供はLLMアプリとの対話において特有の脆弱性を持つ：

1. **擬人化への感受性**: 幼児（2-7歳）は機械と生物の区別が困難。6-11歳の子供もAIに感情を帰属させる傾向がある。これにより、人間のように振る舞うAIに個人情報を過剰に開示するリスクが高まる
2. **ナッジングへの脆弱性**: 「もっと教えて」等のフォローアッププロンプトが、子供に本来共有しないはずの情報を開示させる可能性がある
3. **プライバシーリスクの理解不足**: 子供はオンラインプライバシーのリスクを十分に理解できない場合が多い
4. **間接的な情報開示**: 「おばあちゃんの家の近くの公園」「明日の遠足」など、直接的な個人情報でなくても身元を推定可能な情報を自然に共有する

### 監査の基盤となる7つのプライバシー原則

以下の7原則は、GDPR・COPPA・PIPEDAの3つの規制フレームワークから抽出・統合されたもの：

| # | 原則 | 概要 |
|---|------|------|
| P1 | データ最小化 | 目的に必要なデータのみを収集する |
| P2 | 目的制限 | 収集時に明示した目的以外にデータを使わない |
| P3 | 透明性と説明可能性 | データの収集・利用・共有を明確に伝える |
| P4 | 有意義な同意メカニズム | 検証可能な保護者同意を取得・維持する |
| P5 | ユーザー権利 | アクセス・訂正・削除等の権利を保障する |
| P6 | セキュリティ・バイ・デザイン | 設計段階からセキュリティを組み込む |
| P7 | 説明責任 | コンプライアンスを実証できる体制を整備する |

### 監査対象の4つのライフサイクルステージ

| ステージ | 説明 | 主要リスク |
|----------|------|-----------|
| S1: データ収集 | 訓練・運用データの取得と前処理 | 過剰収集、同意なき収集、子供の画像混入 |
| S2: モデル訓練 | 事前学習・ファインチューニング・RLHF | 記憶化、データ毒入れ、勾配漏洩 |
| S3: 運用・モニタリング | リアルタイムの対話とデータ処理 | 意図しない開示、プロンプトインジェクション、推論漏洩 |
| S4: 継続的検証 | デプロイ後の監視・更新・ガバナンス | ドリフト、権利行使の困難、同意の形骸化 |

---

## 全体フレームワーク

監査は以下のフローで進行する：

```
Step 0: 対象アプリの情報収集
    ↓
Step 1: ライフサイクル×原則のマトリクス監査（コア監査）
    ↓
Step 2: 子供特有リスクの評価（擬人化・ナッジング）
    ↓
Step 3: 規制別コンプライアンスチェック
    ↓
Step 4: リスク評価の統合とレポート生成
```

---

## Step 0: 対象アプリの情報収集

監査を開始する前に、以下の情報を収集する。ユーザーから直接提供されない場合は、
公開情報・プライバシーポリシー・技術文書から推定する。不明な項目は「不明（要確認）」と記録する。

### 収集すべき情報

- **アプリの種別**: 教育チューター / 対話エージェント / ストーリーテリング / ゲーム / その他
- **対象年齢**: 13歳未満 / 13-16歳 / 年齢制限なし（ただし子供がアクセスする可能性あり）
- **LLMの利用形態**: 自社訓練モデル / API経由（OpenAI, Anthropic等）/ ファインチューニング済み
- **データ収集の範囲**: テキスト入力 / 音声 / 画像 / 位置情報 / デバイス情報 / Cookie
- **保護者関与の仕組み**: あり（詳細）/ なし / 不明
- **適用される規制管轄**: EU（GDPR）/ 米国（COPPA）/ カナダ（PIPEDA）/ 複数 / 不明
- **第三者データ共有**: あり / なし / 不明

## Step 1: ライフサイクル×原則のマトリクス監査

これが監査の中核部分。各ライフサイクルステージに対して、関連する原則のチェック項目を評価する。

### S1: データ収集ステージ

**関連原則: P1（データ最小化）, P2（目的制限）, P4（同意メカニズム）**

#### P1-S1: データ最小化チェック

| チェック項目 | 評価 |
|-------------|------|
| 目的に必要なデータのみを収集しているか | ○/△/× |
| ユーザー入力のフィルタリング（PII除去・リダクション）が実装されているか | ○/△/× |
| Cookie・デバイスID・位置情報等のバックグラウンドデータはデフォルトで無効か | ○/△/× |
| フルネーム・生年月日・連絡先等の識別情報を不必要に収集していないか | ○/△/× |
| ウェブスクレイピングで訓練データを収集する場合、子供のデータ（画像含む）を検出・除外する仕組みがあるか | ○/△/× |

**実装のベストプラクティス:**
- 入力フィルタリングにより、ユーザープロンプトからセンシティブ情報をリアルタイムで除去・再構成する
- 収集するデータフィールドを最小限に制限する
- 訓練データセットに子供のデータが混入しないよう、検出ツール（ハッシュベース検出等）を適用する

#### P2-S1: 目的制限チェック

| チェック項目 | 評価 |
|-------------|------|
| データ収集の目的が明確に定義・文書化されているか | ○/△/× |
| データに目的タグ（subject-purpose pair）が付与されているか | ○/△/× |
| スコープ付きアクセス制御により、目的外のデータ利用が防止されているか | ○/△/× |
| 教育目的で収集したデータが広告・プロファイリング・分析に転用されていないか | ○/△/× |

**実装のベストプラクティス:**
- データ取り込み時にsubject-purposeタグを付与し、ランタイムで同意ポリシーとの整合を検証する
- 出所追跡付きアクセス制御を実装し、収集目的が処理全体を通じて保持されるようにする

#### P4-S1: 同意メカニズムチェック

| チェック項目 | 評価 |
|-------------|------|
| データ収集前に検証可能な保護者同意を取得しているか | ○/△/× |
| 同意者が実際に保護者・法定後見人であることを確認する仕組みがあるか（ID確認、クレジットカード少額課金等） | ○/△/× |
| 子供向けにわかりやすい年齢適切な説明を提供しているか | ○/△/× |
| 同意はダイナミック（随時確認・変更・撤回可能）か | ○/△/× |
| 新しい種類のデータ処理が追加される際に再同意を求めているか | ○/△/× |

**実装のベストプラクティス:**
- 保護者向けのコンセントダッシュボードを提供し、粒度の細かい選択を可能にする
- ビジュアルや動画による説明で、子供にもデータ利用の仕組みを伝える
- 同意管理フレームワークを実装し、保護者がリアルタイムでプライバシー設定を確認・更新できるようにする

---

### S2: モデル訓練ステージ

**関連原則: P1（データ最小化）, P6（セキュリティ・バイ・デザイン）, P7（説明責任）**

#### P1-S2: データ最小化チェック

| チェック項目 | 評価 |
|-------------|------|
| タスクに直接関連する最小限のデータセットで訓練しているか | ○/△/× |
| ファインチューニングに使用するユーザーインタラクションデータは、明示的同意を得たもののみか | ○/△/× |
| 訓練データからPII・センシティブ情報が除去・匿名化されているか | ○/△/× |

#### P6-S2: セキュリティ・バイ・デザインチェック

| チェック項目 | 評価 |
|-------------|------|
| 訓練データが転送中・保存時に暗号化されているか | ○/△/× |
| 訓練データへのアクセスがアクセス制御で制限されているか | ○/△/× |
| データ毒入れ攻撃への対策（データソースの検証・分析）があるか | ○/△/× |
| 差分プライバシー等のプライバシー保護技術が適用されているか | ○/△/× |
| 勾配漏洩攻撃への防御策があるか | ○/△/× |
| バックドア攻撃への対策（勾配ベースプルーニング等）があるか | ○/△/× |

#### P7-S2: 説明責任チェック

| チェック項目 | 評価 |
|-------------|------|
| 訓練データの出所記録（データプロベナンス）が維持されているか | ○/△/× |
| データシート（Datasheets for Datasets）またはモデルカードが作成されているか | ○/△/× |
| データ保護影響評価（DPIA）が実施されているか | ○/△/× |
| 責任あるAI（RAI）フレームワークが導入されているか | ○/△/× |

---

### S3: 運用・モニタリングステージ

**関連原則: P3（透明性）, P4（同意）, P2（目的制限）, P6（セキュリティ）**

#### P3-S3: 透明性と説明可能性チェック

| チェック項目 | 評価 |
|-------------|------|
| 対話中にどんなデータを収集するか明確に説明しているか | ○/△/× |
| データの利用・保存・共有方法が説明されているか | ○/△/× |
| 保護者向けダッシュボードでデータフローを可視化しているか | ○/△/× |
| 子供にもわかるビジュアル・動画ベースの説明を提供しているか | ○/△/× |
| AIの出力がどのように生成されるか説明する仕組みがあるか | ○/△/× |
| リスク分類（expert-identified risk taxonomy）が保護者に提供されているか | ○/△/× |

#### P4-S3: 同意メカニズムチェック（運用時）

| チェック項目 | 評価 |
|-------------|------|
| 保護者同意のログが維持されているか | ○/△/× |
| データ利用やシステム機能の変更時に同意が再確認されるか | ○/△/× |
| 保護者ダッシュボードで権限の調整・撤回が可能か | ○/△/× |

#### P2-S3: 目的制限チェック（運用時）

| チェック項目 | 評価 |
|-------------|------|
| ユーザー入力が即時の対話コンテキスト以外に使われていないか | ○/△/× |
| エフェメラルセッションメモリ（対話終了後にコンテキスト削除）が実装されているか | ○/△/× |
| インタラクションデータのモデル訓練への使用がデフォルトで無効か | ○/△/× |
| 第三者へのデータ共有はサービス提供に必須な場合のみに限定されているか | ○/△/× |

#### P6-S3: セキュリティ・バイ・デザインチェック（運用時）

| チェック項目 | 評価 |
|-------------|------|
| プロンプトインジェクション攻撃への防御策があるか | ○/△/× |
| ジェイルブレイク攻撃への防御策があるか | ○/△/× |
| 推論漏洩（訓練データの意図しない露出）への対策があるか | ○/△/× |
| 入力フィルタリング（有害・敵対的プロンプトのブロック）があるか | ○/△/× |
| 出力フィルタリング（不安全なコンテンツの検出・ブロック）があるか | ○/△/× |

---

### S4: 継続的検証ステージ

**関連原則: P7（説明責任）, P5（ユーザー権利）, P4（同意）, P6（セキュリティ）**

#### P7-S4: 説明責任チェック

| チェック項目 | 評価 |
|-------------|------|
| 定期的な監査・DPIAが実施されているか | ○/△/× |
| システム変更・同意変更のログが記録されているか | ○/△/× |
| 規制当局の問い合わせやユーザーの苦情に対応するチャネルがあるか | ○/△/× |

#### P5-S4: ユーザー権利チェック

| チェック項目 | 評価 |
|-------------|------|
| 保護者・後見人がデータのアクセス・訂正・削除を要求できるインターフェースがあるか | ○/△/× |
| 会話記録・音声・画像等の削除が実行可能か | ○/△/× |
| 権利行使の要求がログ・タイムスタンプ付きで記録されるか | ○/△/× |
| 機械学習における忘却（machine unlearning）や同等の仕組みが検討されているか | ○/△/× |

#### P4-S4: 同意の再検証チェック

| チェック項目 | 評価 |
|-------------|------|
| 新機能・データ利用・ポリシー変更時に保護者への再確認が行われるか | ○/△/× |
| 同意が「生きた文書」として管理されているか | ○/△/× |

#### P6-S4: セキュリティ検証チェック

| チェック項目 | 評価 |
|-------------|------|
| 定期的な敵対的テスト（レッドチーミング）が実施されているか | ○/△/× |
| モデルの整合性チェック（ハッシュベース等）が行われているか | ○/△/× |
| モデル監査により、ドリフトや不正な更新が検出されるか | ○/△/× |
| 差分プライバシー等の保護がシステム応答からの再構築を防いでいるか | ○/△/× |

## Step 2: 子供特有リスクの評価

LLMアプリにおけるプライバシー原則の遵守に加え、子供特有のリスクを評価する。
これらは国連子どもの権利条約（UNCRC）およびUK Age-Appropriate Design Code（AADC）に基づく。

### 擬人化リスク評価

| チェック項目 | 評価 |
|-------------|------|
| システムが自らをAIであると明示的に識別しているか | ○/△/× |
| 対話中に定期的にAIであることをリマインドしているか | ○/△/× |
| 人間のような感情表現（「嬉しい」「悲しい」等）を使っていないか | ○/△/× |
| 特定のエージェント態度・応答が情報開示を促進しないか事前検証されているか | ○/△/× |
| 友好的・共感的な外観が個人情報の過剰開示を誘発しないよう設計されているか | ○/△/× |

### ナッジングリスク評価

| チェック項目 | 評価 |
|-------------|------|
| 「もっと教えて」「今どんな気持ち？」等のフォローアッププロンプトが使われていないか | ○/△/× |
| プライバシー保護ナッジ（pro-privacy nudge）が実装されているか | ○/△/× |
| 特定の情報が共有された時に「保護者に話してみて」等の誘導があるか | ○/△/× |
| 提供された情報がアクセス・閲覧される可能性がある旨のリマインダーがあるか | ○/△/× |

### 年齢適切な設計評価

| チェック項目 | 評価 |
|-------------|------|
| インターフェースが対象年齢に適切な言語・デザインを使用しているか | ○/△/× |
| 保護者ダッシュボードは子供の自律性を損なわない形で設計されているか（全トランスクリプトではなく集約情報） | ○/△/× |
| 子供の発達段階に応じたAIリテラシー教育要素があるか | ○/△/× |
| 子供の参加型デザイン（co-design）が設計プロセスに含まれているか | ○/△/× |

## Step 3: 規制別コンプライアンスチェック

対象アプリの適用管轄に応じて、規制固有の要件を確認する。

### COPPA準拠チェック（米国・13歳未満対象）

| 要件 | 評価 |
|------|------|
| 検証可能な保護者同意（VPC）が取得されているか | ○/△/× |
| 明確で包括的なプライバシー通知が掲示されているか | ○/△/× |
| データ収集が活動参加に合理的に必要な範囲に限定されているか | ○/△/× |
| 保護者がデータの閲覧・削除・追加収集拒否を行える仕組みがあるか | ○/△/× |
| 子供の参加条件として不必要な情報開示が求められていないか | ○/△/× |

### GDPR準拠チェック（EU管轄）

| 要件 | 評価 |
|------|------|
| 16歳未満（加盟国により13歳）の処理に保護者の同意があるか（第8条） | ○/△/× |
| プライバシー通知が子供にも理解できる形式か（第12条） | ○/△/× |
| アクセス・訂正・消去の権利が保障されているか（第15-17条） | ○/△/× |
| データポータビリティの権利が保障されているか（第20条） | ○/△/× |
| 自動意思決定・プロファイリングへの異議権があるか（第21-22条） | ○/△/× |
| 技術的・組織的安全措置が実装されているか（第32条） | ○/△/× |

### PIPEDA準拠チェック（カナダ管轄）

| 要件 | 評価 |
|------|------|
| 子供の成熟度に応じた有意義な同意が取得されているか | ○/△/× |
| 子供が合理的に同意できない場合、保護者から同意を取得しているか | ○/△/× |
| 10の公正情報原則が遵守されているか | ○/△/× |
| 苦情申立ての仕組みが提供されているか | ○/△/× |

## Step 4: リスク評価の統合とレポート生成

### リスクスコアリング

各チェック項目を以下の3段階で評価する：

- **○ 適合**: 要件を満たしている、または適切な対策が実装されている
- **△ 部分的**: 一部対応しているが不十分、または改善の余地がある
- **× 不適合**: 要件を満たしていない、または重大なリスクがある

### 深刻度分類

不適合（×）の項目を以下の深刻度で分類する：

| 深刻度 | 基準 | 対応 |
|--------|------|------|
| **Critical** | 子供の個人データが直接的に漏洩・悪用されるリスク。規制違反により法的制裁の対象となる可能性 | 即時対応が必要 |
| **High** | プライバシー保護が不十分で、累積的なリスクが生じる。規制要件への不適合 | 短期的な是正計画が必要 |
| **Medium** | ベストプラクティスに照らして改善が推奨される。法的リスクは限定的 | 中期的な改善計画に組み込む |
| **Low** | 軽微な改善余地。基本的な保護は確保されている | 次回改訂時に検討 |

## 制限事項と注意点

### フレームワークの限界

- この監査は設計レベル・アーキテクチャレベルの評価であり、実装の完全な検証には追加のテクニカルテストが必要
- 差分プライバシーやmachine unlearning等の技術は研究段階にあり、大規模モデルでの実用性には課題が残る
- LLMの記憶化リスクを完全に排除する技術は現時点で存在しない。ターゲットプロンプティングや抽出攻撃に対して、強力なノイズ追加はモデルの精度・有用性を低下させるトレードオフがある
- 規制は動的に進化しており、各管轄の最新要件を常に確認する必要がある
- 小規模な開発者や教育機関にとって、全推奨事項の実装は財務的・技術的に困難な場合がある

### 技術的に困難な領域

- **訓練済みモデルからの個人データの特定・削除**: LLMはデータを分散的なパラメータとして保持するため、特定のレコードの分離・除去が困難
- **間接的な開示の検出**: 「おばあちゃんの家の近くの公園」のような文脈的手がかりは、キーワードベースのフィルタでは捕捉困難
- **子供の同意能力の判定**: 特にPIPEDAのように固定の年齢閾値がない規制では、成熟度ベースの評価の実装が困難
- **サードパーティLLM APIを利用する場合の透明性確保**: モデル提供者のデータ処理慣行を完全に把握・制御することは難しい
