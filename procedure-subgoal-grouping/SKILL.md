# 手順のサブゴール・グルーピング

エージェントに「どう操作するか」を実演やログで渡すとき、ステップの並びを
そのまま渡すと、どの低レベル操作がひとまとまりの意味ある操作なのかが
エージェントから見えにくくなる。ステップを名前付きのサブゴールに区切って
階層化するだけで、エージェントが手順を正しく解釈・再現しやすくなる。

このスキルは、その「フラット → 階層」への変換手順と、どこまで作り込むべきかの
判断基準をまとめたもの。

## このスキルを使うタイミング

- 操作の実演記録（PbD録画、クリックログ、マクロ）をエージェントに渡す前に後処理するとき
- ワークフローや手順書を検索して取り出し、エージェントのコンテキストに差し込むシステムを設計するとき
- コーディングエージェントにサンプルコードや操作例を読ませて、そこからプランを生成させるとき
- 要するに「一連の手順をエージェントに読ませて真似させたい」あらゆる場面

逆に、タスクの指示自体が十分に精密で、エージェントが説明だけから正しい手順を
組み立てられる場合は、わざわざ階層化しても効果が出ない。コストをかける価値があるのは
指示が曖昧で、手順を説明から推論しにくいケースに絞られる（後述）。

## 前提知識: なぜ階層化が効くのか

押さえるべき経験則が4つある。

第一に、フォーマットは中身と独立して結果を左右する。同じ情報でも、
プレーンテキストかMarkdownかJSONか、といった見せ方の違いだけでLLMの精度は
大きく振れることが複数の先行研究で示されている。手順をエージェントに読ませる場面でも、
渡す情報が同じなら見せ方は関係ない、とは言えない。

第二に、効果が出るのは指示が曖昧なときに限られる。指示が曖昧だと、エージェントは
説明だけからは正しい手順を組み立てられず、実演がその欠けた手続き知識を補う。
ところがフラットな並びでは、どの低レベル操作（クリックやキー入力）が
ひとまとまりの操作を構成しているのかが埋もれてしまう。階層化はそれを
ラベル付きの塊として浮かび上がらせ、パターンを解釈可能にする。

第三に、効いているのはサブゴールの「区切り」そのものである。区切りに付随する
メタデータ（後述する状態注釈やパラメータ注釈）を足しても、計測可能な上積みは
確認されなかった。タイプタグだけをフラットなリストに付けても効果は出ない。
区切りと一緒になって初めて意味を持つ。

第四に、階層化は精度を下げるリスクがほぼない。元実験では、結果が変わったタスクは
すべて階層化側が勝ち、悪化したものは一つもなかった（勝敗6:0）。
つまり効果が出るかどうかは別として、入れておいて損をする失敗モードが見当たらない。
安全マージンとして機能する。

## 全体フレームワーク

```
入力: フラットなアクション列（生のステップリスト）
        │
        ▼
[Step 1] サブゴール境界でセグメント分割
        │
        ▼
[Step 2] 各サブゴールに「何をするか」のラベルを付与
        │
        ▼
[Step 3] 各サブゴールに機能タイプのタグを付与
        │
        ▼ （ここまでで効果の大部分が得られる）
        │
[Step 4] （任意）状態注釈・パラメータ注釈を追加
        │
        ▼
出力: ラベル付きサブゴールに階層化された手順
```

## 各ステップの詳細

### Step 1: サブゴール境界でセグメント分割

フラットなアクション列を、意味のあるまとまりに区切る。区切りの手がかりは主に3つ。

ナビゲーション境界で区切る。新しいUI領域へのクリックやページ遷移は、
「ここから別のフェーズが始まる」という合図になりやすい。

アクションタイプの遷移で区切る。たとえば移動系の操作の直後にデータ入力系の操作が
続くなら、そこがフェーズの切れ目である可能性が高い。

機能的なまとまりでクラスタリングする。連続するキー入力が一つの複合操作を
形づくっている場合（メニューを検索して項目を選ぶ一連のキーストロークなど）は、
バラさず一つの塊にまとめる。これをバラバラのステップとして並べると、
エージェントが個別の無関係な操作と誤認しやすい。

この分割は決定的（ルールベース）に行え、ユーザーへの追加質問は不要にできる。
完璧な分割を狙わなくてよい。ナビゲーション境界や、操作間の時間的な間隔だけを
手がかりにした軽量なヒューリスティックでも、効果の大半は拾える見込みがある。

### Step 2: サブゴールにラベルを付与

各まとまりに「何をするフェーズか」が一目で分かる名前を付ける。
たとえば「連絡先追加画面を開く」「情報を入力する」「保存する」のように、
人間が読んで操作の目的を理解できる粒度にする。このラベルが、
エージェントに「このステップ群は一つの原子的な操作だ」と伝え、
フェーズをまたいで操作を混ぜてしまうのを防ぐ。

### Step 3: 機能タイプのタグを付与

各サブゴールを3種類のいずれかに分類してタグ付けする。
これは「どのステップを字義通り再現し、どの値を状況に合わせて差し替えるか」を
エージェントに伝えるためのもの。

PROCESS は再利用可能なUI操作。クリック、スクロール、全選択など、
どのタスクでもそのまま使い回せる足場。

INPUT はユーザー固有のデータ入力。テキストの入力や値の設定など、
タスクごとに中身が変わる部分。

OUTPUT はナビゲーションやページ全体の状態変化。URLを開く、タブを切り替える、
スライドを新規作成するなど。

注意点として、このタイプタグは単独では効果がない。Step 1のサブゴール区切りと
セットで初めて意味を持つ。タグだけをフラットなリストに振っても精度は上がらない。

### Step 4（任意）: 状態注釈・パラメータ注釈

ここから先は、元実験では計測可能な改善が確認されなかった追加要素。
工数対効果を考えると省略してよいが、人間がデバッグするときや、
エージェントに中間状態を検証させたい特殊な用途では役立つことがある。

状態注釈は、各サブゴールに事前条件（実行前に成り立っているべき状態）と
事後条件（実行後に成り立つ状態）を添える。「太字を適用」なら
事前条件は「タイトルが選択されている」、事後条件は「タイトルが太字になっている」など。

パラメータ注釈は、タスク固有の値に明示的な印を付ける。`type("36")` を
不透明なリテラルとして見せるのではなく、`type(value={font_size})` のように
変数として注釈し、別途その値と型を列挙する。再利用可能な足場と
タスク固有のデータを分離するのが狙い。

繰り返すが、これらは無くても階層化の効果は得られる。最小構成で始めて、
必要が出てから足すのが合理的。

## 変換例

同じ手順を、フラット形式と階層形式で並べる。

フラット形式（ステップがすべて同じ階層に並ぶ）

```
1. CLICK  連絡先タブ
2. CLICK  新規追加ボタン
3. CLICK  名前フィールド
4. TYPE   "山田太郎"
5. CLICK  メールフィールド
6. TYPE   "yamada@example.com"
7. CLICK  保存ボタン
```

階層形式（サブゴールにグループ化）

```
GOAL: 新しい連絡先を追加して保存する

SUBGOAL 1: 連絡先追加画面を開く  [PROCESS]
  1. CLICK 連絡先タブ
  2. CLICK 新規追加ボタン

SUBGOAL 2: 連絡先情報を入力する  [INPUT]
  3. CLICK 名前フィールド
  4. TYPE  {name}          # PARAM
  5. CLICK メールフィールド
  6. TYPE  {email}         # PARAM

SUBGOAL 3: 保存する  [OUTPUT]
  7. CLICK 保存ボタン

PARAMETERS:
  - name:  "山田太郎"            (type: text)
  - email: "yamada@example.com"  (type: text)
```

記法そのものは本質ではない。重要なのは、連続する操作が
「画面を開く / 入力する / 保存する」という意味の単位に区切られ、
それぞれに名前が付いていること。インデント形式でもJSONでもMarkdownでも、
区切りと名前が伝われば効果は変わらない。

## どこまで作り込むべきか

元実験のアブレーション（要素を一つずつ外して効果を測る検証）が示した、
費用対効果の判断基準。

必須なのはサブゴールの区切りとラベルだけ。これが効果のほぼすべてを生む。
迷ったらここだけ実装すればよい。

タイプタグはセットで入れておくとよいが、それ単独では効果がない。
区切りがある前提でなら害もないので、付けておく価値はある。

状態注釈とパラメータ注釈は、精度向上という観点では計測可能な効果が
確認されなかった。最小構成では省略してよい。

つまり「とりあえずステップをラベル付きの塊に区切る」だけで、
重い作り込みをした完全版とほぼ同じ精度が出る、というのが実装方針の結論。

## チェックリスト

- [ ] フラットなステップ列を、意味のあるまとまりに区切ったか
- [ ] 区切りはナビゲーション境界・アクションタイプの遷移・機能的まとまりを手がかりにしたか
- [ ] 連続キー入力などの複合操作を、バラさず一つの塊にまとめたか
- [ ] 各サブゴールに、目的が一目で分かるラベルを付けたか
- [ ] （推奨）各サブゴールに機能タイプ（PROCESS / INPUT / OUTPUT）を振ったか
- [ ] タイプタグをサブゴール区切りなしで単独で使っていないか（それでは効かない）
- [ ] 状態注釈・パラメータ注釈は、本当に必要な用途があるときだけ足しているか
- [ ] そもそも対象タスクは「指示が曖昧で手順を推論しにくい」ケースか（精密な指示なら不要）

## 制限事項と注意点

検証は単一のLLMと単一のドメイン（プレゼンソフトのAPI操作）で行われたもの。
モデルが変われば構造化への反応も変わりうるため、別モデルや別アプリで使う際は
小規模に効果を確かめてから本適用するのが安全。

効果は指示が曖昧なタスクに集中する。指示が精密で、エージェントが説明だけから
正しい手順を組み立てられる場合は、階層化しても精度は変わらない。
全部の手順を無差別に階層化するより、曖昧さの残るケースを見極めて適用する方が合理的。

検証はAPIで表現できる操作に限定されている。ブラウザのDOM操作や視覚的な
ドラッグ操作など、API化しにくい操作主体のワークフローでは、
同じ効果が出るかは未検証。

## 発展的応用

この「手順を階層化する」原則は、実演記録の後処理だけにとどまらない。
手続き的なコンテキストをコード生成エージェントに供給するシステムなら、
どれも同じ設計問題（フラットで渡すか、構造化して渡すか）に直面する。

応用先として、ワークフローやマニュアルを検索してエージェントのコンテキストに
差し込むRAG的なシステム、コーディングエージェントにドキュメントやサンプルを
読ませてからプランを生成させる仕組み、過去の操作トラジェクトリを再利用可能な
手順として蓄積するエージェントメモリ、などが挙げられる。いずれの場合も、
取り出した手続き的コンテキストはフラットな並びのまま渡すより、
ラベル付きサブゴールに組織化してから渡す方が、エージェントが解釈しやすい。
