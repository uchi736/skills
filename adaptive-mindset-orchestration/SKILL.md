# 思考モード動的切替による推論フレームワーク

複雑な問題を解くとき、人間は「図で考える → 論理で詰める → 別解を探す → 計算で検証する」のように、思考モードを無意識に切り替えている。このスキルは、その認知プロセスをエージェント設計に落とし込み、1つの問題の中でステップごとに最適な考え方を選択・切替しながら推論を進める手法を定義する。

---

## このスキルを使うタイミング

以下のいずれかに該当する問題に有効：

- 1つの解法を最後まで通すと途中で行き詰まるリスクがある問題（数学コンテスト、複合科学問題など）
- 異なる認知能力を組み合わせる必要がある問題（図の読み取り＋論理＋計算など）
- 中間結果に応じてアプローチを変えるべき問題（最初の方針が間違っている可能性がある場合）

### 使わないほうがよい場面

- 単一の考え方で十分な単純タスク（単純な翻訳、要約、一問一答など）
- オーバーヘッドが許容できないリアルタイム応答

---

## 前提知識：なぜ単一モードでは不十分か

既存の推論手法の大半は、1つの考え方を最後まで変えずに使い続ける。段階的思考も、分岐探索も、コード生成も、それぞれ単独では強力だが「途中でやり方を変える」ことができない。最初にアプローチを選ぶ方式もあるが、中間結果を見て軌道修正する能力がない。

この制約が問題になるのは、複雑なタスクの各サブステップが異なる認知能力を要求するから。たとえば幾何学の証明は、図示→論理→別解探索→計算検証を1つの問題内で横断する。

もう1つの重要な知見：モードを切り替えること自体より、**モード間で渡す情報を適切に絞り込むこと**のほうが精度への影響が大きい。全履歴を無差別に渡すと、履歴が膨らむにつれて余計な情報がノイズとなり、正答率が大幅に下がる。

---

## 全体フレームワーク

### 3層分離アーキテクチャ

```
┌─────────────────────────────────────────┐
│  司令塔（メタ認知層）                      │
│  ・問題を分析し、どの順でどのモードを使うか計画  │
│  ・中間結果を受けて計画を修正               │
│  ・最終回答を出す                          │
└────────┬──────────────┬───────────────────┘
         │ 入口フィルター  │ 出口フィルター
         ▼              ▲
┌─────────────────────────────────────────┐
│  思考モード（実行層）                      │
│  ・具象化モード：図やイメージで考える        │
│  ・収束モード：情報を絞り込み論理で詰める     │
│  ・発散モード：複数の別ルートを同時に試す     │
│  ・計算モード：プログラムで正確に計算する     │
└─────────────────────────────────────────┘
```

### 基本ループ: 計画 → 実行 → 内省

1. **計画（Plan）**: 司令塔が問題を見て、使うモードの順序を決める
2. **実行（Call）**: 選ばれたモードがサブタスクを実行する
3. **内省（Internalize）**: 司令塔が結果を受け取り、気づきを言語化し、必要なら計画を修正する
4. 終了条件を満たすまで2-3を繰り返す
5. **回答出力**: 司令塔が最終回答をまとめる

## 各コンポーネントの詳細

### 1. 司令塔（メタ認知オーケストレータ）

#### 役割
「何を考えるか」ではなく「どう考えるか」を決める。自分では推論しない。

#### 動作の流れ

司令塔は以下の構造化された思考ステップを繰り返す：

- **認知判断**: 問題の性質を見極め、使うモードの順序を計画する。ここでは解くことをせず、計画だけを立てる
- **モード呼び出し**: 計画に基づき、特定のモードにサブタスクの指示を出す
- **結果受領**: モードの実行結果（出口フィルターで要約済み）を受け取る
- **気づきの言語化**: 結果から得られた気づきを短く言語化し、次のステップの判断材料にする
- **計画修正（必要時）**: 中間結果が想定と異なる場合、残りの計画を書き換える

#### 計画修正のトリガー

以下の状況を検知したら、司令塔は未実行の計画を破棄して再計画する：

- 得られた答えが選択肢にない、または明らかにおかしい
- 想定より効率的な解法が中間結果から示唆された
- 前提としていた条件が崩れた

#### 司令塔の設計原則

- 司令塔自身は「考える」ことをしない。あくまでモードに委任する
- 認知判断では解法の中身に踏み込まず、「どのモードをどの順で使うか」だけを決める
- 気づきの言語化は1〜2文に抑え、冗長にしない
- 呼び出し指示は具体的に書く（「この問題を解け」ではなく「この式を変形して条件を簡略化せよ」）

---

### 2. 思考モード

4つの思考モードはそれぞれ独立した文脈で動作し、専用の指示に従って実行する。

#### 具象化モード（Spatial）

目に見えない関係や構造を、視覚的な表現に落とし込んで考える。

**できること：**
- 画像生成が可能なモデル：テキストから図を生成、既存画像を加工・注釈付与、コードでグラフや図を生成
- 画像生成ができないモデル：テキストベースの図示（ASCII図、座標の列挙、構造の言語的記述）、コードによるグラフ生成（matplotlib等）、既存画像の言語的分析と構造記述

**使い分けの目安：**
- 空間的な関係を把握する必要がある（幾何、配置、経路）
- 抽象的な量を直感的に掴みたい（比率、スケール、プロポーション）
- 図に描くことで見落としていた構造が浮かび上がりそうな場面

**画像生成ができないモデルでの代替アプローチ：**
具象化モードの本質は「画像を作ること」ではなく「目に見える形で考えること」にある。テキストベースでも、座標を明示して構造を記述する、ASCII図で配置関係を示す、コードでグラフを描く、といった方法で視覚的思考の恩恵は得られる。ただし、画像生成モデルに比べて空間的直感の精度は落ちるため、このモードの使用頻度は下がり、収束モードや計算モードで補う場面が増える傾向になる。

#### 収束モード（Convergent）

情報を絞り込み、一本の筋道で深く考える。

**動作：**
- 与えられた指示と関連文脈に対して、1回の深い推論を行う
- 各ステップを既知の事実に基づかせる
- 情報が足りない場合はその旨を明示する
- 明確な結論に到達する

**使い分けの目安：**
- 論理的な導出が必要（条件の整理、定理の適用、因果関係の分析）
- 曖昧さの解消（「この条件はAとBどちらに解釈すべきか」）
- 複雑な情報の中から核心を抽出する場面

#### 発散モード（Divergent）

行き詰まりを打破するために、複数の異なるアプローチを同時に試す。

**動作（2段階）：**
1. **ルート生成**: 2〜5本の異なる解法ルートを生成する。各ルートは方法が異なること（表現を変えただけの同じ解法は不可）
2. **ルート探索**: 各ルートを独立に検討し、前提の妥当性・手順・限界を評価する

重要：ルートの最終選択は発散モード自身ではなく、司令塔が行う。発散モードは「選択肢を広げる」ことに専念し、「絞る」のは司令塔の仕事。

**使い分けの目安：**
- 最初のアプローチがうまくいかなかった
- 正解への道筋が複数ありそうで、どれが最善か不明
- 定石が通用しない非定型問題

**注意：** 桁数のざっくり見積もりなど、集中的な計算が主体のタスクでは、発散モードがかえって精度を下げることがある。発散は「行き詰まったとき」に発動するものであり、順調に進んでいるときに無理に使う必要はない。

#### 計算モード（Algorithmic）

プログラムを書いて正確に計算・検証する。

**動作（生成→実行→修復ループ）：**
1. 指示に基づいてプログラムを生成する
2. 実行する
3. エラーが出たら、エラー内容を見て修正し再実行する（最大2回まで）
4. それでも失敗したらエラー内容をそのまま司令塔に返す

**使い分けの目安：**
- 正確な数値計算が必要（暗算では信頼できない場面）
- 場合分けや全探索が必要（条件を満たす値をすべて列挙するなど）
- 結果の検証（他のモードで得た答えを計算で裏取りする）

---

### 3. 情報フィルター

モード間で情報を受け渡す際に、必要な情報だけを抽出・要約する仕組み。司令塔とは別のLLM呼び出し（または同一LLMへの別プロンプト）で実行する。

#### なぜ必要か

推論が進むと履歴が膨らみ、全履歴をそのまま渡すと：
- 思考モード側：関係ない過去の試行錯誤がノイズになり、サブタスクに集中できない
- 司令塔側：モードが出した長い途中経過をすべて読むことになり、要点が埋もれる

経験則として、情報フィルターなしだと処理量が大幅に増加し、正答率も顕著に下がる。モード切替の効果を最大化するには、このフィルター設計が不可欠。

#### 入口フィルター（モードへの入力）

司令塔がモードに出す「指示」を意味的なアンカーとして、履歴の中から以下を抽出する：

- **残すもの**: 数値、座標、過去のモードが出した結論、分析対象のテキストなどサブタスクに直接関係するデータ
- **要約するもの**: 過去の推論の流れは結論だけに圧縮する
- **除外するもの**: 元の問題文（モードは自分のサブタスクだけを見る）、関係ない過去の試行

画像を扱えるモデルの場合：指示に画像への言及があれば該当画像を注入し、純粋にテキストのタスクなら画像は渡さない。

#### 出口フィルター（司令塔への出力）

モードの実行結果から、司令塔が次の判断に必要な情報だけを抽出する：

- **残すもの**: 計算結果、発見されたパターン、結論、生成された図のパス
- **除外するもの**: 途中の導出過程、失敗した試行

## モード選択の経験則

以下はタスク種別ごとの典型的なモード使用パターン。あくまで出発点であり、司令塔は中間結果に応じてこれを逸脱してよい。

| タスクの性質 | よく使うモード | 典型的な流れ |
|---|---|---|
| 数学・証明 | 収束 + 計算 + 発散 | 収束で立式 → 計算で解く → 行き詰まったら発散 |
| コード生成 | 収束 + 計算 | 収束で方針 → 計算でコード生成・実行 |
| 科学問題（テキスト） | 収束 + 発散 | 収束で分析 → 必要に応じて発散で別仮説 |
| 図形・空間 | 具象化 + 収束 + 計算 | 具象化で構造把握 → 収束で関係分析 → 計算で検証 |
| 桁数の見積もり | 計算 + 具象化 | 計算中心。発散は不要なことが多い |

**重要な傾向：** 問題の過半数で2種類以上のモードが使われる。1モードだけで済む問題のほうが少数派。

## 動的リプランニングのパターン

### パターン1：答えが合わない

最初のアプローチで得た答えが選択肢にない、または明らかにおかしい場合。

対処：発散モードに切り替えて別の原理・解法を複数探索し、有望なものを計算モードで検証する。

### パターン2：より効率的な道の発見

最初は力任せの全探索を計画していたが、収束モードの途中で式を簡略化できることに気づいた場合。

対処：残りの計画（全探索）を破棄し、簡略化した式に基づく計算に切り替える。

### パターン3：前提の崩壊

問題の条件を誤解していたことが中間結果から判明した場合。

対処：収束モードで条件を再整理し、正しい前提に基づいて計画を再構築する。

## チェックリスト

### 実行前
- [ ] この問題は複数の考え方を切り替える必要があるか？（Noなら単一モードで十分）
- [ ] どのモードが候補になるか、ざっくり見当がついているか？
- [ ] 画像生成の可否を把握しているか？（不可なら具象化モードの代替方法を想定）

### 実行中
- [ ] 司令塔は自分で「考えて」いないか？（考えるのはモードの仕事）
- [ ] 各モード呼び出しの指示は具体的か？（「解け」ではなく「この式を変形せよ」）
- [ ] 情報フィルターが機能しているか？（全履歴をそのまま渡していないか）
- [ ] 中間結果に違和感があるとき、計画修正を検討しているか？
- [ ] 発散モードのルート選択を発散モード自身にさせていないか？（司令塔が選ぶ）

### 実行後
- [ ] 最終回答が中間結果と整合しているか？
- [ ] 使ったモード数は適切か？（単純な問題に4モードフル稼働は過剰）

## 制限事項と注意点

- **司令塔の判断精度はベースモデルの能力に依存する。** モード選択を誤ると、正しいモードを使った単一モード推論より悪くなることがある
- **全モードが同一モデルだと専門性に限界がある。** 理想的にはモードごとに得意分野の異なるモデルを割り当てるとよいが、現時点ではコストと複雑さのトレードオフ
- **発散モードの過剰使用に注意。** 集中的な計算が主体のタスクでは、発散がかえってノイズになる場合がある
- **情報フィルター自体にもLLM呼び出しコストがかかる。** 単純な問題ではフィルターのオーバーヘッドが恩恵を上回ることがある
- **ループ回数に上限を設けること。** 際限なくモード切替を繰り返すのを防ぐため、最大ステップ数（10程度が目安）を設定する

## 発展的応用

- **モードの追加**: 4種に限定する必要はない。たとえば「類推モード」（似た問題のパターンを適用する）や「批判モード」（自分の推論の穴を探す）を追加できる
- **専門モデルの割り当て**: 計算モードにはコード特化モデル、収束モードには推論特化モデル、というように異なるモデルを使う構成
- **ツールの拡張**: 計算モードに記号計算ソルバー、収束モードにウェブ検索、というようにモードごとに専用ツールを持たせる
- **司令塔の学習**: 現状はプロンプトだけで司令塔を動かしているが、過去の成功・失敗パターンから学習させればモード選択精度が上がる可能性がある
