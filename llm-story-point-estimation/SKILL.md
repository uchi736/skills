# LLMによるストーリーポイント推定

バックログアイテムのタイトルと説明文をLLMに入力し、
ストーリーポイントを自動推定する手法。
教師データなし（ゼロショット）でも教師あり深層学習を上回る精度が得られ、
少数の例示を加えるとさらに改善する。

## このスキルを使うタイミング

- 新規プロジェクト立ち上げ時に、過去データなしでストーリーポイントを推定したい
- プランニングポーカーの事前アンカーとして自動推定値がほしい
- 大量のバックログを短時間でトリアージしたい
- 少数のラベル付きデータしかないプロジェクトで推定精度を確保したい

## 前提知識

### なぜLLMが有効か

ストーリーポイントはプロジェクト固有の相対的な単位であり、
従来の教師あり学習は同一プロジェクトの大量のラベル付きデータを必要とした。
LLMは大規模コーパスでの事前学習により、
タスクの複雑さ・不確実性・実装規模を自然言語記述から読み取る能力を持っている。
このため、プロジェクト固有のデータがなくても妥当な推定を出せる。

### 3つの重要な経験則

1. **LLMは相対順序の推定が得意**：絶対値（ピアソン相関）より順位（スピアマン相関）の方が常に高い。ストーリーポイントは相対的な尺度であるため、これは実用上有利に働く。

2. **少数例示はスケール幅を網羅すると効果的**：頻出値から選ぶより、最小〜最大を均等にカバーする例を選ぶ方が精度が上がる。LLMにプロジェクト固有の「物差し」を教える役割を果たす。

3. **比較判断もフューショット例として使える**：「AとBどちらが大きいか」という比較ペアは、ストーリーポイント値そのものより取得コストが低い。フューショット例として使うと精度を向上させる。

## 全体フレームワーク

```
入力: バックログアイテム群（タイトル＋説明文）
  │
  ├─ Phase 1: ゼロショット推定（データ不要）
  │    → 全アイテムにストーリーポイントを付与
  │
  ├─ Phase 2: フューショット推定（5件のラベル付き例があるとき）
  │    ├─ 方式A: スケール分散型（推奨）
  │    └─ 方式B: 頻度代表型
  │
  └─ Phase 3: 比較判断によるフューショット（ペア比較データがあるとき）
       → ストーリーポイント値の代わりにペア比較結果を例示

出力: 各アイテムの推定ストーリーポイント
評価: ピアソン相関 ρ / スピアマン順位相関 rs
```

## 各フェーズの詳細

### Phase 1: ゼロショット推定

**いつ使うか**: ラベル付きデータが一切ないとき。新規プロジェクトのコールドスタートに最適。

**手順**:

1. バックログアイテムのタイトルと説明文を結合し、1つのテキストにする
2. 以下の構造のプロンプトでLLMに推定させる

プロンプトの設計原則：
- 役割設定：アジャイル見積もりの専門家として振る舞わせる
- 入力：アイテムのタイトル＋説明文をそのまま渡す
- 出力形式：JSON形式で整数値を指定する（パース安定性のため）

```
[役割定義: アジャイルストーリーポイント見積もりの専門家]
[入力: バックログアイテムのテキスト]
[出力指示: {"Story point": <整数>} の形式で回答]
```

**LLMパラメータ設定**:
- temperature: 0（再現性確保のため必須）
- max_tokens: 20程度（簡潔な回答を促す）
- リトライ: API不安定に備え最大3回の自動リトライを実装する

**レスポンス処理（重要）**:

LLMの出力は形式が安定しないため、段階的パース戦略が必要：

1. まずJSON解析を試みる
2. JSON解析に失敗した場合、正規表現で数値を抽出する（例: "points: X" パターン、または最初に現れる1〜20の整数）
3. Markdownの装飾（`**5**` 等）を事前に除去してからパースする

**期待できる性能**:
- 経験則として、ゼロショットでもピアソン相関 0.27〜0.40、スピアマン相関 0.31〜0.41 程度が期待できる
- 高性能なモデルであれば、80%のデータで訓練した教師あり深層学習と同等以上になることがある

---

### Phase 2: フューショット推定（ラベル付き例あり）

**いつ使うか**: プロジェクトから5件程度のラベル付きアイテムが得られるとき。

**例の選定方法（2方式）**:

#### 方式A: スケール分散型（推奨）

ストーリーポイントの全範囲をカバーする例を選ぶ。

手順:
1. プロジェクトのストーリーポイント範囲 [最小値, 最大値] を特定する
2. この範囲を5等分する
3. 各区間から1件ずつランダムにサンプルする

この方式が推奨される理由：LLMにプロジェクト固有のスケール感覚（低工数〜高工数の「物差し」）を教えるアンカーになる。偏りのない例が、絶対値の校正に寄与する。

#### 方式B: 頻度代表型

最頻出のストーリーポイント値から代表例を選ぶ。

手順:
1. 訓練データ中のストーリーポイント値を頻度順にソートする
2. 上位5つの値を特定する
3. 各値から1件ずつランダムにサンプルする

この方式はデータの実際の分布を反映するが、分布が偏っている場合（低工数アイテムが大多数など）、LLMに狭い範囲の例しか見せられない弱点がある。

**プロンプトの設計原則**:

```
[役割定義: アジャイルストーリーポイント見積もりの専門家]
[5件のフューショット例:
  例1: {アイテムテキスト} → ストーリーポイント: {値}
  例2: ...
  ...
  例5: ...]
[指示: 上記の例を参考に、以下のアイテムのストーリーポイントを推定せよ]
[入力: 推定対象のアイテムテキスト]
[出力指示: {"Story point": <整数>} の形式で回答]
```

**期待される改善幅**:
- スケール分散型はゼロショットに比べ、ピアソン相関で平均 0.05〜0.10 程度の改善が期待できる
- ゼロショット精度が低かったモデルほど改善幅が大きい傾向がある
- 頻度代表型もゼロショットより改善するが、スケール分散型には劣る傾向がある

---

### Phase 3: 比較判断によるフューショット

**いつ使うか**: ストーリーポイントの絶対値は持っていないが、「AとBどちらが重いか」というペア比較データがあるとき。ペア比較は人間にとって認知負荷が低く、取得コストが小さい。

**比較判断データの作り方**:

ストーリーポイントが既知の場合:
- ペア (A, B) について、Aのポイント > Bなら「Aが大きい」、逆なら「Bが大きい」とラベルする
- 同値のペアは除外する

ストーリーポイントが未知の場合:
- 開発者に「AとBどちらが実装工数が大きいか」を判断してもらう
- ストーリーポイント値を付けてもらうより認知負荷が低い

**プロンプトの設計原則**:

```
[役割定義: アジャイルストーリーポイント見積もりの専門家]
[5件の比較ペア例:
  ペア1: アイテムA vs アイテムB → 判定: AはBより{大きい/小さい}
  ペア2: ...
  ...
  ペア5: ...]
[指示: 上記の比較例を参考に、以下のアイテムのストーリーポイントを推定せよ]
[入力: 推定対象のアイテムテキスト]
[出力指示: {"Story point": <整数>} の形式で回答]
```

**使い分けの判断基準**:
- 高性能モデルを使う場合 → Phase 2（スケール分散型）の方が高精度
- 軽量・低コストモデルを使う場合 → Phase 3（比較判断）が同等以上の精度になることがある
- ラベル取得コストを最小化したい場合 → Phase 3が実用的（比較判断は人間にとって容易）

---

### 補足: 比較判断の直接予測について

LLMに「AとBどちらが重いか」を直接聞くこともできるが、経験則として、ストーリーポイントを個別に推定してから差を取る方が正確。人間は比較判断の方が得意だが、LLMは逆で、内部的に数値表現を経由して判断していると考えられる。

したがって、ペアの大小を知りたい場合でも、Phase 1 または Phase 2 で個別推定し、推定値の差から比較結果を導出することを推奨する。

## チェックリスト

### 必須事項

- [ ] バックログアイテムのテキストにタイトルと説明文の両方が含まれているか
- [ ] LLMのtemperatureを0に設定しているか
- [ ] レスポンスのパースにJSON解析 → 正規表現フォールバックの2段階を実装しているか
- [ ] Markdownの装飾除去（サニタイズ）を行っているか
- [ ] APIリトライ機構を実装しているか

### 推奨事項

- [ ] フューショット例を使う場合、スケール分散型の選定を優先しているか
- [ ] 5件の例示で十分か確認したか（5件は費用対効果の良い実証済みの数）
- [ ] 推定結果をピアソン相関とスピアマン順位相関の両方で評価しているか
- [ ] プロジェクト固有のストーリーポイント範囲（例: 1〜13, 1〜100）を把握しているか

## 制限事項と注意点

1. **プロジェクト固有性**: ストーリーポイントはプロジェクトごとにスケールが異なる。ゼロショットではLLMが独自のスケール感で推定するため、絶対値のズレが大きくなりやすい。順位の整合性は保たれやすい。

2. **プロンプト依存性**: プロンプトの書き方が推定結果に影響する。できるだけシンプルな指示を使い、過度に複雑なプロンプト設計は避ける方が安定する。

3. **モデル間差**: モデルによって得意・不得意が異なる。特に軽量モデルはゼロショットで絶対値のスケール校正に失敗しやすいが、順位の推定は比較的安定する。

4. **統計的検証の不足**: 限られた回数の実験に基づく経験則であり、大規模な統計検定は行われていない。結果の傾向として参考にし、自プロジェクトでの検証を推奨する。

5. **Chain-of-Thought未検証**: 段階的推論（CoT）プロンプティングの効果は未検証。複雑なアイテムではCoTが有効な可能性があるが、実証データはない。

## 発展的応用

- **コメント・受入基準の追加入力**: タイトルと説明文だけでなく、開発者コメントや受入基準を入力に加えることで精度向上が見込める
- **人間とLLMの協調ワークフロー**: 少数のペア比較を人間が行い、その結果をフューショット例として軽量モデルに渡す「ハイブリッド推定」が実用的
- **教師ありファインチューニング**: 十分なデータが蓄積されたら、LLMをプロジェクト固有データで微調整することでさらなる精度向上が期待できる
- **CoTプロンプティング**: 推定の根拠を段階的に出力させることで、推定結果の説明可能性を高められる可能性がある
