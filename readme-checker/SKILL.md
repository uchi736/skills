# README品質チェッカー

READMEファイルのスタイル（書式・文法）と内容（構成・明瞭さ・網羅性）の
両面を体系的に検証し、具体的な改善提案を行うスキル。

## このスキルを使うタイミング

- READMEの品質レビューを依頼された
- READMEの改善点を洗い出したい
- 新しいREADMEを書く際のガイドラインが欲しい
- プロジェクトのドキュメント品質を底上げしたい
- プルリクエスト前のREADMEチェックを行いたい

## 前提知識

READMEの品質は「書式が正しいか」だけでは測れない。
良いREADMEには以下の多次元的な品質が必要になる：

1. **構造的完全性**: 必要なセクションが揃っているか
2. **内容の明瞭さ**: 対象読者にとって理解しやすいか
3. **技術的正確性**: リンク、コード例、手順が正しいか
4. **アクセシビリティ**: 画像のalt属性、見出し階層など
5. **包摂性**: 差別的・排他的な表現がないか

また、何が「良いREADME」かはプロジェクトの種類によって異なる。
ソフトウェアライブラリ、データセット、インタラクティブシステム、
研究プロトタイプではそれぞれ重視すべきセクションが変わる。

---

## 全体フロー

```
1. プロジェクト種別の判定
   ↓
2. 適用ルールセット（プリセット）の選択
   ↓
3. 各ルールの実行（3カテゴリ × 複数ルール）
   ↓
4. 結果の集約と優先度付け
   ↓
5. 改善提案の提示
   ↓
6. （任意）修正版READMEの生成
```

---

## Step 1: プロジェクト種別の判定

READMEの内容またはユーザーの説明から、以下のどれに該当するか判定する。

| 種別 | 特徴 | 追加で重視するセクション |
|------|------|------------------------|
| ソフトウェアライブラリ | npm/pip等で配布、APIがある | クイックスタート、API参照、インストール手順 |
| インタラクティブシステム | GUI/Webアプリがある | デモリンク、スクリーンショット、操作説明 |
| データセットリポジトリ | データの公開・共有が目的 | データ説明、引用形式、ライセンス、倫理的考慮 |
| 研究プロトタイプ | 論文の実装、再現用 | 再現手順、依存環境、論文引用 |
| 社内ツール/スクリプト | チーム内利用 | セットアップ手順、担当者、更新履歴 |

判定できない場合はユーザーに確認する。

## Step 2: ルールの実行

以下の3カテゴリに分けてチェックを行う。
各ルールは **重要度（Error / Warning / Info）** を持つ。

### カテゴリA: 構造チェック（プログラム的に検証可能）

これらは機械的に判定できるルール。READMEのテキストを直接分析する。

#### A-1: セクション網羅性チェック [Error]
プロジェクト種別に応じた必須セクションが存在するか確認する。

**全種別共通の必須セクション:**
- プロジェクト概要（何をするものか）
- インストール/セットアップ手順
- 基本的な使い方

**ソフトウェアライブラリの追加必須:**
- クイックスタート（5分以内に動かせる手順）
- API/機能のリファレンス（または外部ドキュメントへのリンク）
- ライセンス

**インタラクティブシステムの追加必須:**
- デモリンクまたはスクリーンショット
- 動作要件（ブラウザ、OS等）

**データセットの追加必須:**
- データの説明（カラム定義、サイズ等）
- 引用形式（BibTeX推奨）
- ライセンスとデータ利用条件

**研究プロトタイプの追加必須:**
- 論文の引用情報
- 再現手順（環境構築から結果出力まで）
- 依存ライブラリとバージョン

**判定方法:**
見出し（H1〜H3）のテキストと本文の内容から、
各必須セクションに相当する記述があるか判定する。
見出し名が完全一致しなくても、内容が含まれていれば合格とする。

#### A-2: 目次チェック [Warning]
READMEが長い場合（H2見出しが4つ以上、または200行以上）、
目次（Table of Contents）が存在するか確認する。

#### A-3: リンク検証 [Error]
README内のリンクについて以下をチェックする：
- 内部リンク（アンカーリンク）が対応する見出しを持つか
- 外部リンクのURL形式が正しいか（実際のアクセスは不要）
- 相対パスリンクのファイルが存在しそうか（パス構造の妥当性）

#### A-4: コードブロック整合性 [Warning]
- コードブロックに言語指定があるか（```の後にpython等）
- コードブロックが閉じられているか
- インラインコードとブロックコードの使い分けが適切か

#### A-5: 見出し階層 [Warning]
- H1が1つだけか（プロジェクト名）
- 見出しレベルが飛んでいないか（H1→H3のようなスキップ）
- 見出しの書式が統一されているか

#### A-6: 画像のalt属性 [Warning]
マークダウン画像記法 `![alt](url)` のalt部分が空でないか確認する。

#### A-7: リスト書式の統一 [Info]
箇条書きの記号（`-` / `*` / `+`）がファイル内で統一されているか。

#### A-8: 末尾改行 [Info]
ファイルが改行で終わっているか（POSIX準拠）。

---

### カテゴリB: 内容品質チェック（LLM判定）

これらは文章の意味内容に踏み込むルールで、LLMの判定能力を活用する。
各ルールについて、該当セクションのテキストを抽出し、
明確な判定基準に基づいてPass/Failを判定する。

#### B-1: 専門用語の説明 [Warning]
対象読者にとって馴染みのない可能性がある専門用語・略語に、
説明や補足が付いているか確認する。

**判定基準:**
- 初出の専門用語に括弧書きの説明、脚注、または用語集へのリンクがあるか
- 対象読者の想定知識レベルに対して過度に専門的な表現がないか
- 略語が初出時に展開されているか（例: CLI (Command Line Interface)）

#### B-2: 手順の完全性 [Error]
インストール・セットアップ手順が、前提条件から完了まで
漏れなく記述されているか確認する。

**判定基準:**
- 前提条件（必要なソフトウェア、バージョン等）が明記されているか
- 手順が順番に並んでいるか（番号付きリスト推奨）
- 各ステップの結果（成功時の出力等）が示されているか
- OS/環境による差異が注記されているか

#### B-3: トーンの中立性 [Warning]
文章が客観的で中立的なトーンで書かれているか確認する。

**判定基準:**
- 過度な宣伝表現がないか（「最高の」「革命的な」等）
- 事実と意見が区別されているか
- 他のプロジェクトを貶める表現がないか

#### B-4: 包摂的な言語 [Error]
差別的、排他的、または配慮に欠ける表現がないか確認する。

**チェック対象の例:**
- master/slave → primary/replica, main/secondary
- whitelist/blacklist → allowlist/denylist
- sanity check → confidence check, validation
- dummy → placeholder, sample
- ジェンダーバイアスのある表現（he/him を汎用的に使う等）
- 能力主義的表現（cripple, blind spot 等の比喩的使用）

#### B-5: 冒頭の明瞭さ [Warning]
READMEの最初の段落を読んだだけで、以下が理解できるか確認する：
- このプロジェクトは何をするものか
- 誰のためのものか
- なぜ使うべきか（既存のものとの差異）

#### B-6: コード例の妥当性 [Warning]
READMEに含まれるコード例について：
- 構文的に正しそうか（明らかな構文エラーがないか）
- コピーペーストでそのまま動きそうか
- プレースホルダー（YOUR_API_KEY等）が明示されているか
- 出力例が付いているか（推奨）

---

### カテゴリC: プロジェクト種別固有チェック

Step 1で判定した種別に応じて追加で実行するルール。

#### ソフトウェアライブラリ向け
- **C-L1: バッジの存在** [Info]: CI/CD、バージョン、ライセンス等のバッジがあるか
- **C-L2: パッケージマネージャ情報** [Warning]: npm/pip等でのインストールコマンドが記載されているか
- **C-L3: バージョン情報** [Warning]: 最新バージョンや変更履歴への参照があるか

#### インタラクティブシステム向け
- **C-I1: 視覚的デモ** [Error]: スクリーンショット、GIF、またはデモリンクがあるか
- **C-I2: 操作手順** [Warning]: 基本的な操作フローが説明されているか

#### データセット向け
- **C-D1: データスキーマ** [Error]: データの構造（カラム名、型、説明）が記載されているか
- **C-D2: データ取得方法** [Error]: データのダウンロード方法が明記されているか
- **C-D3: 倫理的考慮** [Warning]: プライバシー、同意、バイアスへの言及があるか

#### 研究プロトタイプ向け
- **C-R1: 再現性情報** [Error]: 環境構築からの完全な再現手順があるか
- **C-R2: 論文引用** [Error]: 対応する論文のBibTeXまたは引用情報があるか

## Step 3: 結果の集約と提示

### 出力フォーマット

チェック結果は以下の形式で提示する：

```
## README品質チェック結果

**プロジェクト種別**: ソフトウェアライブラリ
**総合スコア**: 26/32ルール合格

### ❌ Error（修正必須）
1. [A-1] セクション網羅性: 「ライセンス」セクションがありません
   → MIT等のライセンスを明記してください
2. [B-4] 包摂的な言語: L.42 "master branch" 
   → "main branch" に変更を推奨

### ⚠️ Warning（改善推奨）
3. [A-2] 目次: H2見出しが6つありますが目次がありません
   → 目次の追加を検討してください
4. [B-1] 専門用語: "SSR", "hydration" が説明なしで使われています
   → 初出時に簡単な説明を追加してください

### ℹ️ Info（参考情報）
5. [A-7] リスト書式: `-` と `*` が混在しています
   → どちらかに統一すると読みやすくなります
```

### 優先度の付け方

1. **Error** を最優先で提示する（プロジェクトの利用を妨げる問題）
2. **Warning** を次に提示する（品質を著しく下げる問題）
3. **Info** は最後に提示する（あると良い改善点）

各カテゴリ内では、影響範囲が大きいものを先に並べる。

---

## Step 4: 改善提案

各問題に対して、以下を含む改善提案を行う：

1. **何が問題か**: 具体的な箇所と理由
2. **どう直すか**: 修正例または修正の方針
3. **なぜ直すべきか**: ユーザー体験や採用率への影響

ユーザーが望む場合は、修正版のREADME全体を生成する。
ただし、自動修正はあくまで提案であり、最終判断はユーザーに委ねる。

---

## 実行時の注意事項

### LLM判定ルール（カテゴリB）の制約
- LLMの判定は非決定的であり、誤判定の可能性がある
- 判断に迷う場合は「要確認」として提示し、断定しない
- ルールの適用が文脈的に不適切な場合はスキップする
  （例：個人のメモ用READMEに包摂性チェックを厳格に適用しない）

### コンテキストに応じた柔軟性
- ユーザーが「ざっくり見て」と言った場合はErrorのみ報告する
- ユーザーが「徹底的にチェックして」と言った場合は全ルールを実行する
- 特定のカテゴリだけチェックしてほしい場合はそれに従う

### ユーザーのエージェンシーを尊重する
- チェック結果はあくまで提案であり、強制ではない
- ユーザーが意図的にルールに反している場合もあることを念頭に置く
- 「このルールは今回は無視したい」という判断を尊重する

## チェックリスト（スキル実行者向け）

スキル実行時に以下を確認する：

- [ ] プロジェクト種別を判定したか
- [ ] 全3カテゴリのルールを実行したか（ユーザーの指定がない限り）
- [ ] 結果をError > Warning > Infoの順で整理したか
- [ ] 各問題に具体的な改善提案を付けたか
- [ ] 過度に断定的な表現を避けたか
- [ ] ユーザーの意図や文脈を考慮したか

### 本スキルが論文・コードから取り入れた設計要素

- **3カテゴリのルール分離**: LintMeは21種のオペレーター（extract, count,
  threshold, evaluateUsingLLM, customCode等）をYAMLパイプラインで
  組み合わせる設計。本スキルではこの考え方を「カテゴリA: 構造チェック
  （プログラム的）」「カテゴリB: 内容品質チェック（LLM判定）」
  「カテゴリC: 種別固有チェック」の3層に翻訳した
- **プリセット（種別別ルールセット）**: LintMeはソフトウェアライブラリ、
  インタラクティブシステム、データセットリポジトリの3プリセットを提供。
  本スキルではこれに研究プロトタイプと社内ツールを加えた5種別に拡張した
- **Error/Warning/Infoの重要度分け**: LintMeのlinting ladder
  （checkable→blamable→adjustable→fixable）に基づく段階的フィードバック
- **ユーザーエージェンシーの尊重**: LintMeの設計目標DGagencyに基づき、
  チェック結果を強制せず提案として提示する方針を踏襲した
- **LLM単体との差分**: 論文のLLM比較実験で、LintMeが平均25.4件の問題を
  検出したのに対しLLM単体では9.6件（自由形式）/7.25件（ルール提示）に
  とどまった知見から、「構造化されたルール単位の判定」設計を採用した
