# corpus2skill：検索しないRAG

コーパスを階層ファイルに事前コンパイルし、LLMエージェントに
ナビゲートさせる方式のRAG設計スキル。オフラインのコンパイルと
サービング時のエージェント設計の両方を扱う。

## 使うタイミング

- エンタープライズのナレッジベース検索を構築
- 文書数が1,000〜100,000件、更新頻度が月次以下
- 誤答コストが高く、1クエリ0.1〜0.2ドルが許容される
- 複数トピックにまたがるクエリへの対応が必要
- ベクトルDB運用を避けたい、または根拠の追跡可能性が求められる

避けるケース：高頻度・低単価FAQ、リアルタイム更新コーパス、
数百件以下の小規模、即時応答必須のUX。

## 設計思想

クエリ時に賢く探すのではなく、コンパイル時に歩きやすく整える。
階層がファイルシステムとして可視化されると、エージェントは
「まだ見ていない領域」を認識でき、バックトラックや
クロスブランチ合成が可能になる。従来の上位k件検索では
LLMは今見えている断片しか知らない。

## Phase A：オフラインコンパイル

### Stage 1: 埋め込み
文書に内容ハッシュIDを付与し、埋め込みモデルでベクトル化する
（1024次元程度、CPU動作する軽量モデルで可）。

### Stage 2: 反復的階層クラスタリング
1. ベクトルをK-Meansでクラスタリング（L2正規化推奨）
2. 各クラスタをLLMが要約
3. 要約を再埋め込みして次ラウンドの入力にする
4. トップレベル数がK以下になるまで繰り返す

**重要なパラメータ判断**：

| 枝分かれ数 p | 効果 |
|---|---|
| p=5（狭く深い） | 精度わずかに上、コスト+8% |
| **p=10（推奨）** | バランス型 |
| p=20（広く浅い） | 精度が大きく崩れる、避ける |

**失敗の約6割がトップレベル選択ミスで起きる**ため、狭く深い構造が有利。
Kは7前後（Skills APIの8スキル制約に収まる値）。

### Stage 3: ラベリング
非葉ノードに2〜5語のケバブケースラベルを生成（50文字以内）。
エージェントはラベルだけでルーティングする場面が多い。
具体的な製品名・機能名を含め、抽象的な「〜システム」は避ける。

### Stage 4: 物理化

```
compiled-skills/
├── skill-00-[label]/
│   ├── SKILL.md            ← トップ要約+サブグループ一覧
│   └── group-00-[label]/
│       ├── INDEX.md        ← サブ要約
│       └── group-00/INDEX.md  ← 葉：文書ID一覧
documents.json              ← 全文書本文（IDで参照）
```

**原則：ナビゲーションと証拠を分離**
- SKILL.md/INDEX.mdは要約と文書IDのみ（2KB未満を目安）
- 文書本文は別ファイルに隔離
- エージェントが多数の候補を安価に俯瞰できる

YAMLフロントマターに `name, description, level, num_documents` を記載。
本文は Overview + Contents（子要素一覧）+ 次アクション指示で構成。

### 要約プロンプト設計

**下位レベル**：最大15文書×600文字を入力。
トピック領域・答える質問の種類・頻出用語の3点を含む2〜3文を生成。

**上位レベル**：最大20件の子要約×300文字を入力。
ドメイン・トピック範囲・答えられるクエリ種別の3点を含む。

**原則**：「何が書いてあるか」ではなく
「エージェントがどこに行くかを判断するための情報」として書かせる。

### Skills API制約

8スキル/200ファイル/30MBの上限がある。
200ファイルを超える場合、葉INDEX.mdを親に統合する
**コンパクトモード**を使う。ファイル数を最大80%削減しても
ナビゲーション情報は失われず、探索ターン数はむしろ減る。

## Phase B：サービング設計

### ツール構成：2ツールに必ず分ける

1. **コード実行ツール**：SKILL.md/INDEX.mdを閲覧する
2. **`get_document(doc_id)`**：文書ストアから本文を取得する

ナビゲーション（どこを見るか）と証拠取得（何を引用するか）は
コスト構造が違う。2ツールに分けることで、エージェントは
「候補を俯瞰してから本文を取る」戦略を取れる。
1ツールに統合したり本文を常時プリロードすると
コストが跳ね、探索の自由度も下がる。

### システムプロンプトの必須要素

**A. ハード制約**
- 全ての事実的主張は `get_document` で取得した文書に紐付ける
- **SKILL.md/INDEX.mdはナビゲーション補助。ここから回答を生成しない**
- 手順・URL・価格・仕様を捏造しない
- 情報が見つからなければ「見つからなかった」と正直に答える

**重要**：要約ファイルからの回答生成は明示的に禁止しないとLLMが流用する。
要約は抽象的なのでFactualityが下がる。

**B. 4ステップのナビゲーション指示**
1. 関連性が高いスキル1〜2個のSKILL.mdを読む
2. 関連サブグループのINDEX.mdに降りる
3. 葉INDEX.mdから関連文書IDを選ぶ
4. `get_document` で本文を取得してから回答する

**C. 回答フォーマット制約**
- 最初の文で直接回答（前置きなし）
- 事実質問：1〜3文、80語まで
- 手順質問：番号付きリスト、150語まで
- プレーンテキスト、太字や見出しなし
- 複数案を並べない、1アプローチに絞る

### 2つのナビゲーションパターンを許容する

- **直接降下**：単一トピックで1本の枝をまっすぐ降りる
- **クロスブランチ探索**：複数トピックで同じスキル内の別サブグループを横断

「1本で完結させろ」と制約しすぎるとクロスブランチが死ぬ。
「最初の文書で答えが不完全なら別サブグループも見て良い」という
バランスが有効。

### パラメータ推奨値

**サービングLLM**：

| モデル層 | 1クエリコスト | 特性 |
|---|---|---|
| 最上位モデル | 約0.17ドル | F1・Factuality最高 |
| 軽量モデル | 約0.09ドル | F1は8%低下、Context Recallは上昇傾向 |

**経験則**：階層の質が精度の大部分を決める。サービング側のモデル性能より、
コンパイル済み階層の質が重要。コスト優先なら軽量モデルで十分。

**最大ラウンド数**：5で精度飽和。10を推奨、20にしても伸びない。

**コスト内訳**（最上位モデル実測）：
入力トークン約53,000（ナビゲーションファイル再読込が主）、
出力約750、合計0.17ドル。入力支配型のため、プロンプトキャッシュが
効く設計なら大幅に安くなる。

## チェックリスト

### コンパイル時
- [ ] p=10, K=7でスタート。精度不足なら p=5 へ
- [ ] 各階層の要約にトピック/質問タイプ/キーワードが入っているか
- [ ] トップレベル要約に具体的な製品名・機能名が入っているか
- [ ] SKILL.md/INDEX.mdがSkills API制約に収まっているか
- [ ] 文書本文が別ファイルに分離されているか

### サービングデプロイ時
- [ ] システムプロンプトに4つのハード制約が入っているか
- [ ] 2ツール構成になっているか
- [ ] 回答フォーマット制約が明示されているか

### 運用時
- [ ] Factualityが目標水準を維持しているか
- [ ] 平均ターン数が2〜3ターンに収まっているか
- [ ] 品質劣化時は失敗パターンを特定
  （トップレベルミス→再コンパイル、合成エラー→プロンプト強化）

## 制限事項

- **単一パス割当**：横断的文書は1ブランチにしか置けない。要約文で関連性を明記し、クロスブランチ探索を促す
- **インクリメンタル更新不可**：月次等の定期再コンパイル前提
- **入力トークン支配**：ナビゲーションファイル再読込が累積する構造的制約。プロンプトキャッシュで軽減
- **要約流用リスク**：SKILL.md/INDEX.mdからの回答生成を明示的に禁止する
- **コンパイル品質は要約LLMに依存**：サービング側は軽量LLMで可、コンパイル側は高品質モデルを使う

## 発展的応用

- セッション内キャッシュで連続クエリを高速化
- ハイブリッド運用（単純クエリは従来検索、複雑クエリのみこの方式）
- 失敗ログ→コンパイル改善（トップレベル粒度や同義語補強にフィードバック）
- ナビゲーション痕跡のUI可視化（コンプライアンス用途で根拠追跡）

## 参考実装値

6,221文書・p=10・K=7で実測：
3レベル階層、6スキル、665ファイル、文書ストア13MB、
32CPUサーバーで6.5分、LLM費用5〜10ドル。
