# 敵対的テスト強化（Adversarial Test Strengthening）

テスト生成AIとバグ注入AIの役割を交互に演じ、
テストスイートの「バグ検出力」を反復的に鍛えるワークフロー。

## なぜこのアプローチが有効か

カバレッジが高くてもバグ検出力が低いテストは珍しくない。
コードを「通過」するだけで「検証」していないテストが原因。
人工バグ（ミュータント）を仕掛けてテストが見破れるか試すと、
この盲点が可視化される。

研究知見として、カバレッジがほぼ横ばい（88%→95%）でも
バグ検出率はほぼ倍増（35%→68%）するケースが報告されている。
反復回数は3〜5ラウンドで大きな改善が得られ、
それ以降は収穫逓減の傾向がある。

---

## 前提条件

- 対象コードと、それに対する既存テストスイート（または生成する初期テスト）がある
- テストランナーが実行可能な環境（pytest, jest, vitest, JUnit等）
- テストが実行でき、pass/failの判定ができること

---

## 全体フロー

```
[対象コード] → ① 初期テスト生成
                    ↓
              ② ミュータント生成（3〜5体）
                    ↓
              ③ テスト実行 → 生存ミュータント特定
                    ↓
              ④ テスト強化（生存者を狙い撃ち）
                    ↓
              ⑤ 新ミュータント生成（弱点を突く）
                    ↓
              ③に戻る（2〜4ラウンド繰り返し）
                    ↓
              ⑥ 最終テスト強化 → 完了
```

**重要**: 最後は必ずテスト強化（④）で終える。
ミュータント生成で終わると、未検証の弱点が放置される。

---

## Phase 1: 初期テスト生成

既存テストがなければ生成する。既存テストがあればスキップ。

### やること

1. 対象コードの責務を分析する
   - 正常系：主要な入出力パターン
   - 異常系：null/undefined、空配列、境界値、型違い
   - エッジケース：ゼロ除算、最大値付近、空文字列
2. 各パターンに対してテストを書く
3. テストを実行して全パスすることを確認

### 判断基準

- 関数の引数の各型・値域を最低1つはカバーする
- 条件分岐（if/else, switch）の各枝を最低1つはカバーする
- 完璧を目指さなくてよい（Phase 3以降で鍛えるため）

---

## Phase 2: ミュータント生成

対象コードに小さな人工バグを仕掛ける。

### ミュータントの作り方

**1行だけ変更する。** これが最も重要なルール。
複数行を変えると原因の切り分けが困難になり、
コンパイル/構文エラーのリスクも上がる。

#### 推奨する変異パターン（優先度順）

| パターン | 例 | 狙い |
|---------|---|------|
| 演算子すり替え | `a + b` → `a - b` | 計算ロジックの検証 |
| 比較の反転 | `x > 0` → `x >= 0`, `x < 0` | 境界条件の検証 |
| 戻り値の改変 | `return result` → `return null` | 戻り値の検証 |
| 関数呼び出しの変更 | `Math.max(a,b)` → `Math.min(a,b)` | 意味的な正しさの検証 |
| 定数の変更 | `timeout = 3000` → `timeout = 0` | マジックナンバーの検証 |
| 条件の除去 | `if (x != null)` → `if (true)` | ガード条件の検証 |
| 早期リターンの除去 | `if (err) return;` → 行削除 | エラーハンドリングの検証 |

#### 避けるべき変異

- コメントや空白だけの変更（意味がない）
- 構文エラーになる変更（テスト不能）
- 同じ行に対する同じパターンの重複（冗長）

### 生成数の目安

- 対象コードの行数が〜30行：3体
- 30〜100行：5体
- 100行超：5〜8体（ただし重要なロジックに集中）

### 実装方法

ミュータントは個別のファイルとして作成するのではなく、
**差分の一覧**として管理する。

```
ミュータント #1:
  場所: src/calculator.ts:15
  元コード:   return a + b;
  変異コード: return a - b;
  狙い: 加算が正しく検証されているか

ミュータント #2:
  場所: src/calculator.ts:22
  元コード:   if (divisor !== 0) {
  変異コード: if (divisor !== 1) {
  狙い: ゼロ除算ガードが検証されているか
```

## Phase 3: ミュータント検証

各ミュータントに対してテストスイートを実行し、
「生存者」（テストに見破られなかったミュータント）を特定する。

### 手順

1. 対象コードの該当行をミュータントの変異コードに一時的に書き換える
2. テストスイートを実行する
3. 結果を記録する：
   - **撃墜（killed）**: 1つ以上のテストがfailした → このミュータントは検出された
   - **生存（survived）**: 全テストがpassした → テストに盲点がある
   - **無効（invalid）**: 構文エラーやタイムアウト → 集計から除外
4. 元のコードに戻す
5. 全ミュータントについて繰り返す

### ミューテーションスコアの計算

```
ミューテーションスコア = 撃墜数 / (撃墜数 + 生存数)
```

目安：
- 0.8以上: 良好。テストスイートに一定の検出力がある
- 0.5〜0.8: 改善の余地あり。Phase 4で強化する
- 0.5未満: テストの質に大きな問題がある。重点的に強化する

### 生存ミュータントの分析

生存者が出たら、**なぜ見破れなかったか**を分析する。
典型的な原因：

- そもそもその行を実行するテストがない（カバレッジの穴）
- 行は実行しているが、結果をアサーションしていない（弱いアサーション）
- アサーションはあるが、変異後の値でもたまたまpassする（不十分な入力値）

この分析結果がPhase 4の入力になる。

---

## Phase 4: テスト強化

生存ミュータントの情報をもとに、ピンポイントでテストを追加・改良する。

### やること

生存ミュータントごとに、以下の思考プロセスを踏む：

1. **変異の内容を自然言語で理解する**
   「この変異は○○を△△にすり替えている」
2. **見破るにはどんな入力が必要か考える**
   「○○と△△で結果が変わるような入力は何か」
3. **その入力に対する期待値を明確にする**
   「入力Xを与えたとき、元コードならY、変異コードならZになるはず」
4. **テストを書く**
   入力X → 期待値Yをアサーション

### 例

```
生存ミュータント:
  元:   return Math.max(a, b);
  変異: return Math.min(a, b);

思考:
  max→minの違いが出るのは a ≠ b のとき。
  a=10, b=3 なら、元は10を返し、変異は3を返す。

追加テスト:
  test('should return the larger value', () => {
    expect(getMax(10, 3)).toBe(10);  // min(10,3)=3 → fail → 撃墜
  });
```

### 注意点

- 生存者1体につきテスト1〜2件が目安。大量に書かない
- 新しいテストは元コードに対してpassすることを必ず確認する
- 既存テストの修正で対応できるなら、新規追加より修正を優先する

---

## Phase 5: 新ミュータント生成（2ラウンド目以降）

テストが強化されたので、今度は新しい弱点を探す。

### 2つの方向から攻める

#### 方向A: カバレッジの穴を突く

テストが通過していないコード領域があれば、そこを優先的に変異させる。
カバレッジ情報が取得可能な場合（pytest-cov, istanbul等）は活用する。
取得できない場合は、テストケースから推測する（どの分岐が未テストか）。

#### 方向B: 生存ミュータントの周辺を突く

Phase 3で生存したミュータントがあった行の周辺は、
テストが手薄な可能性が高い。同じ行に対して別パターンの変異を試みる。

**例**: Phase 3で `a + b → a - b` が生存していた場合、
Phase 5では同じ行に `a + b → a * b` や `a + b → b` を試みる。

### 避けるべきこと

- Phase 2で既に撃墜されたのと同じ変異を再生成しない
- 前ラウンドで無効判定されたパターンを繰り返さない

---

## ループの制御

### 推奨ラウンド数

- **通常: 3ラウンド**（Phase 2〜5 を3回転）
  費用対効果が最も高い。大半の改善はここで得られる。
- **重要なコード: 5ラウンド**
  決済処理、認証、データ整合性チェック等。
- **1ラウンドで十分なケース**
  ミューテーションスコアが初回から0.8以上の場合。

### 各ラウンドで記録すること

```
=== ラウンド N ===
ミュータント数: X体（新規Y体 + 前回からの持越Z体）
撃墜: A体
生存: B体
無効: C体
ミューテーションスコア: A / (A + B) = XX%
追加テスト: D件
主な発見: [生存ミュータントが示した弱点の要約]
```

### 終了条件

以下のいずれかを満たしたら終了する：
- ミューテーションスコアが0.8以上に到達
- 2ラウンド連続でスコアの改善が5%未満
- 指定ラウンド数に到達
- ユーザーが「もう十分」と判断

---

## 最終仕上げ

ループ完了後、以下を行う：

1. **全テストを元コードに対して実行** → 全passを確認
2. **不要なテストの整理** → 同じ変異を狙った重複テストがあれば統合
3. **テスト名・コメントの整理** → ミュータント参照の一時的なコメントを除去
4. **レポート出力**（任意）

```
=== 敵対的テスト強化レポート ===
対象: src/calculator.ts
ラウンド数: 3
初期テスト数: 8 → 最終テスト数: 14（+6）
ミューテーションスコア: 0.40 → 0.85（+112%）
生成ミュータント総数: 15体
  撃墜: 11体 / 生存: 2体 / 無効: 2体
主な改善点:
  - 境界値テスト3件追加（ゼロ除算、負数、最大値）
  - 戻り値のアサーション強化2件
  - エラーハンドリング検証1件追加
```

## 言語別の実行Tips

### Python (pytest)

```bash
# テスト実行
pytest tests/ -v --tb=short

# カバレッジ取得（可能な場合）
pytest tests/ --cov=src --cov-report=term-missing

# ミュータント適用→テスト→復元の一連は
# sed やPythonスクリプトで自動化可能だが、
# Claude Codeではstr_replaceツールで1行ずつ書き換えるのが確実
```

### TypeScript/JavaScript (jest/vitest)

```bash
# テスト実行
npx jest --verbose
# or
npx vitest run

# カバレッジ
npx jest --coverage
npx vitest run --coverage
```

### Java (JUnit)

```bash
# Maven
mvn test -pl module-name

# Gradle
./gradlew test
```

## よくある落とし穴

### ミュータントが全部「無効」になる
→ 変異が構文エラーを起こしている。1行変更の制約を厳守し、
  変異後のコードが文法的に正しいことを目視確認する。

### ミュータントが全部「撃墜」される
→ テストが既に強い（良いこと）。ただし、変異パターンが
  単純すぎる可能性もある。関数呼び出しの変更や条件除去など、
  より意味的な変異を試みる。

### テストが元コードでもfailする
→ テスト自体にバグがある。または対象コードに本物のバグがある。
  敵対的ループを一旦止めて、テストまたはコードを修正する。

### 何ラウンドやってもスコアが上がらない
→ 生存ミュータントが「等価ミュータント」（元コードと挙動が同じ変異）
  の可能性がある。たとえば `x * 1` を `x * 2` に変えても、
  xが常に0なら結果は同じ。こうした生存者はスコア計算から除外してよい。
