# スキル組み合わせリスク検査 (compositional-skill-check)

複数のスキルをエージェントの同一セッションに読み込むと、エージェントはそれら
すべての能力の **和集合** を継承する。各スキルが単体では安全でも、和集合が
「ファイル読み取り ∧ 外向き通信」のような禁止された能力結合を満たせば、
データ持ち出しなどの危険な動作面が開く。このスキルは、スキルを発動する直前に
その組み合わせをチェックし、個別スキャンでは構造的に見逃す合成リスクを検出する。

---

## このスキルを使うタイミング

- 複数のスキルを同時に発動・インストールする直前に、組み合わせの安全性を確認したい
- 既に有効なスキル集合に新しいスキルを1つ追加するとき、新たな危険面が開かないか見たい
- スキルレジストリのレビューで、ペア単位の能力結合リスクを根拠付きで把握したい

**前提となる脅威モデル：** エージェントが単一セッション内で全インストール済み
スキルの能力を呼び出せる「統合・非隔離ランタイム」を最悪ケースとして想定する。
ランタイム側のサンドボックス・能力スコープ・確認プロンプトがあれば実リスクは下がるが、
それらは本チェックの **補完** であって代替ではない（後述の制限事項を参照）。

---

## 前提知識：なぜ「組み合わせ」を見るのか

### 個別スキャンの構造的盲点

スキルを1つずつ検査する従来手法は、合成リスクを **定義上** 見逃す。

```
スキルA（リサーチ補助）  能力 = {ファイル読み取り}        → 単体スキャン: PASS
スキルB（API連携）       能力 = {外向き通信}             → 単体スキャン: PASS
────────────────────────────────────────────────
両方を発動した集合 S     能力 = {ファイル読み取り, 外向き通信}
                        {ファイル読み取り ∧ 外向き通信} ⊆ Cap(S)  → 禁止パターン充足: FLAG
```

ポリシー（禁止パターン）は同じで、変わるのは **検査対象** だけ
（スキル単体 → 発動するスキル集合）。エージェントが継承するのは集合の能力和集合
なので、セキュリティ上の正しい単位は「パッケージ」ではなく
「同一セッションで利用可能なスキル集合」である。

### 経験則：フラグは「判定」ではなく「トリアージ信号」

この検査は **再現率重視（high recall）** に設計されている。出典研究の大規模測定では、
個別安全なペアの約22%が能力和集合で何らかの禁止パターンを満たした（生のフラグ率）が、
人手監査を通すと **フラグされた (ペア×パターン) のうち本物の合成リスクはおよそ5件に1件**
にとどまった。つまり生のフラグ率は「スキャナの再現率上限」であり、出力は
**人による確認を要する候補** として扱う。それでも、単一レジストリ内で個別スキャンが
構造的に見逃す本物のリスクが数千〜万件規模で残るため、チェック自体の価値は大きい。

### 最重要の注意：これは「能力面」の検査であって「実行されるか」の検査ではない

本チェックが測るのは **危険な能力面が到達可能になるか**（ingredients が揃うか）であり、
エージェントが実際にその危険な動作を **実行するか** ではない。出典研究の動的検証では、
同一の危険要求に対して挙動はホストモデルの気質で大きく分かれた
（あるモデルはダウンロード→実行の連鎖を完遂、別のモデルはダウンロードのみ、別のモデルは拒否）。
さらに、要求を固定してインストール済みスキルだけを変える対照実験では、
**スキルが何もインストールされていないときに最も応諾率が高かった**。

この知見の含意：

- BLOCK / WARN は「危険な能力面が新たに開いた」を意味し、「悪用が起きる」を意味しない
- 実際に実行されるかはモデルの整合性（alignment）・プロンプト・ランタイムが決める
- したがって本チェックは、モデル整合性とランタイム隔離と **三層で併用** する
  （静的合成チェック ＋ モデル整合性 ＋ ランタイムポリシー）

## 能力モデル（8 capabilities）

各スキルを次の8能力の部分集合として表現する。略号は本スキル内で一貫して使う。

| 略号 | 能力 | 典型的な兆候（コード／文章） |
|------|------|------|
| FR | ファイル読み取り (file read) | `open(...,'r')`, `read`, `glob`, ファイルを読む |
| FW | ファイル書き込み (file write) | `open(...,'w')`, `write`, 保存, ファイル作成 |
| NO | 外向き通信 (network out) | `https?://`, `requests`, `curl`/`wget`, `socket.connect`, 送信, アップロード, API呼び出し |
| NI | 内向き通信 (network in) | `listen`, `bind`, `http.server`, サーバを立てる |
| ER | 環境変数読み取り (env read) | `os.environ`, `getenv`, `process.env`, 環境変数 |
| PS | プロセス起動 (process spawn) | `subprocess`, `os.system`, `exec`, `Popen`, シェル実行 |
| CA | 認証情報アクセス (credential access) | `api_key`, `token`, `password`, `oauth`, 認証情報 |
| SI | システム情報 (system info) | `platform`, `uname`, `whoami`, ホスト名取得 |

能力は **コードパターン** と **自然言語パターン** のどちらかが一致すれば発火する
（再現率重視）。この方針により誤検出が増えるため、抽出時の否定処理が重要（後述）。

---

## 禁止パターン（10パターン）と深刻度

各パターンは「結合された能力プロファイル」に対する **能力の連言（AND）** で定義される。
深刻度とアクションの対応、および「フラグが本物だった監査上の実証率の目安」を併記する。
実証率は、フラグを受け取ったあとに **どれを優先して確認すべきか** の重み付けに使う。

| # | パターン | 能力結合 | 深刻度 | 実証率の目安 |
|---|----------|----------|--------|------|
| 1 | データ持ち出し (Data Exfiltration) | FR ∧ NO | HIGH | 約10% |
| 2 | 認証情報窃取 (Credential Theft) | CA ∧ NO | CRITICAL | 約25% |
| 3 | Lethal Trifecta | CA ∧ FR ∧ NO | CRITICAL | 約25% |
| 4 | 権限昇格 (Privilege Escalation) | ER ∧ PS | HIGH | 約45% |
| 5 | リバースシェル (Reverse Shell) | NI ∧ PS | CRITICAL | 約5% |
| 6 | 永続バックドア (Persistent Backdoor) | FW ∧ PS | HIGH | 約25% |
| 7 | 横展開 (Lateral Movement) | CA ∧ NO ∧ PS | CRITICAL | 約10% |
| 8 | 環境変数持ち出し (Environment Exfiltration) | ER ∧ NO | HIGH | 約25% |
| 9 | システム偵察持ち出し (System Recon. Exfil.) | SI ∧ NO | MEDIUM | 約15% |
| 10 | ドロッパー (Dropper) | NO ∧ FW ∧ PS | CRITICAL | 約10% |

**パターンは互いに素ではない。** 長い連言（Lethal Trifecta, 横展開, ドロッパー）は
短い連言に **包含** される（例：Lethal Trifecta を満たすペアは必ずデータ持ち出しと
認証情報窃取も満たす）。能力上は短いパターンが立てば長いパターンの追加情報は無い。
ただし **運用上の物語が異なる**（ドロッパーは「ダウンロード→書き込み→実行」の連鎖を表す）
ため、人への報告では包含されるパターンも名前で出す。一方、件数を足し合わせて
「リスク総数」とは数えない（独立した寄与ではない）。

## チェックの全体フロー

入力：発動しようとするスキル群（各スキルの SKILL.md テキスト＋同梱コード）と、
任意で「発動前にすでに有効な能力ベースライン」。
出力：集合レベルの判定（Mode 1）と、ペアレベルの根拠（Mode 2）。

```
[各スキル] ──能力抽出（regex＋文章、否定ウィンドウ適用）──▶ Cap(s)
                                                          │
        ┌─────────────────────────────────────────────────┘
        ▼
Mode 1: 集合レベルゲート ── 新規に開くパターンのみ判定 ──▶ BLOCK / WARN / ALLOW
        ▼
Mode 2: ペアレベル証拠 ── どのペアがどの能力でどのパターンを立てたか ──▶ レビュー用レポート
```

### Mode 1：集合レベルゲート（高速・同期的）

新しい能力面 **だけ** を見るのが install-time チェックの肝。すでに持っていた危険面を
毎回再警告しても意味がないので、**和集合では立つが、ベースライン単独では立たなかった**
パターンのみをフラグする。

手順：

1. ベースライン能力 `U_base` を求める（既存有効スキルの能力和集合。ゼロから複数スキルを
   同時発動する場合は `U_base = ∅`）。
2. 発動後の総能力 `U_all = U_base ∪ (発動する各スキルの能力)` を求める。
3. **新規に立つ違反** `V = { f ∈ 禁止パターン | f ⊆ U_all かつ f ⊄ U_base }` を求める。
4. 判定：
   - `V` に **CRITICAL** が1つでもあれば → **BLOCK**（発動を止め、根拠を提示）
   - `V` が空でないが CRITICAL を含まない → **WARN**（注意喚起し、利用者に判断を委ねる）
   - `V` が空 → **ALLOW**

`f ⊆ U_all` は「パターンの全能力が総能力に含まれる」、`f ⊄ U_base` は
「ベースライン単独ではそのパターンを満たさなかった（=この発動で新たに開いた）」を意味する。

> 設計判断：CRITICAL を BLOCK、それ以外を WARN にする粒度は、実証率の目安と組み合わせて
> 微調整してよい。例えば「データ持ち出し（HIGH／実証率約10%）」は誤検出が多いので
> WARN に留め、「ドロッパー（CRITICAL／実行連鎖）」は実証率が低めでも連鎖の危険性ゆえ
> BLOCK にする、という現行の割り当ては妥当な初期値。運用ログを見て調整する。

### Mode 2：ペアレベル証拠レポート（レビュー用）

人が最終判断するために、**どのスキル対が、どの能力を持ち寄って、どのパターンを
新たに立てたか** を列挙する。各ペア `(s_a, s_b)` について：

- 和集合 `Cap(s_a) ∪ Cap(s_b)` がパターン `f` を満たし、かつ `s_a` 単独でも `s_b` 単独でも
  満たさない場合のみ報告する（＝合成によってのみ生じるリスク）。
- 報告項目：対象ペア、立ったパターン、各能力をどちらのスキルが提供したか、
  根拠スニペット（一致したファイル名・一致した語・前後40字程度の抜粋）。

ペア限定は実務上の既定だが、**3つ以上のスキルの組み合わせでのみ完成するパターン**
（3番目のスキルにしか無い能力が連言を完成させる場合）も存在する。Mode 1 は集合全体の
和集合を見るのでこれを捕捉するが、Mode 2 のペア根拠だけ見ると見落とすことがある。
大きな集合では Mode 1（集合全体）の結果を主、Mode 2 を根拠補助として併読する。

## 能力抽出の実務：誤検出を減らす

抽出器の出力は **再現率重視のスキャナ出力であって真実ではない**。フラグの精度は
ここの作り込みで大きく変わる。出典研究の信頼性診断から、効く順に：

### 1. 否定ウィンドウ（最大の誤検出低減策）

能力は文章中の言及でも発火するため、「APIキー不要」「no credentials needed」
「外部送信はしない」のような **否定文脈** が偽陽性を生む。一致箇所の前後約40字に
否定語があれば、その一致は無効化する。

- 否定語の例（日英）：不要／なし／しない／せず／禁止／持たない／no／not／without／never／n't
- 出典研究では、根拠の **約9%** が40字の否定ウィンドウ内に入っていた。
  特に否定率が高い能力：プロセス起動（約26%）、環境変数読み取り（約23%）、
  認証情報アクセス（約18%）。これらの能力ほど否定処理を丁寧に行う。

### 2. net_out（外向き通信）を最優先で正しく判定する

ほとんどの禁止パターンは外向き通信を経由する。出典研究で、外向き通信の検出器を
外すと合成候補率が **約92%崩落** した（次点のファイル読み取りで約44%）。
残り6能力はそれぞれ寄与1ポイント未満。つまり：

- 1つだけ能力を厳密に検証できるなら、**外向き通信** を選ぶ。
- 外向き通信は検出が最も安定し（人手ラベルとの一致が高く）、否定率も低い（約2%）。
- 逆に言えば、外向き通信を持つスキルとファイル/認証/環境を持つスキルの共存は、
  ほぼ必ず何らかの持ち出しパターンを立てる。これがデータ持ち出しが最多
  （候補の約7割）になる構造的理由。

### 3. コード兆候と文章兆候を分けて記録する

各一致を「コードでの一致か、文章（散文）での一致か」で区別して根拠に残す。
文章のみの一致は **ドキュメントの記述であって実装ではない** 可能性が高く、
人手監査で偽陽性（regex 誤発火）と判定されやすい。

## 結果の解釈：どのフラグを信じるか

フラグの確からしさはパターンによって大きく異なる。**最も多いフラグが最も弱い証拠**
という非直感的な事実に注意する。

- **権限昇格（ER ∧ PS）は実証率が最も高い（約45%）。** フラグされたら優先的に精査する。
- **データ持ち出し（FR ∧ NO）は最多だが実証率は最低クラス（約10%）。**
  単独のデータ持ち出しフラグは「ファイル系スキルと通信系スキルが共存しているだけ」で
  あることが多く、それ自体は弱い証拠。BLOCK ではなく WARN 寄りに扱う。
- **リバースシェル（NI ∧ PS）は実証率約5%。** 内向き通信の検出が偽陽性を出しやすい。
- 認証情報窃取・環境変数持ち出し・永続バックドア・Lethal Trifecta は中程度（約25%）。

判断の指針：**深刻度（被害の大きさ）× 実証率（本物らしさ）** の両軸で優先順位を付ける。
深刻度だけで機械的に止めると誤検出疲れを起こし、実証率だけで見ると重大な連鎖を見逃す。

## チェックリスト

実装・運用時に確認すべき必須事項：

- [ ] 8能力それぞれにコード兆候と文章兆候の両方の検出規則を用意したか
- [ ] すべての一致に対して否定ウィンドウ（±約40字）を適用したか
- [ ] 外向き通信の検出規則を特に厚く作り込んだか（load-bearing capability）
- [ ] Mode 1 が「新規に開くパターンのみ」を判定しているか（ベースライン差分ロジック）
- [ ] CRITICAL → BLOCK、その他の違反 → WARN、違反なし → ALLOW になっているか
- [ ] Mode 2 が「合成によってのみ生じる」ペアのみ報告しているか
       （各スキル単独でも立つパターンは除外）
- [ ] 根拠（ファイル名・一致語・前後抜粋・コード/文章の別）を各フラグに添えているか
- [ ] 包含されるパターン（Dropper / Lethal Trifecta / 横展開）を件数加算せず、
       名前での報告に留めているか
- [ ] 出力に「これは能力面の検査であり実行可否の検査ではない」旨を明記しているか

## 制限事項と注意点

正直に記述すべき限界（いずれも出典研究が自認しているもの）：

1. **静的過大近似。** 能力の和集合は実行を意味しない。本チェックは危険な連鎖の
   「材料が揃うか」を数えるのであって、ホストモデル・プロンプト・ワークフローが
   それを実際のツール呼び出し連鎖に組み立てるかは別問題。最も悪用されやすい条件下でも、
   実行まで進むかはモデルの気質に強く依存した。

2. **抽出ノイズ。** regex は文章にも発火し、否定語が偽陽性を生む。人手ラベルとの
   一致は全体として低い（slight 水準）。生のフラグ率は上限であり、人手監査で
   大きく下がる。根拠スニペットを必ず添え、人が確認できるようにする。

3. **ペア限定が既定。** 主にペアを解析する。3つ以上の集合は新たな候補
   （第3のスキルにしかない能力で連言が完成）を生むことも、冗長になることもある。
   Mode 1 で集合全体の和集合を見ることで一定は捕捉するが、大きな k の体系的解析は
   今後の課題。

4. **タキソノミー限定の完全性。** この10パターンの範囲内、かつ能力ラベルが正しい
   という条件下でのみ「漏れなく検出」と言える。新種の攻撃合成や能力の誤ラベルには
   完全性を主張しない。

5. **補完であって代替ではない。** per-skill スキャン、ランタイムサンドボックス、
   プロンプトインジェクション対策を置き換えるものではない。発動時の追加レイヤとして使う。

6. **実現はモデル依存。** 同じ危険要求でもホストモデルにより応諾〜拒否まで大きく割れ、
   要求を固定してスキルだけ変える対照ではスキル無しが最も応諾率が高かった。
   よって本チェックの BLOCK/WARN は「能力面が開いた」事実であり、悪用の予測ではない。

## 発展的応用

- **学習型の合成モニタへ。** 固定 regex は厳密かつ高速（1インストールあたり1ミリ秒未満）
  だが regex が取りこぼすものには盲目。SKILL.md の散文を読む／根拠を要約する／
  モデルが出したツール呼び出し計画を検査する、小型ローカルモデルを足すと網羅性が上がる
  （発動時ゲートとして使うため、フロンティアモデル呼び出しではなく安価なローカル部品に保つ）。
- **能力伝播の強制（ランタイム層）。** 値に能力予算を付与し、ツール連鎖に沿って積を取って
  「合成は権限を減衰させることはあっても拡大させない」を保証する仕組みは、本静的チェックが
  測る合成エスカレーションに直接対応するランタイム側の実装例。
- **レジストリ／ランタイムのポリシー。** 支配的な軸（ファイルアクセス＋ネットワーク送出）
  に対しては、能力スコープの明示要求、ファイル読み取りスキルから無関係な通信スキルへ
  セッション内データが渡る際の確認要求、明示許可なしの文脈共有の禁止などが有効。
- **k>2 の合成検査・複数アンカーの動的検証** への拡張。

本スキルは、エージェントスキル生態系における **合成セキュリティ測定** の研究
（ClawHub スナップショット上での 1,520 スキル・約21万ペアの大規模ペアワイズ
能力和集合解析、人手較正、行動ベース検証ハーネスからなる枠組み）に基づく。
能力タキソノミー・10禁止パターン・install-time チェッカ（2モード）の発想を、
実行可能なチェック手順として再構成した。能力結合の定義・深刻度割当・実証率の目安は
同研究の測定結果を判断基準として抽象化したものであり、文章・図表・プロンプトの逐語的
再現は行っていない。合成セキュリティの系譜（能力ハイパーグラフ上の非合成性、
情報フロー、最小権限、Android のアプリ間権限漏洩解析）も同研究の位置づけに沿う。

> 注意：付属スクリプトの能力検出規則は **再現率重視の出発点** であり、ground truth では
> ない。運用環境に合わせて規則を増補し、否定語リストを言語・ドメインに合わせて
> 調整すること。

## 付属スクリプト

`scripts/compositional_check.py` に、上記 Mode 1 / Mode 2 の参照実装を置く。
能力抽出（コード＋文章 regex、否定ウィンドウ）、10パターン照合、集合レベルゲート、
ペアレベル証拠レポートを含む。SKILL.md 単体でも手法は完結するが、スクリプトは
実際に発動前チェックを回すための実行用部品。
