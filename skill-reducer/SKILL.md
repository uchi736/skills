# Skill Reducer

SkillReducer 論文（arXiv:2603.29919）の方法論を、対話可能な範囲で実装したスキル。既存のスキルを「ルーティング層」と「本文層」に分けて、それぞれ別の戦略で削る。

## 前提：どこまでできて、どこからできないか

論文の完全パイプラインには、Claude Code CLI を実際に叩いてスキルが発火するか確認する工程と、エージェントに自動でタスクを解かせて採点する工程が含まれる。Claude.ai 環境ではこれらは直接実行できない。よってこのスキルでは次のように代替する。

- ルーティング検証 → 「似たスキルとの紛らわしさ」を Claude 自身が脳内シミュレートし、削った節がルーティングを壊すかを判定する
- タスク採点 → 圧縮前後の本文を読み比べ、操作的な概念が抜けていないかをチェックする「忠実性ゲート」のみを実行する
- 自動の自己修正ループ → ユーザーに「この圧縮で気になる点は？」と確認し、必要なら戻す

完全自動ではないことを最初にユーザーに伝えること。

## 入力の受け取り方

ユーザーが対象スキルを示す方法は次のいずれか。

1. SKILL.md と参照ファイル群をアップロードする
2. スキルのフォルダパスを指定する
3. SKILL.md の中身をチャットに貼り付ける

参照ファイル（同じフォルダ内の `examples.md`、`templates.md`、その他 `.md`）が存在する場合は、本文と一緒に必ず読み込むこと。本文と参照の重複除去はステージ2の重要工程なので、参照だけ見落とすと圧縮率が大きく落ちる。

## 全体ワークフロー

ステージ1（説明文）→ ステージ2（本文）→ ステージ2（参照ファイル）→ 品質ゲート → ユーザー確認 → 出力。

各ステージの結果は必ずユーザーに見せ、進めてよいか確認を取ること。途中で大きく削った場合は「ここを削りました、戻したい箇所はありますか」と聞く。

---

## ステージ1：説明文の最小化

### 既存の説明文がある場合

説明文を「意味のかたまり（節）」に分解する。節とは、ルーティングに効く独立した意味の単位のこと。文単位だと粗すぎ、単語単位だと細かすぎる。たとえば「JWT 認証、OAuth 2.0 対応、トークンリフレッシュ機能」は3つの節に分かれる。

分解したら、各節について次を自問する。

- この節を削ったとき、似た名前の別スキルと取り違える可能性が上がるか
- この節は他の節から推測できる冗長な情報か（例：機能リストから推測できるトリガー語列挙）
- この節は固有名詞・ライブラリ名・API 名など、他では代替できない識別子を含むか

固有名詞や識別子を含む節は原則残す。他の節から推測できる冗長な節、長大なトリガー語の列挙、使用例の羅列は削除候補。

### 削除候補をユーザーに提示する

削除する前に、削除候補と「なぜ削れると判断したか」をユーザーに見せる。論文のデルタデバッギングは自動だが、ここでは人間に最終判定を委ねる。

### 説明文が空または極端に短い場合（40 トークン未満が目安）

本文から次の3要素を抽出して新しい説明文を生成する。各要素 20〜40 トークンが目安。

- 主要機能：このスキルが何をするか（動詞ベース）
- 起動条件：どんなユーザー発話・文脈で呼ぶべきか
- 固有識別子：ライブラリ名、API 名、方法論名、独自用語

生成した説明文には、論文と同じく「やや押しの強い」トリガー指示を含めること。Claude にはスキルを過小利用する傾向があるため、「〜と言ったときは必ず使う」「〜の話題が出たら使う」といった明示的な指示が効く。

---

## ステージ2：本文の階層化

### ステップ1：本文を5分類する

本文を段落単位（または論理的なまとまり単位）に区切り、それぞれを次のどれかに分類する。

- **コアルール（core rule）**：エージェントが従わなければならない操作指示。「〜すること」「〜してはならない」「次の手順で進める」など、行動を直接規定するもの
- **背景（background）**：理由、動機、前提知識の説明。読まなくても動けるが、理解を助ける
- **例（example）**：入出力ペア、コードスニペット、典型的なやりとりの例示
- **テンプレート（template）**：コピペで使うひな形、設定ファイルの雛形、定型句
- **冗長（redundant）**：他の段落と内容が重複している、または前後と矛盾せず削っても情報損失がない段落

判断に迷う段落は安全側に倒してコアルールに分類する。論文のフォールバック方針と同じ。

### ステップ2：分類結果を可視化する

分類した結果を、ユーザーに表形式または箇条書きで見せる。「この段落をコアルールに分類しました、本当にこれは行動指示として必須ですか」と聞ける状態にする。特に「例」と「テンプレ」に分類したものは、暗黙のうちに行動規範になっているケースがある（論文で言う example-as-specification 問題）。ここを誤ると圧縮後にエージェントの挙動が崩れるので、ユーザー確認を必ず挟む。

### ステップ3：型ごとに圧縮する

| 分類 | 処理 | 行き先 |
|---|---|---|
| コアルール | 意味の近いものを統合し、簡潔な命令文に書き換える。元より必ず短くする | SKILL.md 本文 |
| 背景 | 数値、しきい値、API エンドポイントなど固有の事実は保持したまま、説明を短い段落に要約する | `references/background.md` |
| 例 | 概念ごとにグループ化し、概念ごとに最も代表的な1例だけ残す。コメントや決まり文句は削る | `references/examples.md` |
| テンプレート | 概念ごとに1つだけ残す | `references/templates.md` |
| 冗長 | 削除 | なし |

### ステップ4：参照ファイルの重複除去

元のスキルに参照ファイル（`examples.md` 等）がすでに存在する場合：

1. 各参照ファイルと本文の内容を突き合わせ、本文側または新しい `references/` 側にすでに含まれている内容を参照から削除する
2. 削除後に 30 トークン未満まで縮んだ参照ファイルは丸ごと捨てる
3. 残った参照ファイルそれぞれに、SKILL.md 本文から「いつ読むべきか」を示すメモを書く

### ステップ5：参照ファイルへのルーティングメモ

SKILL.md 本文の末尾に、参照ファイルへの誘導セクションを置く。エージェントが中身を読まなくても、いつ読むべきか判断できるようにする。書き方の例：

```markdown
## 追加の参照

必要に応じて以下を読み込むこと。

- `references/examples.md` — 具体的なペルソナ別メッセージの書き方を見たいとき
- `references/templates.md` — HubSpot の設定ファイルを書く必要があるとき
- `references/background.md` — ポジショニング方法論の背景を理解したいとき
```

「いつ読むか」は条件節で書く。トピックキーワードを3〜5個併記すると、エージェントが自分のタスクと照合しやすくなる。

---

## 品質ゲート（忠実性チェック）

圧縮版が完成したら、元の本文と圧縮後の本文＋参照ファイル群を突き合わせ、次を確認する。

- 元のコアルールに含まれていた操作概念が、圧縮後のコアまたは参照のどこかに必ず存在するか
- 数値、しきい値、API 名、固有名詞などの一意な事実が消えていないか
- 元の本文で「〜してはならない」「絶対に〜」と強調されていた制約が、圧縮後も同じ強さで残っているか

抜けが見つかった場合、その項目はコアルールに昇格させて圧縮前の文言のまま戻す（論文の自己修正ループに相当）。圧縮率より忠実性を優先する。

ユーザーには「忠実性チェックの結果、次の項目をコアに戻しました」と必ず報告する。

---

## 出力形式

最終的に次を出力する。

1. **新しい SKILL.md** — 圧縮された説明文と本文、参照ファイルへの誘導セクション付き
2. **`references/` ディレクトリ** — `background.md`、`examples.md`、`templates.md`、および元から存在し重複除去された参照ファイル
3. **圧縮レポート（Markdown）** — 次を含む
   - 説明文：元のトークン数 → 圧縮後トークン数（削減率）
   - 本文：元のトークン数 → 圧縮後トークン数（削減率）
   - 参照込み合計：元 → 圧縮後
   - 段落分類の内訳（コアルール何件、背景何件…）
   - 忠実性ゲートで戻した項目があればそのリスト
   - ユーザーが確認すべき注意点

トークン数の概算には文字数ベースの近似を使ってよい（日本語なら概ね 1 文字 ≒ 1〜1.5 トークン、英語は 4 文字 ≒ 1 トークン）。正確である必要はなく、削減傾向が伝わればよい。

---

## ユーザーとの対話の進め方

このスキルは半自動である。次のチェックポイントで必ずユーザーに確認を取る。

1. ステージ1で削除候補を出した直後
2. ステージ2の5分類が終わった直後
3. 圧縮後の SKILL.md の素案ができた直後
4. 忠実性ゲートでコアに戻した項目がある場合

それ以外の細かい書き換えはユーザー確認なしで進めてよい。確認は要点を絞り、毎回「進めてよいですか」を聞きすぎないこと。

---

## やってはいけないこと

- 一気に最終形まで進めてユーザーに見せる（途中での修正機会を奪うため）
- 「例」や「テンプレ」を機械的に参照ファイルへ追い出す（暗黙の行動規範を含むことがある）
- 数値・固有名詞・API 名を要約で潰す
- 説明文から識別子を含む節を削る
- 元の SKILL.md を上書きする（必ず別ファイルとして出力する）

## 参考

このスキルは Gao et al. "SkillReducer: Optimizing LLM Agent Skills for Token Efficiency" (arXiv:2603.29919, 2026) の方法論に基づく。論文の核心は次の3点。

- 説明文の 26.4% は空または極端に短く、本文の 60% 以上は非実行的内容である
- 削るとむしろ性能が上がる「less-is-more 効果」が観察される
- ルール・例・背景を1ファイルに混ぜていることが肥大化の根本原因
