# モデルとハーネスのかみ合わせを整えるエージェント設計

LLMコーディングエージェントの実力は、モデル単体ではなく「モデルとハーネスの整合」で決まる。
このスキルは、モデルの意図とハーネスの実行のあいだに生じる双方向のズレを抑え、
ベンチマークで報告された公称性能を自分の環境で再現・超過するための設計手順を示す。

## このスキルを使うタイミング

- LLMを呼び出して道具を実行させるエージェントのハーネス（実行ループ・道具・フィードバック層）を自作している
- 既存ハーネスでモデルを差し替えたら性能が頭打ちになり、原因がモデルかハーネスか切り分けたい
- 強いモデルを入れても弱いモデルと精度が変わらない（`acc(H, 強モデル) ≈ acc(H, 弱モデル)`）状況に陥っている
- 道具呼び出しが空になる・道具名が壊れるなど、説明のつかない失敗が断続的に出ている
- pass@1 では差がつかない複数モデルの「解き方の違い」を観測して、モデルとハーネスを協調設計したい

## 前提となる核心的洞察

このスキルが立脚する一つの考え方は **意図実行ギャップ（intent-execution gap）** である。
これはモデルとハーネスの境界で生じる **双方向** のミスマッチを指す。

1. **下り方向**: モデルが意図したこと ≠ ハーネスが実行したこと
   （例：1箇所だけ置換したいのにハーネスが全一致箇所を黙って書き換える）
2. **上り方向**: 環境で実際に起きたこと ≠ モデルに伝わったこと
   （例：長いシェル出力が途中で切られ、見せるべきテスト失敗が隠れる）

このギャップが厄介なのは、失敗が **両方向で複利的に増幅** する点にある。
誤解された編集は状態を静かに壊し、不十分な実行結果はモデルに誤った前提から
推論を始めさせる。さらにモデルは多くの場合、ハーネス由来の失敗を
「自分の使い方ミス」と誤帰属し、同じ無効な操作を繰り返したあげく、
本来は有効だったタスクを途中で諦めてしまう。これは精度を下げるだけでなく、
文脈に誤誘導トークンを残して以降の品質も汚染する。

設計の出発点となる2つの問いは常にこれである。

- ハーネスはモデルが意図したことを忠実に実行しているか
- ハーネスが何をしたかを、モデルは正確に知らされているか

**重要な戦略判断**: 特定モデル・特定ベンチマーク向けの作り込み
（専用プロンプト、専用道具スキーマ、手組みの実行グラフ）はギャップを一時的に
減らせるが脆い。モデルが更新されると挙動が変わり、過剰適合した最適化は次世代で
劣化する。したがって、**ファミリーや世代をまたいで効く不変の原則を主軸に置き、
ファミリーが本当に異なる箇所だけを適応させる**。これが持続する設計である。

## 全体フレームワーク

ハーネス設計を「不変軸（全モデル共通で固定）」と「適応軸（ファミリー差のみ）」に分ける。

```
                 ┌─────────────────────────────────────────┐
                 │  不変軸（全ファミリー共通・固定）          │
                 │  ・透明で構造化された道具境界フィードバック │
                 │  ・安全な編集セマンティクス（行アンカー＋差分）│
                 │  ・実行ループ／終了条件／計測の同一実装     │
                 └─────────────────────────────────────────┘
                                   ＋
                 ┌─────────────────────────────────────────┐
                 │  適応軸（ファミリー差のみ・最小限）        │
                 │  ・推論ナッジの種類（数値目標 or 柔軟指示） │
                 │  ・道具インターフェースの形（モデルの好み）  │
                 └─────────────────────────────────────────┘
                                   ↓
                 ┌─────────────────────────────────────────┐
                 │  診断ループ（軌跡分析で適応軸を調整）       │
                 │  編集/テスト比・フェーズ構成・バックトラック │
                 │  ・真のエラー率 → 次の改善箇所を特定        │
                 └─────────────────────────────────────────┘
```

設計対象のハーネスは、最小限の構成で十分に機能する。
中核は薄い制御ループ（モデルを呼ぶ→要求された道具を実行→結果を追記→繰り返す）で、
道具面は意図的に小さく保つ（基本はシェル道具1つ＋ファイル閲覧編集道具1つ）。
凝った多エージェント構成や複雑な実行グラフは出発点として不要である。

## フェーズ1（不変）フィードバックを豊かにした道具境界

最優先で実装する不変原則。モデルと道具の境界でやり取りされる情報を
**透明かつ明示的** にする。

### シェル実行の構造化フィードバック

すべてのシェル呼び出しは、最低限つぎを構造化して返す。

| 返す項目 | 目的 |
|---|---|
| 実行したコマンド | モデルが「自分が何を投げたか」を確認できる |
| ステータス（成功/失敗/不明） | 結果の解釈の起点 |
| 終了コード | 真の失敗か想定内かを区別する材料 |
| 標準出力 | 実行結果の本体 |
| エラーテキスト | 失敗時の原因特定 |

タイムアウトで中断したときは、利用可能なら **部分出力を返す**。
長い出力は **中央でクリップし、先頭と末尾は必ず残す**。
失敗の要約や最終テスト結果は出力の端に出ることが多く、そこを失うと
モデルが「見えない失敗」から誤推論するためである。

### 安全な編集セマンティクス

ファイル編集の道具は、つぎの規律を必ず備える。

- **行アンカー**: すべての編集を周辺行に固定し、対象を一意に特定する
- **部分一致・複数一致は拒否**: 曖昧な置換は実行せず、モデルが次のターンで
  より正確な編集を出せるよう、**曖昧さを解消するフィードバック** を返す
  （「指定文字列が複数箇所に一致した／部分行にしか一致しない」等を明示）
- **成功時は適用後の差分（unified diff）を返す**: モデルが「意図した変更が
  本当に当たったか」を別途確認する必要をなくす

この「拒否＋具体的な再試行ヒント」と「成功時の差分返却」の組み合わせが、
下り方向のギャップ（意図と異なる書き換え）と上り方向のギャップ
（変更が当たったか不明）を同時に塞ぐ。

### パス正規化

編集対象パスは、特徴抽出・差分計算の前に **ワークスペース相対へ正規化** する。
絶対パス（例 `/testbed/...`）のまま扱うと、後段の解析や状態追跡で
パス接頭辞が食い違い、状態が正しく追えなくなる。

## フェーズ2（適応）推論と道具呼び出しのバランス調整

連鎖的推論（chain-of-thought）は問題分解・次手計画・道具選択に明確に有用である。
しかし **過剰な内省には固有の失敗モード** がある。長く考えすぎると、モデルは
環境を検証する代わりに環境について **仮定を作り始め**、根拠の薄い道具呼び出しや
必要な検証の省略を引き起こす。逆に推論不足だと道具使用が反応的になり、
浅い探索・冗長な呼び出し・手順の乱れを生む。

この緊張を「**推論ナッジ（reasoning nudge）**」で調整する。
狙いは「次の一手を決めるのに十分なだけ考えたら、さらなる内省より
環境との証拠収集を優先させる」ことである。内省を延ばすのではなく、
道具出力で仮説を検証する方向へモデルを促す。

```
  考えすぎ ←─────────── バランス点 ───────────→ 呼びすぎ
  Over-Thinking          Balanced              Over-Calling
  ・長い内省で行動が遅い   ・次手を決める分だけ考える  ・無計画な頻回呼び出し
  ・環境を仮定で埋める     ・地の真実は道具で取りに行く ・方向性のない反応的実行
  ・検証を後回しにする     ・証拠で反復する
```

### ナッジは「ファミリー固有」である

**全ファミリーに効く単一の「黄金プロンプト」は存在しない。** ここが適応軸になる。

- **数値目標型ナッジ**（Claude系で有効な傾向）:
  「道具呼び出しは50回以上」「理想は100回」のような **定量的な北極星** を与えると、
  長い推論連鎖が切れて環境との対話へ寄る。具体的な目標数そのものは重要でなく、
  行動側へバイアスをかける装置として機能する。
  （注：この定量的な道具呼び出しプロンプトの手法は、Claude Sonnet 4.5 の
  公開時の知見に由来する。）
- **柔軟指示型ナッジ**（Gemini・Grok系で有効な傾向）:
  数値目標を **字義通りに解釈** し、数を満たすためだけに **空の道具呼び出し** を
  乱発するファミリーがある。これは品質をむしろ下げる。こうしたモデルには
  「できるだけ積極的に道具を使う」程度の **数値を伴わない柔軟な指示** が効く。

**経験則**: まず柔軟指示から始め、推論が長すぎて行動が遅いファミリーにだけ
数値目標を試す。数値目標を入れたら「空呼び出しの増加」を必ず監視し、
増えたら柔軟指示へ戻す。

### 「考える道具（think）」の使いどころ

明示的な熟考ステップを設けると、最初の思いつきではなく検討済みの計画で
行動させられる。これは特に、インターリーブ思考を持たない旧世代モデルで
推論の足場として有効。設計指針はつぎの通り。

- 使うべき場面: バグを特定した直後（根本原因を一文で述べ、2〜4個の候補修正を
  挙げ、症状対処か根本対処かを判定して最小の修正を選ぶ）／テスト失敗の直後
  （失敗仮説を尤度順に2〜4個並べ、それらを切り分ける最も安い次手を特定）／
  リファクタや複数ファイル変更の前（方針・影響ファイル・1つの具体的リスクを概説）
- 使わない場面: 一行修正・自明な次コマンド・単純なファイル参照・次手が
  すでに確定している手順。直前にやったことの実況にも使わない
- 出力形式: 3〜5個の簡潔な箇条書き。問題文の再掲はしない

## フェーズ3（適応）モデルの道具利用の好みに合わせる

道具の機能が同一でも、モデルは **呼び出し方の好み** が異なる。これは訓練の副産物であり、
**好みと戦うより活かす**。代表的なファミリー差は以下。

| ファミリー | 観測される好み | ハーネス側の対応 |
|---|---|---|
| GPT系 | 別ファイルのテキストを特定形式で差し込む「patch適用」方式の編集を好む | patch適用型の編集インターフェースを提供する。好みの整形を拒むと性能が落ちる |
| Grok系 | 巨大な単一道具（閲覧＋編集の一体型）は苦手。原子的操作への分割で改善 | 閲覧・編集・書き込みを別道具に分ける。各呼び出しで1つの操作に専念させる |
| Grok系 | 行番号の接頭辞と内容を分離するのが苦手 | 閲覧道具の行番号表示を無効化すると道具を使いこなせる |
| Claude・Qwen系 | 閲覧/作成/置換/取り消しを束ねた一体型編集道具で問題なく機能 | 一体型の str_replace 系編集道具でよい |
| 旧世代・非インターリーブ思考モデル | 熟考の足場が要る | 専用の「考える道具」を付与する |

さらに、モデルが多様なパラメータ名（行範囲の指定キー名のばらつき等）を出してくる
場合は、ハーネス側に **寛容なフォールバック**（入力中から行端点らしいキーを走査して
解釈する等）を持たせる。これは「ハーネスがモデルの好みに歩み寄る」具体例である。

**設計原則**: エージェント性能は「どの道具があるか」だけでなく
「その道具がモデルの学習済み挙動にどれだけ自然に噛み合うか」の関数でもある。
良いハーネスは **実行の不変条件は固定したまま、インターフェースとフィードバックを
モデルの強みに合わせる**。

### バッチ実行インターフェースは万能ではない

複数コマンドを1ターンで実行するバッチ道具は、対話往復のオーバーヘッドを
減らす自然な発想だが、効果はファミリー依存である。

- バッチ化はモデルに **ターンをまたいで一貫した端末状態を保つ** ことを要求し、
  推論の複雑さを上げる
- Claude系: 節約できた往復分を、増えた自己回帰的推論が相殺してしまい、得にならない
- Gemini・Grok系: 追加の推論を誘発しないため、バッチ化が効く

バッチ道具を提供するなら、説明文で **いつ束ねるべきか（互いに独立な探索：
レイアウト調査・複数ファイル読み・無関係な複数テスト）** と
**いつ単一にすべきか（次のコマンドが前の出力に本当に依存する／単一の長時間
コマンド）** を明示する。

## フェーズ4（不変）軌跡分析で診断し、適応軸を調整する

pass@1 は「解けたか」を語るが「どう解いたか」を語らない。
モデルとハーネスを協調設計するには、**軌跡（trajectory）の挙動** を観測する。
ここで得た所見が、フェーズ2・3の適応軸を調整する根拠になる。

### 道具呼び出しを分類して挙動を見る

各道具呼び出しを分類器（LLMジャッジ等）でラベル付けし、軌跡の挙動を集計する。
分類の足場として有効な軸はつぎの通り（自前で組む場合の設計指針）。

- **行動カテゴリ**: 探索/ナビ・検索/特定・コード読み・ソース編集・テスト編集・
  使い捨てスクリプト作成・本物のテストスイート実行・使い捨て実行・環境構築・
  バージョン管理操作 など
- **フェーズ**: explore（リポ把握・バグ再現）→ localize（該当コードへ絞り込み）→
  implement（修正を書く）→ verify（テストで確認）
- **エラー種別**: ここが最重要。**真の道具失敗と想定内の非ゼロ終了を必ず区別する**

### 真のエラー vs 想定内エラー

非ゼロ終了がすべて道具の不具合とは限らない。区別を誤ると診断が歪む。

| 種別 | 例 | 扱い |
|---|---|---|
| 道具起動失敗 | コマンドが見つからない／シェル構文エラー／引数拒否／編集の対象文字列が見つからない | 真のエラー（修正対象） |
| サブプロセス実行時失敗 | 再現スクリプトのトレースバック／import失敗／フィクスチャ読み込み中のクラッシュ | 真のエラー（修正対象） |
| 想定内の非ゼロ | grep の不一致（exit 1）／pytest がテスト失敗を報告（実行自体は成功）／修正前の再現スクリプトを意図的に失敗させた | エラーではない（除外する） |

ハーネスが生で数える「エラー件数」は、想定内の非ゼロを含むため真の失敗率を
過大評価する。**改善の優先度は「真のエラー（起動失敗＋実行時失敗の和）」で測る**。

### 観測すべき診断シグナル

分類結果から、つぎの挙動シグナルを軌跡の正規化位置（0〜1）に沿って見る。

- **編集/テスト比**: 編集寄りの呼び出し（ソース編集・テスト編集・使い捨て作成）と
  読み寄りの呼び出し（コード読み・検索・探索）の比。高ければ「ほぼ編集する」、
  低ければ「ほぼ探索・テストする」を意味する
- **フェーズ構成**: explore/localize/implement/verify の各フェーズが軌跡のどこで
  どれだけの幅を占めるか。実装ピークの位置・幅、検証フェーズの裾の長さが
  ファミリーごとに異なる
- **バックトラック**: 状態を正解から「遠ざける」編集の割合。解決率とは
  ほぼ独立に動くため、別の品質指標として有用
- **真の道具エラー率**: 道具ファミリー別（シェル系 vs 編集系）に集計

### 診断から得られる普遍的な所見

- **同じ解決率でも軌跡は大きく異なりうる**。pass@1 がほぼ同じ2モデルでも、
  テストの扱い（早期から走らせ続けるか、徐々に増やすか）やフェーズの組み方が違う
- **バックトラックは解決率と切り離されている**。バックトラック率が最も高いモデルと
  最も低いモデルが、ほぼ同じ pass@1 を出すことがある
- **タスク難度がフェーズ配分を変える**。難しいタスクほど編集の比率が上がり、
  逆説的に（時間・手数の制約から）テストに割く資源が減る傾向がある

これらは集約指標には現れず、ベンチマークをまたいで安定する **ファミリーの挙動署名**
である。署名を読み、フェーズ2・3の適応（ナッジ・道具形）を当てるべき箇所を決める。

## フェーズ5（不変）推論スタック境界での出力破損をデバッグする

セルフホストや特定の配信スタック経由でモデルを動かすとき、
**モデルの重みでもハーネスの道具登録でもなく、配信境界（serving boundary）で
出力が壊れる** ことがある。これは意図実行ギャップの極端な実例であり、
気づきにくいので独立した手順として扱う。

### 症状と一次診断

- **道具呼び出しの引数本体が断続的に空になる**、または
  **道具名に制御トークン文字列が混入する**（存在しない道具名になり、ハーネスが拒否）
- 強力な一次診断は **キャッシュヒット率の異常**。健全な多ターン軌跡では、
  各リクエストが既処理の長い接頭辞を再投入するためヒット率は1.0へ近づくはず。
  軌跡の途中で **ヒット率がゼロに落ちてキャッシュ書き込みが続く** なら、
  接頭辞照合が失敗しており、エージェントが送った文脈とサーバ側の文脈が
  最終アシスタントメッセージで食い違っている兆候

### 根本原因

多くのチャット補完APIは **トークンレベルでステートレス** である。各ターンで
ハーネスは会話を構造化JSONとして再送し、サーバは前ターンで生成された
トークンIDを再利用せず、フィールド（本文・推論・各道具呼び出しの名前と引数）から
プロンプトを再構築して再トークン化する。この **デコード→再エンコードは恒等写像ではない**。
通常のテキストは往復で生き残る（だからキャッシュは効く）が、再構築された
アシスタントターンは元の出力とバイト同一ではない。高いサンプリング温度の下では
区切りトークンが不適切な位置に生成されやすく、一度混入するとAPIは予約制御トークンと
同じ綴りのただの文字列を区別できないまま、見かけ上は妥当な道具呼び出しとして
クライアントへ返してしまう。

### 対処

- **破損サンプルを、モデルに見えるトランスクリプトへ入る前に再試行可能にする**。
  観測される破損モードをすべて単一の明示的シグナル（再試行可能なHTTPエラー等）へ
  収束させ、ハーネスはバックオフ付きで再試行する。破損はまれなトークン列に
  由来するため、同じプロンプトの再サンプルはたいてい整形済みのターンを返す
- 設計上の根治策として、テキストから再構築せず **生成されたトークンIDをそのまま
  戻す（token-in/token-out）** インターフェースを検討する。JSON経由の補完パスでは
  これができないため、構造化フィールドからの再構築に伴う非可逆性を避けられない
- 教訓: **説明のつかない断続的失敗を「モデルが弱い」で片付けない**。
  キャッシュヒット率・道具名・引数本体の健全性をまず疑い、失敗を配信境界・
  ハーネス・重みのどこに局在させられるかを切り分ける

## チェックリスト

### 不変軸（全モデルで固定する）

- [ ] シェル呼び出しが「コマンド・ステータス・終了コード・出力・エラー」を構造化して返す
- [ ] 長い出力を中央クリップし、先頭と末尾を保持している
- [ ] タイムアウト時に部分出力を返している
- [ ] 編集が行アンカーされ、部分一致・複数一致を再試行ヒント付きで拒否している
- [ ] 編集成功時に適用後の差分を返している
- [ ] 編集対象パスを特徴抽出・状態追跡の前に相対正規化している
- [ ] 実行ループ・終了条件・計測が全ファミリーで同一実装になっている
- [ ] 軌跡を記録し、真のエラーと想定内エラーを分けて集計できる
- [ ] 配信スタックのキャッシュヒット率を監視している

### 適応軸（ファミリー差のみ調整する）

- [ ] 推論ナッジをファミリーに合わせている（数値目標か柔軟指示か）
- [ ] 数値目標を入れた場合、空呼び出しの増加を監視している
- [ ] 道具インターフェースの形をモデルの好みに合わせている（patch適用／原子的分割／行番号有無）
- [ ] バッチ実行道具の効果をファミリー別に検証し、効かないファミリーには無理に使わせていない
- [ ] 非インターリーブ思考モデルに熟考の足場（考える道具）を与えている

### 評価の衛生

- [ ] 実行時情報漏洩を遮断している（後述）
- [ ] 真の失敗率（起動失敗＋実行時失敗）で改善優先度を判断している

## 制限事項と注意点

- **不変原則は万能ではない**。フィードバック設計・編集セマンティクスを固めても、
  モデルとハーネスのファミリー差は残る。不変軸で土台を作り、適応軸で詰める二段構えが前提
- **単一の最適プロンプトは存在しない**。推論ナッジは必ずファミリーごとに当て、
  ベンチマークを変えたら再検証する
- **軌跡分析の指標は構造的であって意味論的ではない**。たとえば正解への距離を
  テキスト変更行の一致で測ると、正しいが表現の異なる修正（別の識別子名、
  リファクタされた式、別位置のガード）を過小評価する。中間状態や未解決軌跡には
  意味論的な距離（AST整合・埋め込み類似・LLMジャッジによる「修正達成度」）の
  併用を検討する
- **バックトラックの解釈はタスク依存**。変更が数行で済むタスクでは全面差し戻しが
  起きやすく、複数ファイルに広がるタスクでは起きにくい。絶対値の比較ではなく
  同条件内での相対比較に使う

### 評価時のデータ漏洩（訓練汚染とは別物）

ベンチマーク評価では、**訓練データ汚染とは独立に、評価環境そのものが解を
漏らす「実行時漏洩」** に注意する。代表例は、コンテナの作業ツリーが正しく
過去時点にチェックアウトされていても、**未来のバージョン管理オブジェクト
（将来コミット・ブランチ・タグ・参照ログ）が到達可能なまま残る** ケース。
エージェントは履歴照会の通常コマンドだけで意図された修正を復元でき、測定された
pass@1 を最大で数ポイント押し上げる。影響はモデルの道具利用挙動によって不均一に出る
（履歴を漁る挙動を持つモデルほど大きく恩恵を受ける）。

対処は **時間的に隔離した環境** を用意すること。作業ツリーは同一に保ちつつ、
エージェント開始前に未来の履歴・リモート・参照を除去し、元のHEADに単一の
ローカルブランチを作り直す。報告時は、隔離後のスコアを使うか、漏洩露出を
明示的に併記する。直接漏洩（正解コミットの照会が文脈に入った確認済み事例）の
計上は **下限** にすぎず、間接的・近傍コミット経由の漏洩は捕捉できない点に留意する。

## 発展的応用

- **軌跡品質の厳密な定量化**: 本スキルでは編集/テスト比・フェーズ構成・
  バックトラックの「シグナル」を診断に使うが、これを数理的に定式化した
  「正解集合への距離（solution distance）」指標として再構成できる。
  ライブ状態のソース差分特徴と検証済み修正の特徴集合のリコール型ダイバージェンスを
  各サイクルで測り、距離の単調減少・面積・閾値到達時刻・編集ごとの増減
  （バックトラック）を時系列で評価する。実行済みの全解決軌跡から経験的な
  参照解集合を構築し、近接解はJaccard類似でマージする。この定量化を
  独立したスキルに切り出せば、「pass@1を超えてエージェントの探索効率と軌跡安定性を
  測る評価スキル」になる
- **協調設計のループ化**: 軌跡署名（フェーズ配分・バックトラック・編集テスト比）の
  観測→適応軸（ナッジ・道具形）の調整→再観測、を回す定常運用に発展させられる
- **道具面の最小化検証**: 道具を増やす前に「その道具がどのファミリーの学習済み
  挙動に噛み合うか」を軌跡で確認し、噛み合わないなら追加しない判断に使う
